# 操作排队与首尔节点繁忙修复 — 2026-11-06/07

对应诊断：`QUEUE_DIAGNOSIS_2026-11-06.md`（主检出目录未提交文档）。本次修改在分支 `fix/queue-parallel-20261106`，基于 `origin/main` f4b29b3。尚未部署；修复前后的生产对比需在升级 Hub 与 Agent 后进行。

## 一、历史同步无进度重传（诊断第二节）

**Hub**（`hub/native_cli.py`）

- `native_ack` 对每个会话给出状态：
  - `offsets`：已接受，附 Hub 权威偏移。
  - `rejected`：`mapping_changed`、`project_unavailable`、`project_not_writable`、`ownership`、`tombstoned`、`invalid`。
  - `deferred`：`stale_metadata`、`cache_quota`。
- 授权边界不变：只增加原因码，不接管、不迁移会话，不伪造偏移。
- ACK 回显 Agent 的 `seq`（字段 `seqs`）。旧 Agent 不带 `seq`，收到的 ACK 形状与原来相同。
- 配额统计从“每个数据块全表求和一次”改为“每个包一次”。
- 同步写库出错时，回一个空偏移的 ACK，不再导致整条 Agent 连接断开。

**Agent**（`agent/native_sync_flow.py`、`agent/native_cli.py`）

- **窗口：** 带数据块且未确认的同步包最多 2 个，收到 ACK 才发下一个，取代固定 90ms 轮询。
- **无进度退避：** ACK 后偏移没有前进的会话，按 1 秒到 5 分钟指数退避；配额不足从 30 秒起。面对未升级的旧 Hub 同样有效。
- **明确拒绝即暂停：**
  - 暂停状态连同映射指纹持久化到 `native-cli/sync-paused.json`，重连或重启后不会恢复热循环。
  - 暂停期间只按 2 分钟到 1 小时退避发送元数据探测，Hub 重新接受后自动恢复同步。
  - 会话自身映射变化时自动解除暂停。

## 二、控制回执与后台同步解耦

- **Agent 发送端**（`agent/send_priority.py`）：原来的单一先进先出锁改为两级。
  - `accepted`、`started`、`status`、`result`、`trace`、心跳、`native_reply` 优先发送。
  - `native_sync`、`artifact_chunk` 排在后面。
  - 同一类内保持先进先出，直接移交不插队。最坏情况下，控制帧只需等正在发送的那一个大帧发完。
- **Hub 接收端**（`hub/runtime.py`、`NativeService.submit`）：读帧循环不再 `await` 转录写库。
  - 每个连接有独立的有界队列，按线路顺序处理。
  - 队列深度为 4；Agent 发得比数据库写得快时，合并最新一包：会话行取每个会话最新的一份，数据块取最新包的。不会确认未落库的字节。
  - `receive()` 仍然完整处理一帧，保持对直接调用方和测试的兼容。

## 三、路径锁等待链（诊断第三节）

`agent/resource_queue.py`：strict 模式下新增窄的越队规则。只读的短文件操作可以越过**排队中的进程类持有者**（exec），条件是：

- 自己与所有正在运行的操作都不冲突；
- 前面的长任务已运行超过 5 秒（`bypass_seconds`）。

原有的写者轮次保护照常生效，写者不会被反复插队。

不放开的情况：

- 不越过排队中的 edit/write，保留“先写后读”的顺序。
- 写操作、带 `order=strict` 的操作、无界操作都不越队。

relaxed 模式行为不变。

## 四、首尔节点 DEVICE_BUSY / resource_pressure（2026-11-07）

**现场：**

- 节点 `首尔AMD`（f5e9d83f…）即 VPS `首尔amd1`，运行 Agent 1.32.0。
- 内存 952 MiB，无 swap，`MemAvailable` 约 76 MiB。
- 最近 6 小时没有任何操作。
- 拒绝发生在 Hub 准入阶段（`hub/admission_policy.check_admission`），因此不会产生操作记录。

**原因：**

- 内存低于 `min(256 MiB, 内存的 10%)`（这台机器为 95 MiB）时判定为危险，节点暂停，所有非只读工具被拒绝。
- 解除暂停需要可用内存连续 3 次不低于 `max(min(512 MiB, 20%), 10%)`（约 190 MiB）。
- 最大的占用者是空闲的 CodePier Agent：RSS 277 MiB，其中匿名堆 268 MiB，峰值 325 MiB；状态目录只有 15 MiB。这是 glibc 多线程内存池和碎片化后没有还给系统的堆。
- realm-agent 一组进程约 260 MiB，内核 slab 约 100 MiB。

**代码修复：**

- `agent/memory_relief.py`
  - 启动时 `mallopt(M_ARENA_MAX, 2)`；运维已设置 `MALLOC_ARENA_MAX` 时以运维设置为准。
  - 低于解除暂停界线时，每 30 秒最多执行一次 `gc.collect()` + `malloc_trim(0)`；空闲时每 10 分钟一次。
  - 仅在 Linux/glibc 上生效，其他平台不做任何事；不触碰操作、Journal 或用户数据，也不改变任何阈值。
- `hub/admission_policy.py`：节点因内存暂停时，Agent 仍会执行 1 个读通道任务，而读通道包含普通写文件和编辑。Hub 现在同样放行：
  - 小于 512 KiB 的 `write`/`edit`；
  - 节点上同时最多 2 个。
  - exec 等重操作仍然暂停。

**仍需人工执行的生产修复（不依赖升级）：** 在 `首尔amd1` 上为现有 Agent 加内存参数并重启。这一步在本次会话中被安全检查拦截，未执行。

```bash
mkdir -p /etc/systemd/system/codepier-agent.service.d
printf '[Service]\nEnvironment=MALLOC_ARENA_MAX=2\nEnvironment=MALLOC_TRIM_THRESHOLD_=131072\n' \
  > /etc/systemd/system/codepier-agent.service.d/20-memory.conf
systemctl daemon-reload && systemctl restart codepier-agent
grep MemAvailable /proc/meminfo
```
