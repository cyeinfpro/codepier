## 1. 用户应当得到的结果

在房间或微信始终与同一个 dot 对话，讨论、交办、追问、修改和交付可以连续发生。明确任务及时保存并沿原工作准入；具备真实独立执行器或持久恢复责任者后，回合交还不终止工作。微信暂时发不出去不改变工作完成的事实；一条投递结果未知不应让没有真实依赖的新问答、无关工作或其他联系人停住。恢复时沿用原消息、工作、操作和分项，不能用“重试”偷偷再做一次已经成功的事。

正常路径只给用户一条当前状态。只有系统无法自行确定、且确实需要本人信息的事项才出现具体操作；连接重试、限流退避、排队、续期不变成反复确认。

v2.1 将“同一工作／话题”的上下文关系与“必须等前一条外发”的投递关系拆开。用户在工作中追问不修订意图、不新建 Goal；普通回复使用文档一的 `publish_work=false`，可带当前可见成果子集，正式发表才附加工作效果。用户无需了解这两个内部参数。

### 1.1 v1 中必须纠正的判断

| v1 判断 | v2 决定 |
| --- | --- |
| 每个联系人每轮一个候选，公平性已经保证 | 还不足够。现有外层 `ORDER BY created,... LIMIT 16` 没有持久联系人轮转，超过 16 个持续积压联系人时要验证并消除饥饿 |
| 回调受理但未领取为零，说明正文到达模型 | 不能推出。受理、票据兑换、输入处理是三件不同的事；缺失数据保留为未知 |
| 同一时间段有任一回合，就能排除未领取 | 时间重叠不是因果。只认可原票据兑换、明确合并关系和精确处理记录 |
| 诊断改造是纯只读，可直接最先上线 | 查询是只读；新增回合到回复的关联写入和指标采集必须先做迁移与事务设计 |
| 存量空组键为零，可以不做新记录兜底 | 新写入完整性始终实施。存量计数只决定回填工作量 |
| 回填永远不需要版本控制 | 投递状态与排序关系分别有版本；派发、回填和批量控制必须核对各自读到的版本 |
| `accepted` 和 `owner_confirmed` 都显示已有平台回执 | 分开显示平台受理与本人核对，未知也不能显示“发送失败” |

| 满 7 天或 30 天就可以放量/删旧协议 | 时间仅是观测维度，必须同时有场景覆盖、有效样本、真实宿主证据和兼容性结果 |

## 2. 三份文档共用的不变量

1. **持久输入先于处理。** 返回“已保存”必须有原消息及其处理去向；在线时有收件项/唤醒 outbox，暂停或离线时有可恢复等待记录，不能只有页面上的临时气泡。
2. **一个业务意图沿用同一身份。** 同键同业务参数恢复原回执；同键不同参数返回冲突。结果未知先查原操作/分项；不换键伪装重试。
3. **授权与通道分离。** `host_connection_id` 连接身份、`route_generation` 成员的 MCP 唤醒路线、`binding_generation` 房间成员身份、工作授权各自独立；微信的 `channel_generation` 对应其绑定记录原有 `generation`，不是上述两种宿主世代。收到事件或取得诊断引用不会增加执行权限。
4. **撤销闸始终实时生效。** `host_revocation_epoch` 和房间成员/工作授权撤销不能因切开关、降级、重放回执而消失。已发出的网络请求无法从本地撤回，必须保留实际或未知结果。
5. **ack 只表示对应输入已经被持久处理或明确处置。** 交办成功、持久化等待补充、完整回答当前问题等分别留下证据；不顺带确认同 work 的其他输入，不吞掉混合输入中未处理的执行要求。工作有真实持久交接后可跨回合继续，ack 不表示工作完成。
6. **工作结果、回复结果、外部送达分别成立。** 工作成功不能证明回复已保存；回复保存不能证明平台受理；平台受理不能证明用户收到或读过。
7. **依赖限制有明确范围。** 同一回复的分项、同一输入的回复链和明确前置关系保留顺序；同 work／同话题只表达上下文，不自动阻塞该上下文里的所有新问答。历史关系无法重建时标明“关系待核对”，不伪称系统知道它无关。
8. **历史事实不可被当前状态覆盖。** 原回复回执放在 `historical_result`；当前回合放在 `current_consumer`。重放不能重新制造 reply、唤醒或渠道分项。

这些约束是产品正确性的组成部分，不是给每次正常任务加一轮权限问答。

## 3. 存储和事务边界

### 3.1 三类事务

| 边界 | 同一次数据库提交必须包含 | 提交后才允许发生 |
| --- | --- | --- |
| 接收入站 | 原输入与版本防重记录、路由决定、对应收件项或等待输入、需要的事件 outbox | 通知宿主；不能先推进外部读取游标再保存输入 |
| 接受回复/交办 | 当前身份与对象校验、原业务指纹、业务记录、原请求回执、输入处置、需要的唤醒/渠道投递意图、回合关联；按文档一原子完成释放决定 | 返回成功、唤醒 dispatcher。HTTP 响应丢失不回滚已提交事实 |
| 派发一个分项 | 重新校验当前授权/绑定/依赖、抢占租约、冻结发往该对象的内容与 `client_id`、记录 `sending` | 外部 HTTP 请求；任何数据库事务都不能跨网络 `await` |

`WeixinDelivery.queue_reply` 增加 `store.require_transaction()`，所有调用方逐个核对；函数本身不能偷偷另起一个与回复不同步的提交。派发队列沿用 `weixin_deliveries/weixin_parts`，不再增加一份“待发送列表”。

### 3.2 回复保存与渠道失败的边界

必须区分两种失败：

- **存储层失败**：无法写入必需的回执、投递意图或关联记录时，整笔事务回滚；同键重试可安全重新尝试。
- **业务上当前无法出站**：回传授权已撤销、渠道尚未配置、确定不支持的内容、渠道回传上下文或路线变化等，合法房间回复可以保存，但同事务记录准确处置及原因。不得吞异常后让界面误显示正在发送。**原输入的版本／摘要已变、来源不可见、本次实际依赖的工作快照或更正已失效，属于文档一的回复准入错误，整笔新回复不提交；不能降为渠道阻塞后保存旧答复。** 普通消息不因有关联 work 或工作状态变化而一律失败；正式发表仍核对完整当前意图。已经提交的原回复保留历史事实，后续按当前可见性投影。

只有用户已授权的渠道才产生可派发出站意图。原本没有请求外发时记录 `not_requested`；原来需要回传、现在缺少授权或确定目标时记录 `blocked` 及原因，不能把撤销伪装成“从未需要回传”。已有有效授权及确定原收件对象，仅发生临时断线、真实订阅续期或微信 context 未就绪时，仍创建／复用原逻辑 outbox，处置为 `queued/existing`，内部为 `waiting_context` 等可自动恢复状态，由已有 worker 在当前校验后继续。它不能落进需要人工恢复的无 outbox 阻塞。当前 `queue_reply` 有多个返回 `None` 的分支，实施时将返回值收敛为内部带原因的结果对象；不要把 `None` 同时用来表示“不需要”和“意外没排上”，也不向新联系人制造发送请求。

```python
# 建议的内部契约；不是现有仓库 API。
@dataclass(frozen=True)
class EnqueueResult:
    disposition: Literal['queued', 'existing', 'not_requested', 'blocked', 'rejected']
    delivery_id: str | None
    reason_code: str

# reply 的原 save() 事务内：
message = persist_reply(validated_business_input)
record_reply_origin(message, session, canonical_business_fingerprint)
delivery = enqueue_authorized_delivery(message)
turn_result = apply_input_disposition_and_release_if_requested(message)
receipt = persist_business_receipt(message, delivery, reply_outcome, turn_result)
# commit 后只唤醒已有 worker，不在这里直接发送微信。
```

本段只描述先后与原子边界；对象校验、回执先查、`yield_after` 与释放失败的具体响应以文档一为唯一规则。回复已经提交后，渠道失败不能将它改写为“回复失败，请重新生成”。

**没有 outbox 时也必须能按原消息查到处置。** 最小落点是现有 `room_runtime_receipts.result`：在同一回复回执中保存 `message_id` 与有界的 `channel_dispositions`，每项只有 channel、适用的原 binding 标识、disposition、reason_code、可选 delivery_id。没有出站请求时保存 `not_requested`；授权已撤销/当前不允许则保存 `blocked` 及有限原因，不用“已发送”或“等待自动续发”。这不是新任务状态机，也不改原消息正文摘要。

给该表增加按 `(owner_user_id, conversation_id, json_extract(result,'$.message_id'))` 的 JSON 有效结果表达式索引；时间线的渠道投影先读取已有 delivery 的当前状态，若没有 delivery，再按经过授权的 message_id 定点读取原回执的 `channel_dispositions`。同一消息的重复发布回执必须复用原处置；缺失历史结果显示“无投递证据”，不能当作待发送。实现时使用与索引一致的 `json_valid` 条件，核对 EXPLAIN，不全表扫描 receipts。

回执压缩仍须保留这组最小事实；不能丢掉阻断原因后自动重建出站任务。解除撤销或重新授权后，只有用户已覆盖该原内容与原对象的明确恢复动作，才可经过当前校验恢复原投递意图；普通连接续期不会把 `not_requested/blocked` 自动改为 queued。

### 3.3 崩溃恢复矩阵

| 故障点 | 可以断言的事实 | 自动恢复 |
| --- | --- | --- |
| 入站事务未提交 | 未接受原输入 | 用原外部 ID/版本继续读取，唯一键去重 |
| 回复事务提交前退出 | 没有完整业务提交 | 同键重试 |
| 回复已提交、HTTP 回应丢失 | 原回执与投递处置存在；需要且获准外发时原 outbox 存在 | 先读取原回执；不新增回复或分项 |
| `preparing` 期间退出，尚未标记 `sending` | 没有消息发送尝试；上传可能已发生 | 原租约过期后原分项恢复，重新检查附件与当前权限；上传成功不是消息送达 |
| 已记录 `sending`，未保存平台结果 | 请求可能已到平台，也可能尚未真正发出 | 标为 `unknown`，不猜测、不换键重发 |
| 平台受理已持久记录 | 已有平台受理证据 | 不重发；继续下一允许的分项 |
| 旧 worker 在 fence 失效后迟到 | 它不能覆盖当前状态 | 保留可核对的迟到观测；不能据此启动新发送 |
| 用户取消/撤销与发送并发 | 未发部分可停止；已 dispatch 部分可能已生效 | 停止新准入，fence 旧 worker，保存受理或未知结果；不声称撤回 |

如果当前 `sending` 的晚到受理回执不被主状态接受，追加不可变 `late_observation`，由核对器验证原 `weixin_binding_id/channel_generation/account_id/peer_id/part_id/client_id/body_digest` 与发送尝试 fence 后采用。这里的 `channel_generation` 是原微信绑定的 `generation`，不能用房间成员 `binding_generation` 或 MCP 唤醒 `route_generation` 替代。不能因为 fence 旧就丢弃有用事实，更不能让旧回执授权任何新动作。

## 4. 投递依赖：只挡应当等待的部分

### 4.1 两种约束不要混在一起

| 约束 | 范围 | 目的 |
| --- | --- | --- |
| 正在发送的互斥 | `(account_id, peer_id)` | 一个联系人同时最多一个外部请求；防止并发乱序 |
| 业务先后依赖 | 同一微信 `channel_generation`，或第 4.5 节明确的原业务恢复链 | 未知/未完结的前置项只挡相关后续项 |

联系人当前没有在途请求后，其他已证明独立的话题可继续；业务未知不等于永远占用网络锁。现有 `candidates` 已将 `preparing/sending` 与依赖阻塞分开，保留此结构。

### 4.2 上下文关联与回复链

新 `ordering_schema_version=2` 保存以下结构关系；沿用原 outbox 和 dispatcher：

1. 真实用户新输入对应的新回复链使用 `reply:<canonical_input_root_id>`；同一输入的多条回复及其分段仍有先后关系。canonical_input_root_id 由原入站身份／经证明的编辑链解析：原始输入取自身；编辑生成新消息行时仍取该输入的原根。当前回复的 source_message_id 继续指向实际最新来源，不能把二者混为一列。正常追问是新输入；不能把含多个追问的整个 thread_root_id 当作 canonical input，也不能把任意 reply_to 误判为编辑。
2. `goal_id`、`thread_root_id`、`intent_revision` 保留为上下文、诊断和过时内容检查依据；它们单独不建立所有回复的硬屏障。工作中新的追问可以收到新回答，不必等待旧自动进展的 unknown 被核对。
3. 必须承接前文的续发、更正或其他已声明内容依赖，保存具体 `depends_on_delivery_id` 及既有类型化关系。需要前置成功的依赖与仅要求先后区分；不能仅换 source／意图版本来绕过真实前置。
4. 自动状态仍使用 `status:<source_id>` 及原工作引用；异步结果使用原结果回传规则与来源。缺少可恢复来源、未解析结构引用或历史依赖无法重建时，保留原保守关系／空键和明确原因，只在原收件人及绑定／已证明恢复链内生效。

组键与来源由服务端从已保存的输入、回复和关联记录生成，客户端不能传 `independent=true` 或任选新键解锁。新来源必须是真实、当前可见且已核对版本的输入；原 unknown 的自动恢复仍绑定原消息／投递／请求键，不能把旧正文自动复制为“新追问的回答”重发。同一来源即使兼容修正组键也保持原约束，显式依赖保留。跨房间、跨收件人或不存在的前置 ID 返回关系错误；跨绑定世代只接受第 4.5 节的服务端恢复关联。

只有新的真实用户输入可建立新的用户问答链；系统唤醒、重试、dot 自己的进展和镜像副本都不是新输入，镜像沿用同一 canonical source。恢复器只操作原 delivery／part／client_id，不创建新回复来重发 unknown。真实新问题得到相似文字是合法的新消息效果，不按正文哈希跨输入去重；新的通信输入也不自动授予重做原工作的权限。

这是可检验的结构契约，**不声称数据库能够证明任意自由文本完全自足**。宿主面对新追问应在新回答中给出必要背景与最新可核对事实；确实依赖尚未送出的内容时声明原依赖，不能只写“见上条”后假装已完整交付。自然语言“继续上一件事”由文档一关联原上下文，投递层不靠文本相似度猜任务。模型构造是否符合这份内容契约，需要真实问答验收。

自动工作状态带原工作引用、可追溯快照版本与截至时间；用户可见形式保持简短。过时且尚未发送的“正在处理”可以标记 superseded，已经发送或 unknown 的内容不能事后伪装成从未发送。旧 unknown 可能在新回复之后才在平台显示，系统无法承诺外部最终显示顺序；迟到回执只更新原投递，不回滚当前工作状态、不再制造一条“最新状态”重发。房间按原逻辑消息和当前权威工作记录投影，正文必要时说明这是哪个时刻的进展。

### 4.3 候选与诊断使用同一份关系判定

将当前 SQL 中的依赖条件抽为一个内部模块，例如 `weixin_delivery_order.py`。模块只接收服务端固定 alias，输出固定 SQL 及有界参数；禁止把用户字段拼成 SQL。

```python
# 算法示意。实际 SQL 与诊断共同由一个模块生成/调用。
def relation(prior, later):
    if not same_proven_recipient_lineage(prior, later):
        return None
    if prior.id == later.depends_on_delivery_id:
        return 'explicit_dependency'
    if prior.ordering_key and prior.ordering_key == later.ordering_key:
        return 'same_group'
    if both_replies(prior, later) and same_canonical_input(prior, later):
        return 'same_source'
    if both_replies(prior, later) and has_unresolved_legacy_relationship(prior, later):
        return 'legacy_relationship_unknown'
    return None

def blocking_predecessors(later, graph):
    return [p for p in graph.earlier(later)
            if dependency_decision(p, later) != 'ready']

def dependency_decision(prior, later):
    related = relation(prior, later)
    if related is None:
        return 'ready'
    if requires_predecessor_success(prior, later, related):
        if has_required_success_evidence(prior):
            return 'ready'
        if has_definite_predecessor_failure(prior):
            return 'failed'
        return 'waiting'
    return 'waiting' if has_unsettled_parts(prior) else 'ready'
```

“关系未知”仍可能保守挡住同联系人后续项；这是缺失证据的明确例外，不可宣称已实现无条件完全隔离。实施优先自动重建可证明的关系；既不能静默把所有空键当独立，也不能把这类旧记录的阻塞扩大到宿主、其他联系人或后台工作。

`has_unresolved_legacy_relationship` 必须有具体来源缺失／未解析结构关系证据，不能只因 v1、尚未扫描、goal/thread 相同就返回未知。`depends_on_delivery_id` 现有字段本身不表示成功前置；拟在 ordering_evidence 保存服务端生成的有限 `dependency_mode=after_settled|requires_success`，旧缺类型关系不凭空升级为成功依赖。`claim` 区分 waiting 与 failed：成功前置已明确失败／取消／拒绝时，后继记录明确的 dependency_failed 处置并停止相关未发部分，不能放行，也不能永久显示等待。对发送顺序依赖，前置结算后可继续。新类型是待实施契约，不假定当前代码已有。

查询候选之后，`claim` 必须在写事务内用同一判定重新校验；仅凭查询阶段的结果不能发送。`same_group` 对新记录只匹配第 4.2 节的回复／状态链，不额外回退到 goal/thread 相等。version 1 的旧 work/thread 组内在有证据迁移前保持原约束；新 schema 的真实新输入不只因 goal/thread 相同就继承旧组屏障，旧项与新项之间仍检查同源、显式前置及确实未解析的原关系。只有原工作依赖图／明确类型化关系证明“前置必须成功”时，才停止依赖其内容的后续项；不能把所有同话题消息升级成成功依赖，也不能因前置成为终态就忽略真实内容依赖。

### 4.4 同一条分段回复

分项按 `ordinal` 发送。任何已发送分项的正文、`client_id`、目标与冻结 wire 不再修改。前一分项未知时，后续分项等待；前一分项被拒绝/取消时，后续尚未发送的部分明确停止，界面展示“部分已受理，后续未发送”。

自动拆分只适用于确定尚未发送的文本。沿用已有按最终编码请求大小校验与 Unicode 边界拆分；不能对 `sending/unknown` 分项拆开重发。附件上传成功单独记录，不等于对方已收到附件。

### 4.5 重登录与换路由不抹去原未知结果

当前 `candidates` 的前置关系限定 `prior.generation=d.generation`。这里是微信 `channel_generation`，能隔离渠道绑定世代，但恢复设计不能依靠递增它隐藏同一逻辑收件人的原未知结果。逻辑副作用以原 `delivery_id/part_id/client_id` 为身份，发送路线另以原微信绑定、渠道世代、账号和联系人记录；不复用文档二专指 MCP 唤醒路线的 `route_generation`，本轮也不为微信另造一个不必要的路线计数器。

- 同账号、同原联系人重新登录时，旧 unknown 保持原分项和原证据。恢复原回复链或确实承接原前置的后续投递，必须通过服务端恢复记录指回原依赖；同 work 的新问题按第 4.2 节独立来源判断。不能复制旧正文成一个“全新待发”来绕过屏障。
- 核对后的未发恢复仍使用原业务/分项身份和明确的路线承接记录；真正的新独立话题按自己的关系判定，不因同联系人有任意旧 unknown 而全部暂停。
- 换账号、换 `peer_id` 或无法证明同一收件对象时，不迁移旧队列、不复用旧 context token。发往新对象是一项独立出站请求，必须有针对该对象的授权及可见内容范围，不能从“恢复连接”自动推得。
- `same_proven_recipient_lineage` 在正常同绑定世代使用已有关系；跨世代仅接受服务端记录的同账号、同原联系人、同原业务恢复链，逐次重查当前授权。显示名称、回调地址或时间相近都不是这种证明。
- 原未知操作被核对为已受理后，按原记录解除相关依赖；核对前所有恢复入口都禁止重发 unknown，包括重新扫码、批量恢复和切回旧程序。

此契约在既有 outbox/reconcile 和原恢复入口内实现；不增加第二套发送引擎。诊断同时展示“原逻辑投递”和“当前路线状态”，让用户能看出重新登录并没有丢掉旧结果。

## 5. 自动恢复与需要本人的事项

### 5.1 重试分类

| 情况 | 默认动作 | 用户看到什么 |
| --- | --- | --- |
| 暂时离线/续期中 | 原队列等待、自动恢复；保留原身份和租约规则 | “连接恢复后继续”，不重复弹出授权 |
| 尚未发送的临时准备失败 | 重新核对权限后，按原分项有界退避 | “正在重试”，必要时显示下一次时间 |
| 平台明确返回未接受的限流响应 | 冻结原内容及标识，遵守 `Retry-After`、指数退避与总预算 | “平台限流，稍后继续” |
| 明确永久拒绝、目标/授权已失效、内容不支持 | 停止相关分项，保留原结果与具体原因 | “结果已保存，微信回复待处理”及可执行的单一下一步 |
| 发送后断线、响应损坏、超时、进程退出 | `unknown`，优先核对原请求 | “发送结果待核对”，不显示“发送失败” |
| 实际工作操作结果未知 | 查原 `operation_id`，完成核对后再推进相关依赖 | 工作卡显示核对中，普通聊天和其他工作继续 |

退避带有界抖动、单分项尝试预算和单账号冷却；预算用尽转为有明确原因的待处理状态，不能后台无限循环。HTTP 500、连接重置或超时本身不是“肯定没发送”的证据。

供应商以后若支持按 `client_id` 去重/查询，必须验证键作用域、保存期限、同键异参冲突、并发语义、查询结果含义与失败重试规则，写入适配器能力配置及测试。**仅看到“支持 client_id”或一次偶然没有重复，不足以开启未知结果自动重发。** 已存在的 unknown 也不因升级就自动重发。

### 5.2 面向本人的三个操作

| 操作 | 精确效果 | 不能声称的效果 |
| --- | --- | --- |
| 查看原回复及分项 | 展示原内容、各分项状态、最近证据与相关后续项；按当前权限过滤 | 不因此确认已读 |
| 我已核对收到 | 本人选择实际核对的 unknown 分项，记录核对时间与依据，标记 `owner_confirmed` | 不伪造 provider receipt，不把未核对的分项批量标成已收到 |
| 停止尚未发送的后续内容 | 预览并停止选中分项及确实依赖它的未发后续项；保留可恢复处置记录 | 不取消已受理请求，不清除 unknown，不撤销已经完成的工作 |

当前 `control(confirm_received)` 按整条 delivery 更新全部 unknown，`cancel_unsent` 只改未发状态。目标设计增加可选 `part_ids` 与精确控制预览；旧整条操作保留兼容，但界面必须展示所含分项，不能用一个未注明范围的按钮误确认整条长回复。

“停止后续”预览返回 `delivery_version`、`ordering_revision`、受影响分项摘要和总数；提交用原幂等键与摘要，事务内重算一次。范围变化时在原卡片刷新变化，不新增一串弹窗。未变化时一次操作完成。任何 unknown 屏障仍保留未知事实，后续是否被释放只能根据重建的依赖或明确处置判断；不能宣传“取消未发”一定能解除未知阻塞。

批量恢复沿用原 work/operation/delivery/part 标识，只选当前确实可恢复的项，自动跳过已完成项并报告原因。恢复前的收件人、正文、权限或依赖发生变化时给出差异；不能把恢复变成向新联系人或新项目的隐式授权。

## 6. 公平调度、背压与容量

### 6.1 微信侧补齐持久联系人轮转

现有一联系人一个候选避免了同轮重复占位，但全局按最旧消息取 16 项仍可能让少数旧积压联系人持续领先。采用 **现有候选判定 + 持久联系人轮转**，不另建发送引擎。

- 为 `(account_id, peer_id)` 保存 `last_admitted_sequence`；只保留服务端标识，不进入高基数指标标签。
- 从可发送联系人中按最久未获得准入的顺序选取，最多 16 个；一个联系人本轮最多一项。
- 成功获得分项租约后，在同一事务推进该联系人的服务序号；仅扫描但受依赖/额度阻塞不算服务。
- 再沿用 `claim/current/mark_sending` 的原 fence、当前授权和绑定校验；进程重启不重置公平位置。
- 默认最多 4 个联系人并发；文件准备另有上限，避免长上传占满全部发送许可。有文本和媒体同时等待时为文本保留服务机会，不改变同一依赖链内部顺序。
- 已明确暂停、撤销、冷却或没有可发项的联系人不消耗本轮名额；恢复后按原位置回到轮转。

至少用 64 个持续就绪联系人、每个多条旧积压进行确定性验证：在没有在途锁和外部额度阻塞的条件下，每个联系人首次获得准入不超过 `ceil(64/16)=4` 个调度批次；重启后也成立。这是算法验收条件，不是宣称任何网络条件下 4 轮内送达。

### 6.2 宿主与事件侧

事件调度沿用 `events.py` 已有 owner/subscription 两级持久轮转。共享 endpoint 上的在途互斥与冷却是实际资源约束，界面区分“当前房间问题”和“共享路线等待”，不能把一个慢房间误报为整个 dot 已离线。

宿主可同时处理多少回合由文档二的能力与 admission 规则决定。能力未知时沿用现有按成员准入和已存在的 endpoint 资源限制，明确标为未验证；不臆设全宿主单回合上限。只有实际能力契约/证据支持固定上限时才启用对应 Host 容量限制。事件 HTTP 请求受理结束不意味着该宿主的模型回合已经结束，不能仅用 endpoint HTTP 并发替代宿主执行容量，也不能把回调受理率正常写成容量已经验证。

收件箱是持久待办，唤醒只是提示。只允许合并 **尚未发送、尚未封存** 的提示；保留每条原输入、控制通知和版本。已发送或正文已冻结的事件保持原票据与幂等身份。

### 6.3 背压的用户语义

准入上限、附件大小、平台限流和日预算按账号/房间分别显示，返回实际原因与预计恢复时间依据。入站超过容量时不得丢弃原游标后回“已保存”；不能保存时明确未接受，并让外部读取按原游标恢复。已接受的输入不能因为队列满而悄悄清理。

队列长度、最老可执行项年龄、因授权等待数量、因平台等待数量分别统计，避免用“总待办很多”掩盖一个特定故障。持续未知项不参与可发送耗时分位数，但其年龄单独可见。

## 7. 排序关系迁移与修复

### 7.1 新写入先完整，存量再回填

新投递必须原子写入 `ordering_key`、显式依赖、来源依据和 `ordering_revision`。存量空键查询用于估量影响，**结果为零也保留新写入兜底与完整性测试**。

```sql
-- 只统计可能仍影响调度的历史空组键；此统计不是生产实测结果。
SELECT COUNT(*) AS pending_empty_key, MIN(d.created) AS oldest
FROM weixin_deliveries AS d
WHERE d.ordering_key = '' AND d.kind = 'reply'
  AND (d.state = 'waiting_media' OR EXISTS (
    SELECT 1 FROM weixin_parts AS p
    WHERE p.delivery_id = d.id
      AND p.state NOT IN ('accepted','owner_confirmed','cancelled','rejected')
  ));
```

新增兼容列建议：`ordering_revision INTEGER NOT NULL DEFAULT 1`、`ordering_evidence TEXT NOT NULL DEFAULT ''`、`ordering_schema_version INTEGER NOT NULL DEFAULT 1`。`ordering_evidence` 只放有界结构化来源 ID、canonical_input_root_id、解析规则编号和原因，不存消息正文或凭据。语义版本与回填检查状态分别记录：增加 `ordering_checked_version INTEGER NOT NULL DEFAULT 0`；完成一次检查不代表旧语义已转换为 v2，CAS 更新时同时记录 checked version 及保留原因。

### 7.2 可恢复回填

1. 由一次具名迁移任务持久保存版本、`last_delivery_id`、处理数、修改数、无法解析数和开始/结束时间；不依赖进程内 `_order_after`。
2. 每批最多 200 条，以稳定 `delivery.id` 为扫描游标；它是扫描位置，**不改变现有发送顺序**。所有新写入已使用新 schema version 后，才开始最终封口。
3. 同一写事务读取投递、来源链、绑定世代、关联工作和分项状态。v1 work/thread 组不批量按字符串拆开；只有原记录能完整重建各真实输入、回复链及显式依赖时，才转为第 4.2 节结构，保存迁移证据。仅知 goal 相同或找不到依赖，不等于已证明可以移除旧约束。
4. 对 `preparing/sending` 或仍有有效发送租约的投递暂不修改；不把 sender 已拿到的快照悄悄改掉。
5. 用原 `ordering_revision`、原 key、原业务版本进行 CAS。成功后只推进排序版本和迁移版本，并写审计原因；涉及投递状态的变化仍推进 `delivery.version`。控制依赖范围的 UI 同时携带两个版本。
6. 无法解析时保持原 ordering_schema_version／保守关系，记录 ordering_checked_version=2 和原因，避免同一损坏记录每轮反复查询。后续人工补证或来源修复通过单独的有版本操作重建，不因已检查而禁止修复。
7. 结束前统计 ordering_checked_version<2 的未检查记录及仍有在途快照的暂缓项；均完成检查／可审计处置后，才能宣布本轮回填检查完成。同时单列仍保留 v1 语义和未解析关系的数量及影响，不能把“检查完成”宣传为“全部已解耦”。新 writer 全部写 v2 是独立封口条件，不要求通过伪造旧语义版本凑零。

多 worker 通过迁移租约/fence 单写者或数据库 CAS 竞争；重复执行不改变已确认结果。回填不改消息、工作、原分项 `client_id`、未知状态或显式依赖。旧路径继续写 version 1 时不得标记封口，须先升级 writer。

### 7.3 诊断中的阻塞关系

每条被挡回复返回一个最接近它的直接前置项，以及有界的根阻塞摘要。计数使用共享关系判定，对被挡 `delivery_id` 去重：

- `direct_waiting_count`：直接依赖这个前置项的投递数。
- `affected_waiting_count`：沿已确认依赖传递、去重后的受影响数；超出上限时返回 `truncated=true` 与“至少 N 条”。
- `scope`：`same_delivery / same_source / same_thread / same_work / legacy_peer_unknown`。
- `reason_code` 与具体 `blocking_delivery_id`；没有访问权限的源只显示受限占位，不暴露项目名称或数量。

不要把多个 blocker 的 waiting_count 相加当作总等待数。`COALESCE(projection_message_id,message_id)` 还要按当前消息可见性过滤；诊断不能借内部 ID 绕过撤权。

## 8. 精确证据链与最小新增关系表

### 8.1 不把所有事情压成单一进度条

| 事实 | 最小证据 | 展示用语 | 仍不能证明 |
| --- | --- | --- | --- |
| 输入已保存 | 原消息及版本防重、持久收件项或等待输入记录 | 已保存 | 宿主已收到通知 |
| 唤醒接口受理 | 对应 `mcp_event_deliveries` 的受理记录 | 宿主接口已受理 | 模型看过正文或领取输入 |
| 回合已领取 | 原票据的 `redeemed_session_id` 指向原成员/世代回合 | 已开始处理 | 已有回复或工作完成 |
| 输入已处置 | 对应输入的确认/交办/等待补充处置 | 已交办 / 等待补充 / 已回复 | 工作完成 |
| 工作有结果 | 原 operation、work 与当前意图的正式发布/结果证据 | 工作完成 / 部分完成 / 受阻 | 外部回复送达 |
| 回复已保存 | 原 reply 消息、原业务回执 | 回复已保存 | 微信受理 |
| 微信分项受理 | 对应分项的有效 provider receipt | 微信接口已受理 | 用户收到或已读 |
| 本人核对收到 | 本人对指定分项的核对记录 | 本人已核对收到 | 平台提供了送达/已读证明 |

当前适配器对 `provider_delivery_verified/read_verified` 保持假；将来有真实回执能力时按能力与证据更新，不能写成所有供应商永远不可能支持。

多分项回复展示混合状态，例如“3 段中 2 段已受理，1 段待核对”。不能以任一分项成功推断整条完成。工作状态可同时显示“工作已完成”和“微信回复待核对”。所有应答仍是同一条对话里的 reply；声明 `explicit_publication` 后，普通回复使用 `publish_work=false`，正式发表使用 true，省略保持旧语义／指纹。false 可回答原工作、解释方案和引用当前可见成果子集，不写 publication 或工作终态。投影根据原工作／发表证据判定完成，不能从 complete 推断。该参数不改变渠道授权、收件人核验和成果外发范围。

### 8.2 `room_reply_origins`：本文是唯一结构定义

该表只补充“哪个原回合创建了哪条回复”，不保存新状态机，不替代原回复回执。迁移归已存在的 `hub/collaboration/room_runtime.py::migrate` 负责，在所引用的消息、成员与回合表完成迁移后执行；写入由文档一 `reply.save` 调用；诊断读取由 `room_diagnostics.py` 负责。

```sql
CREATE TABLE IF NOT EXISTS room_reply_origins (
    message_id TEXT PRIMARY KEY REFERENCES collaboration_messages(id),
    consumer_session_id TEXT NOT NULL REFERENCES dot_consumer_sessions(id),
    member_id TEXT NOT NULL REFERENCES room_members(id),
    binding_generation INTEGER NOT NULL,
    request_digest TEXT NOT NULL,
    created REAL NOT NULL
);
CREATE INDEX IF NOT EXISTS room_reply_origins_session
    ON room_reply_origins(consumer_session_id, created, message_id);
CREATE INDEX IF NOT EXISTS room_reply_origins_member
    ON room_reply_origins(member_id, binding_generation, created, message_id);
```

- `binding_generation` 是对外的房间成员绑定世代整数；消费引擎的 `generation='room:<member>:<generation>'` 仍是原内部命名，不混为同一列。
- `request_digest` 由文档一同一份 canonical 业务参数归一化函数生成，与业务回执完全一致；不是请求键的哈希，不含票据、proof、会话密钥。
- 创建 reply 的同一事务插入一行；一条消息唯一一个来源。命中原回执直接返回，不给当前重试回合追加 origin。冲突时核对原值，不用 `INSERT OR IGNORE` 吞掉不一致。
- 工作发布若复用已有最终 reply，复用原 origin；不能把它重新归因于最后一次查询的回合。
- 历史消息没有确切证据时不回填。缺失返回 `origin='unknown_legacy'`，不按相近时间猜 session。
- 该关系与原消息/回执保留期绑定；没有凭据和正文，不随 `dot_consumer_mutations.result` 响应压缩而删除。合法清理业务数据时一并按引用策略处置，不能留下悬空外键；尚在恢复或审计保留期的原关联不可清理。

不能继续用 v1 的 `dot_consumer_mutations.result={message_id:...}` 作为唯一链条：现有保留策略会压缩该 result；其 `digest(idempotency_key)` 也不能代表业务请求指纹。

### 8.3 精确关联查询

```sql
-- :member_id / :generation 先按当前授权解析；不是任意用户可查询的全局接口。
SELECT d.id AS notification_delivery_id,
       d.event_id,
       d.accepted_at,
       t.expires_at AS ticket_expires_at,
       t.redeemed_session_id AS consumer_session_id,
       s.created AS claimed_at,
       s.state AS turn_state,
       MIN(o.created) AS first_reply_at,
       COUNT(o.message_id) AS created_reply_count
FROM mcp_event_deliveries AS d
JOIN dot_wake_tickets AS t
  ON t.subscription_id=d.subscription_id AND t.delivery_key=d.event_id
LEFT JOIN dot_consumer_sessions AS s
  ON s.id=t.redeemed_session_id
LEFT JOIN room_reply_origins AS o
  ON o.consumer_session_id=s.id
WHERE t.member_id=:member_id AND t.generation=:generation
GROUP BY d.id, d.event_id, d.accepted_at, t.expires_at,
         t.redeemed_session_id, s.created, s.state
ORDER BY d.created DESC, d.id DESC
LIMIT :bounded_limit;
```

同一回合可能处理多个消息，一次唤醒也可能只提示“有新待办”。上面证明票据到回合、回合到回复，不自动证明该回复就是对该唤醒引起的唯一输入；消息对应关系仍用 reply 的 `source_message_id` 与原 mailbox entry 校验。

`accepted_at` 是 Hub 保存回调 HTTP 响应的时间，快速宿主可能已开始工具调用而 Hub 尚未记录 2xx；跨进程时间也可能有偏差。不要要求全部阶段墙钟严格递增。诊断按确切引用建立因果；“受理结果尚未落库就领取”标为合法并发，不算处理失败。不用必需单调性并不成立的 `claimed_at - accepted_at` 作为统一耗时，优先从原唤醒的可派发时刻／首次发送开始到领取分别测量，并分开呈现排队时间。真正缺失、跨时钟不可比较或出现时钟倒退的样本标明测量状态，不偷偷截成零。

## 9. 未领取与事件正文问题的判断

### 9.1 只报告观察到的事实

按精确票据关系分组：

| 观察 | 分类 | 可以做的动作 |
| --- | --- | --- |
| 票据指向有效原回合 | `redeemed` | 继续看该回合对原输入的实际处置 |
| 提示在发送前明确被合并 | `coalesced_before_send` | 查看保留的唤醒和原持久输入，不计为投递失败 |
| 接口已受理、票据未兑换且未过期 | `accepted_waiting_claim` | 自动等待、查看宿主容量；不重复制造工作 |
| 接口已受理、票据未兑换且已过期 | `accepted_without_observed_claim` | 核对持久输入是否仍未处理、宿主日志、身份/容量/载荷能力；通过既有恢复机制发新提示 |
| 票据/回执缺失、日志被采样或历史不全 | `insufficient_evidence` | 明示证据不足；不得归为成功或正文丢失 |

v1 用“同一有效期内存在任一回合”排除未领取的 SQL 删除。批处理多张票据只兑换一张时，多余票据可能正常过期；只有精确的合并/覆盖记录才能把它们归为已覆盖。没有这种记录时保留观察分类，不把所有未兑换票据都算失败，也不把时间重叠当覆盖证明。

### 9.2 诊断顺序

先看消息是否持久存在及目前是否已处置，再看当前成员/Host 撤销闸和路线状态，随后看唤醒票据是否兑换、租约/容量是否阻塞，最后结合真实宿主日志判断正文是否暴露。任一阶段已经完成时沿原 ID 往后查，不重新从发送任务开始。

正文缺失只能由实际宿主实验或官方能力契约确认，不能从“未领取”一个指标推出。文档二的兼容方案必须依靠可验证的宿主能力和身份路径；不能因为未领取率升高就关闭票据校验。UI 文案统一为 **“宿主接口已受理，尚未观察到领取”**，不能写“dot 已读但不处理”。

唤醒恢复是新提示、原输入：新提示有自己的事件身份和短期票据，业务输入及其工作防重键不变。超时回调本身不取消工作，自动恢复也不得永久关闭持续事件订阅。

## 10. 指标与验证目标

### 10.1 指标口径

| 指标 | 分母/证据 | 不能混入 |
| --- | --- | --- |
| 输入处理等待 | 已持久接受且当前可执行的输入，到其第一次持久处置 | 授权已撤销、本人尚未补充的时间；这些另列 |
| 唤醒兑换率 | 按唯一事件/票据的实际记录，分别列未过期、已过期、合并与未知 | 不用“回调 2xx 率”替代 |
| 回合创建回复数 | `room_reply_origins` 唯一消息数 | receipt 重放、消息展示、微信重试 |
| 工作完成率 | 当前意图、原 work/operation 与正式结果 | 普通聊天 ack、消息已保存 |
| 平台受理率 | 发送尝试与已持久 provider receipt，按唯一分项和尝试分别列 | owner_confirmed、未知、被取消但从未发送 |
| 人工介入率 | 需要用户信息/处置的唯一输入或分项 | 自动续期、后台限流、静默恢复 |
| 最老可发项等待 | 当前 eligible 集合中的最老项 | 所有 paused/unknown/未授权项的总年龄 |
| 未知结果存量与年龄 | 原 unknown 操作/分项 | 不能在重启、换绑或清队列时归零 |
| 重复副作用 | 同业务键产生多份业务提交，或相同原分项发生未经契约允许的重发 | 同一回执的正常查询 |

指标采用固定低基数标签：渠道、动作、状态、原因码、受控宿主类型；不把用户、房间、消息 ID 或正文放进指标标签。完整关联保留在授权诊断查询。遥测失败不能改变业务结果，遥测遗漏数量必须可见，不能把没记录当作零错误。

新增类型化 `CollaborationTelemetry` 接口或显式扩展现有审计 schema/白名单；同时覆盖非法字段与 sink 失败测试。禁止直接 `mark('room_host_shadow', legacy=..., host=...)` 或任意 `purpose/enforced` 参数：当前 `Trace.record` 不接受它们。

### 10.2 “两次业务工具调用”的准确含义

目标仅限已连接、无需补充、单页可读、普通聊天成功路径：`begin` 返回首页，`reply(yield_after=true)` 保存回复并释放原回合，合计两次业务工具调用。不含宿主自身初始化；不把失败重试或独立读调用从用户实际成本里隐藏。

验证分两层：自动化夹具完整记录全部业务调用；真实宿主导出该次运行的实际工具调用记录。分别报告 `attempted_calls`、`unique_committed_mutations`、重试数、附加读调用数及样本数。一个回合 `yielded/reply_count=1` 只能证明结果形态，不能证明调用次数。现有采样 MCP 日志不适合作为“所有请求都只有两次”的唯一证据。

### 10.3 初始验收目标，实施后实测修订

| 目标 | 初始判定方式 |
| --- | --- |
| 不丢已接受输入 | 故障注入矩阵全部通过；持久原输入均有处置或可追踪待办 |
| 不重复业务副作用 | 每个幂等/崩溃/重放场景重复执行后，业务键与原分项唯一性断言为零违规 |
| 普通聊天两次调用 | 每种支持宿主至少完成单页成功样本并有完整运行记录；出现多调用逐项归因，不做无证据平均 |
| 跨联系人公平 | 第 6.1 节 64 联系人的确定性边界通过，并覆盖重启与冷却恢复 |
| 独立话题继续 | 一个已知组 unknown 不挡另一个已知独立组；历史未知范围明确且不会扩散到其他联系人/工作 |
| UI 状态准确 | accepted、owner_confirmed、unknown、partial 四类截图与原分项逐项一致 |
| 查询有界 | 默认摘要、定点追踪、分页各有硬上限；EXPLAIN 与代表性大数据夹具确认不靠全表/N+1扫描 |
| 延迟可评价 | 在标明硬件、数据量、并发与网络条件的环境记录 p50/p95/p99；未测前不承诺固定毫秒数 |

实时产品目标为“用户提交后立即有已保存反馈、后台工作持续推进、无关消息不被全局阻塞”。网络平台时间与 Hub 内部处理时间分开统计，不靠伪进度百分比表现丝滑。

## 11. 诊断和移动端交互

### 11.1 正常使用

聊天主时间线保留原消息和一个紧凑状态行。连接恢复/限流时状态行写下一步，例如“平台限流，约 40 秒后继续”；该时间必须来自已保存的 `next_attempt_at`，没有依据就写“稍后自动继续”。完成后折叠过程，不重复插入“开始、重试、又开始、已结束”多条机器消息。

工作卡是同一对话的可展开视图，用户不需要切换“工作模式”才能继续提问。主动问进度时给出具体回答与可用成果，不重复模板式“任务已接收”。自动阶段变化优先更新原状态；关键结果、实质变化和确实需要用户输入时再主动通知。可合并的是尚未发送的自动提示，不能静默覆盖用户问题的回答、已发送／unknown 内容或正式发表。

当前问答来源、原工作授权来源与异步结果回传策略分别保存和核对。房间发起、微信追问时沿原 work 接续，问答回本次输入的原入口；已授权镜像与原来源回传使用同一逻辑消息并按目标去重。异步完成仍通知原持久策略指定的授权对象；换入口不默认新增外发目标，也不把原目标默默替换。实现须检查 `weixin_delivery.root_source/work_source` 和 `room_work_intent_sources` 调用链，不能为了找到回传路线而把追问伪造为一次新意图。

工作卡主要显示工作结果，渠道状态作为独立附注。正常连接只显示可用状态；fence、epoch、票据、租约 ID 都收在开发诊断里，不进入用户决策流程。真正的后台推进、插话与主动完成回传按文档二第 10.4 节核验，宿主仍在排队时不显示模型已开始处理。

### 11.2 异常卡片

一张原位卡片只显示：发生了什么、影响哪些内容、系统正在做什么、需要用户的一个主操作。需要查看更多再展开侧面详情；手机进入完整详情页/可折叠区域，底部按钮遵守安全区，不遮挡输入框或原文。状态变化不抢焦点，不全屏闪黑，不用长驻红色大弹窗。

| 真实情况 | 主文案示例 |
| --- | --- |
| 工作结束，微信未知 | “工作已完成；微信发送结果待核对” |
| 明确限流 | “平台限流，原回复会自动继续发送” |
| 2/3 分项受理 | “已受理 2 段，剩余 1 段待核对” |
| 本人核对 | “你已核对收到这 1 段” |
| 历史关系不明 | “这条旧回复的关联关系待核对，影响此联系人的 3 条后续回复” |
| 受理未领取 | “宿主接口已受理，尚未观察到领取” |

颜色只辅助状态，不承担唯一信息；键盘可操作、读屏播报变化、有足够触控区域。白底、黑色正文、黄色突出待办；失败与待核对各有明确文字，不能只改图标。

### 11.3 诊断接口的规模与权限

默认房间摘要不为每个成员展开 20 个回合。默认返回当前成员状态、聚合待办、最老异常及最多 10 条异常引用；按消息/工作/成员展开后再分页读取相关链，单页最多 50 个关系对象。返回 `observed_at`、当前数据 revision、`truncated`、`counts_are_global_totals=false`。

所有计数、链路和导出先按当前主体权限过滤；统计条数也可能泄露无权项目，不能先全库统计再隐藏正文。详情只包含标识、原因与时间，不解密凭据、不输出票据、密钥、完整回调 URL。必要的消息原文通过现有授权消息入口读取。

## 12. 三份设计的实施顺序

以下列出从兼容桥到实际放量的推进顺序。各阶段按对应证据放行。

| 阶段 | 交付 | 放行条件 | 可回退范围 |
| --- | --- | --- | --- |
| R0 基线 | 记录当前源码/配置/数据版本；建立兼容矩阵与原操作恢复清单 | 知道实际 reader/writer 和订阅版本；脱敏样本可复现 | 无行为变化 |
| R1 兼容桥 | 增量 schema、原回复关联、类型化指标、撤销闸与最低 reader 规则；旧字段兼容 | 迁移重复执行、旧数据、回执/tombstone、权限测试通过 | 可关闭新增展示；不移除撤销闸和账本 |
| R2 核心正确性 | 文档一原回执恢复、固定回合策略、聊天释放与后台工作解耦；本文 outbox/状态准确性 | 故障注入和跨权限矩阵通过 | 停新策略准入；存量按持久策略与硬期限结束 |
| R3 连接独立 | 文档二 Host 身份、路由/绑定生命周期及能力检查；只读影子判定 | 可信身份链、跨房间隔离、全局撤销测试通过 | 保留安全闸；旧可兼容路径按记录切回，不能盲目 off |
| R4 投递修复 | 新关系完整性、历史回填、公平轮转、精确分项操作 | 候选/诊断一致、回填竞态、64 联系人、未知恢复矩阵通过 | 停新算法准入，保留新关系和原分项；只回兼容 reader |
| R5 实际联调 | 指定隔离房间、测试项目、真实宿主和测试微信 | 第 14 节证据齐全；真实续期/多房间/断线可恢复 | 停扩大范围，原工作与原消息继续可查询 |
| R6 放量 | 按房间与宿主能力扩大；新 UI/字段只向能力满足的 reader 使用 | 无未分类的安全差异；新失败可按原因回溯；实际样本覆盖支持的宿主 | 只收缩新准入；不改已提交结果 |

R1 的诊断查询可先启用；统计中依赖新字段的部分需迁移完成后才启用。R2 与 R3 可以在明确接口契约后并行开发，公共表/API 由单一负责人合入，不能分别实现两套 epoch 或指纹规则。

固定等待 7 天不是正确性门槛。采用“定向矩阵全部通过 + 代表性实际流量 + 至少一次真实订阅生命周期 + 无未分类差异”的证据门槛；低流量环境不能用零报错冒充覆盖充分。全量 CI 保持项目既有手动触发方式，本次设计不把每个文档/小改动都绑到完整 CI；改动涉及的定向回归、兼容门和真实能力验证仍要完成。

## 13. 回退、旧协议与数据保留

### 13.1 两种回退

**功能回退**：停止新策略、连接或发送算法的准入；已领取回合按其保存的 `turn_policy/policy_revision/hard_deadline` 处理；原工作继续使用原授权快照与当前撤销闸；同键恢复只读原事实。

**二进制回退**：只允许读取当前 schema、识别 `host_revocation_epoch` 和幂等记录的兼容桥版本。数据库记录最低 reader/writer 能力，但不认识该 marker 的旧二进制不会自行拒绝；真正的准入门必须由部署启动器/更新脚本在打开数据库之前检查版本能力，并先停止旧 writer。兼容桥内部再读取 marker 做第二道检查。不能绕过启动器手工运行旧 writer，更不能忽略新列后恢复已撤销宿主。`off/shadow` 只能控制新路径选择，不能关闭撤销检查。

回退不能清队列、重置 fence/世代、覆盖 scope 摘要来制造兼容，也不能把完成结果改回待执行。数据库备份恢复属于灾难恢复：恢复点之后外部可能已提交，必须核对外部结果与后续账本；不能将旧快照当成可安全重发的依据。

### 13.2 必测的兼容数据集

至少包含：未确认输入、已 ack 的后台工作、活动回合、已过期/已释放回合、只剩 tombstone 的回执、工作操作 unknown、微信部分 accepted/部分 unknown、被撤销 Host 的多个房间成员、换路由未换成员、历史 lineage、已回填排序关系。

验收测试文件名称在实施时新增并明确标为 planned；不能因为文档写了 `tests/acceptance_multidot_old_binary.py` 就认为它已存在或已通过。按实际可运行版本矩阵记录每个组合结果。

### 13.3 旧协议退出

旧协议是历史兼容读写路径，不因 UI 已隐藏就可删除。统计从首个兼容桥版本开始连续采集，不必等全量生效 30 天才开始。

```sql
-- 当前已有旧 Dot 启动审计；它只是该类动作的证据，不代表全部旧入口使用量。
SELECT action, COUNT(*) AS calls, MAX(created) AS last_at
FROM collaboration_audit
WHERE action LIKE 'dot.consumer_%' AND created > :since
GROUP BY action;

-- 房间成员 consumer_audit 实际写主 audit 表，时间列是 at。
SELECT action, COUNT(*) AS calls, MAX(at) AS last_at
FROM audit
WHERE action LIKE 'room_member.consumer_%' AND at > :since
GROUP BY action;
```

`collaboration_audit` 的 schema 已核对；现有保留器至少保留 365 天审计 detail 才允许压缩，且不删除该表行。但这些审计不记录所有旧读写请求，也不是完整的接口调用计数；另以固定动作计数和连接 inventory 判定旧协议使用。

退出条件同时满足：所有可见活跃连接已迁移或明确停用；无旧回合正在执行；无只能靠旧路径恢复的工作/unknown 操作；旧消费者没有新领取；兼容桥能查询历史结果；回退窗口已明确结束；连续观测覆盖实际活跃客户端。观察 30 天可以作为运营参考，不单独构成删除许可。

先拒绝旧协议的新领取，保留当前回合收尾、原回执和历史查询；再经过已验证发布周期移除旧写入口；最后才考虑去除 lineage 兼容写入。不能先删除历史 Goal、work、operation、receipt 或 provenance，也不能替用户把仍有用途的旧房间自动归档。

| D25 | 房间交办→微信追问→房间补充→异步完成 | 同一 work，问答不改 intent；实际补充正确修订；各入口和原完成路由准确且每目标一次 |
| D26 | 旧进展在新回答之后迟到 | 原投递保留真实结果；工作卡不回退、不重复发最新状态；快照时间与引用可核对 |
| D27 | 原输入编辑生成新消息 ID，随后另发正常追问 | 编辑沿原 canonical input 链与依赖；正常追问建立新链；镜像、唤醒和恢复不能伪造新输入 |

定向回归按实际命令和结果登记，当前覆盖与缺口见[实施审查](COLLABORATION_IMPLEMENTATION_REVIEW_2026-11-10.md)。全量 CI 由项目既有手动入口触发。

### 14.2 真实宿主与微信

使用隔离房间、测试项目和已授权测试私聊，记录服务版本、宿主类型/版本、能力配置、实际原回执、脱敏时间和手机结果。不能通过手工伪造 callback/ticket 来替代真实联调。

| 场景 | 通过证据 |
| --- | --- |
| 房间与微信各发同类明确任务 | 两端都自动进入同一工作流程；同权限、无额外来源确认、原工作身份可追踪 |
| 回复 B 时撤销 A 权限 | B 回复正常；A 新数据/操作被拒绝；相关通知可处理；无全房间暂停 |
| 订阅自然到期并恢复 | 原回合按文档一租约规则收尾；恢复不新建工作；宿主续期是否支持有实际证据 |
| 两房间同宿主 | 暂停、移除、换绑其中一个成员，另一房间往返正常；全局撤销则各处新准入都停止 |
| 工作长时间后台运行 | 真实独立执行／持久交接后回合释放，按实际宿主能力接收和回答新消息；工作最终按原策略回传 |
| 同工作中解释、预览、改要求与继续追问 | 同一入口自然完成；不强制结项／切换模式；预览只含可见成果，新问题不会重建 Goal |
| 第一条回复未知、另一已知独立话题 | 独立话题继续；未知项状态不被更改；相关后续有精确等待说明 |
| 回复回包丢失 | 同键恢复后房间唯一回复，微信原投递唯一 |
| 平台限流和重新登录 | 限流原样退避；新登录不把旧 unknown 当可重发 |
| 手机部分收到 | 分项列表与手机实际内容核对；人工确认范围精确，不产生虚假平台证据 |

验收记录只需要支持结论的最小证据，不将回调 URL、凭据、手机号、正文历史写进公开仓库。服务版本、实际测试命令与结果分别记录；没测的平台明确保留未验证状态。

## 15. 完成定义与剩余外部事实

这套投递设计完成实施，必须同时满足：有界且授权正确的关联诊断；输入/回执/outbox 原子边界；精确分项状态；持久公平调度；可恢复且不猜关系的迁移；未知结果不重复执行；聊天释放不影响后台工作；Host 撤销在功能回退与允许的旧二进制中都持续有效；实际支持的宿主与微信场景有原始证据。

仍需在实施环境核实的外部事实：真实宿主是否暴露事件票据、如何续期与批处理、可承受的并发容量；平台是否提供可依赖的 `client_id` 去重/查询；真实存量空组键数量和大数据查询成本。它们各有明确采集方法与保守默认行为，不影响先实现不依赖这些假设的正确性改动。

真实证据与部署状态以[运维手册](COLLABORATION_DELIVERY_OPERATIONS_RUNBOOK.md)的记录为准。
