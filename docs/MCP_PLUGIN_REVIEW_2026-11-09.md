# CodePier MCP 插件实测评估与优化建议

> 日期：2026-11-09（Asia/Shanghai）
>
> 版本范围：v1.33.1 源码及本次 ChatGPT 连接实际暴露的工具。
>
> 文档来源：合并原稿中 Claude 的调用观察，以及 ChatGPT 的实际调用、字符测量和源码核对。原稿未复测的项目单独标明。
>
> 状态：F01–F10 已在项目源码中实施。第 2–5 节保留评审快照，第 11 节记录实现与回归。

## 1. 核心结论

统一为 `query / act`、批量读取、项目上下文复用、紧凑目录、原操作恢复和日志游标的方向正确，已经有可验证的减量效果。下一轮优化应优先提高首次调用成功率，并让精简展示成为常用操作的默认体验。

当前主要问题集中在：

1. 当前可见动作、静态说明、帮助示例和事件恢复入口没有完全同步。
2. 默认帮助暴露较多底层契约与完整输出 schema，却没有给出包含必填字段的有效示例。
3. 两个事件订阅工具重复携带很长的事件目录，宿主可见参数类型又退化为 `unknown`。
4. 已成功的短命令仍返回较重的内部调度元数据。
5. 已有的 `context_id`、compact 和游标能力不够容易发现；知识地图是否可用也没有在项目打开时直接呈现。

优化目标应是完成同一项任务所需的总调用轮数、有效信息量和成功率，而不只统计工具数量或单次回包长度。

**本报告的字符量、原稿粗略字节估算和真实计费 token 是三种不同口径。未取得宿主实际 usage，不给出实际费用或总 token 节省百分比。**

## 3. 测量结果

### 3.1 本轮精确字符测量

业务回包的口径是对单份 `structuredContent` 使用 `JSON.stringify` 后的字符串长度；本轮相关样本以基本多文种字符为主，按此口径报告字符量。工具目录则测量本轮 `ALL_TOOLS` 展开的说明和声明。这不是 HTTP 报文大小、完整原始 MCP 目录大小或 tokenizer 计量。两类数据只在各自口径内比较。

| 对象 | 本轮测量 | 解释 |
| --- | --- | --- |
| 首次打开 MCP | 5,030 字符 | 包含项目状态、上下文索引、运行环境和能力索引 |
| 同项目携带 context_id 重开 | 1,788 字符 | 减少 64.5%；context 为 null，context_unchanged 为 true |

## 4. 已有能力中值得保留的部分

### 4.1 统一入口与按需发现

`query / act` 将读取与变更、执行区分开，能减少选工具的负担。详细 schema 按需取得适合冷门能力。常用路径应继续完善参数发现，不宜为追求最少工具数量而让常见任务都依赖额外 help。

### 4.2 有效的返回预算与增量能力

- file 支持最多 8 项批读；结果携带 SHA、offset、end_line、next_offset 和截断状态。
- 超预算时明确返回 budget_limited/truncated，而不是将部分文件伪装成全文。
- context_id 能减少 open 和 baseline 的重复上下文，仍保留当前状态与重新核验。
- compact tree 保留分页、错误及路径边界，明显减少重复键和值。
- job 的 after_output_seq 允许只获取新增日志。
- 本轮短命令直接返回终态，不需要先拿启动回执再额外轮询；长任务等待行为仍以契约和实际原操作状态为准。

### 4.3 回执展示已与持久记录分离

`shared/unified_contracts.py` 的 `_slim / present_unified` 已删除内部重复 stdout、部分成功恢复字段和空 next_call。原始持久回执保持完整，只对展示副本做处理。这是继续优化成功回执的正确基础。

需要区分两件事：内部重复 stdout 已有去重；text 与 structuredContent 的协议镜像是否被宿主重复呈现，是另一个尚未验证的问题。

### 4.4 正确性保障

文件 SHA、幂等键、原 operation_id、日志游标、当前权限核验都具有明确用途。它们减少并发覆盖、重复执行和错误恢复成本，不应因压缩展示而失效。

工具声明中的协作 handle 也有减少重复消费凭据的潜力，但本轮没有实际验证这条协作流程。

### 4.5 知识地图与用量统计的谨慎边界

知识地图文档明确：结构生成不调用模型、不执行项目代码；摘要绑定源文件 SHA；只重验本次选中条目；过期摘要不外显；显式初始化后的维护与只读查询分离。这适合长期项目，但本次 MCP 地图缺失，尚未验证有索引时的检索效果。

用量文档区分工具文本、调用经验先验和上下文情景，并将真实宿主 actual_usage 保持为未知。此边界应继续保留，避免把估价面板当作真实账单。

## 5. 问题与建议

### F01 · 当前目录、说明与恢复入口不同步 · P1

**证据。** act 说明包含 project_create/gui，query 说明包含 devices，但本次对应动作未出现在可选枚举。`hub/unified_tools.py` 先用 visible_actions 按 scopes 筛选动作，再统一使用静态 DESCRIPTIONS；相关功能在路由中确实存在。项目 next 和部分事件说明仍出现 fs_read、skills_read、show_changes、task_query、collaboration_query 等旧名字。

**影响。** 模型需要额外判断入口或查询帮助，容易按不可见名字调用。事件消费提示与当前目录不一致还会影响原操作恢复。

**建议。** 从同一份路由表生成当前连接的动作枚举、简短说明、help 和 next_call；事件恢复请求也按当前目录投影。旧入口保留兼容，但当前目录的提示应使用当前入口。

**验收。** 对不同权限和目录档位，提示中的入口均可被该目录识别；说明与可见动作一致；恢复请求保留原 operation_id 和已读游标；不扩大执行权限。

### F02 · help 较重且示例不能直接使用 · P1

**证据。** knowledge 帮助 4,771 字符中，输出 schema 占 3,116 字符；部分成功字段在根 properties 与 anyOf 分支中重复。普通 help 仍返回底层 tool、operation/options，再追加 unified_call。示例固定为 action/view/args:{}，没有补齐项目、query 或 ids 等必要字段。

**补充实测。** 文档更新时按此前 open 帮助传入 `query(action=project, args={capture_baseline:true})`，服务端明确拒绝并提示使用 `act(action=baseline)`。只读边界正确，但统一帮助继续暴露底层有副作用参数会导致绕路。baseline 帮助中的底层 requires_idempotency_key:false 也不应取代 act 层的实际幂等要求。

**建议。** 默认帮助返回当前 unified 契约、默认 view、必填字段、常用参数和一个有效示例；完整 input/output schema 放到显式详细入口。将 options 字段如何映射到 args 直接说清楚，区分统一等待参数与底层执行参数。

**验收。** 常用动作示例满足当前 unified 输入校验；不会把底层 operation/options 原样误传；只读帮助不建议触发写入的参数；原机器验证 schema 保持完整。

### F03 · 事件说明重复与参数类型退化 · P1

**证据。** 两个订阅工具占可见工具文本约 64.8%，相同事件说明块为 3,921 字符。宿主可见 triggers 类型为 unknown 数组，而 `hub/collaboration/event_contracts.py` 中已有 RoomInboxFilters、OperationFilters、DelegationFilters 等明确模型。

**建议。** 常驻说明保留用途、关键权限语义、更新时 triggers 全量替换等约束；具体事件过滤参数和消费步骤按事件名取得。追踪事件定义到宿主工具生成过程，定位 unknown 来源，再修复可控制的环节。

**验收。** 创建和更新工具不再重复展开整份长目录；事件参数有可用的类型或精确按需帮助；恢复请求使用当前目录；必要授权和原操作恢复语义仍可获得。

**边界。** 本轮未创建订阅，不能据此认定真实事件投递失败；也不能直接断言服务端未定义 schema。

### F04 · 成功回执元数据偏重 · P2

**证据。** 23 字符正文对应 1,312 字符业务回执。终态成功仍携带多个时间戳、next_attempt、deadline、空错误字段及重复操作引用。原稿另报告扁平对象与 operations 数组两种 exec 展示形态，该项需复测。

**建议。** 延续已有 lean 投影，按状态组织默认展示：

| 状态 | 默认返回重点 |
| --- | --- |
| 成功 | operation_id、state、exit_code、output、output_seq、截断状态、必要执行环境引用；耗时按需要保留 |
| 排队/运行 | 当前阶段、等待原因、建议等待时间、原操作恢复请求 |
| 失败/不确定 | 准确错误类别、关键诊断、原操作状态、合法后续请求 |
| 显式诊断 | 完整回执与轨迹 |

对已完成操作可省略无助于下一步决策的内部调度字段。执行环境可用稳定引用关联，变化时再提供细节。统一同一类 exec 的展示形态或明确其判别字段。

**验收。** 输出游标和截断信息可用；完整诊断可按原编号取回；存储回执、授权核验和恢复行为不变；失败不被精简成看似成功。

### F05 · 上下文复用与紧凑输出不够容易发现 · P2

**证据。** open 携带 context_id 减少 64.5%；compact tree 减少 59.1%；本次 baseline 携带 context_id 同样返回 context:null。原稿“baseline 重复完整 open”只适用于未传相应去重条件的样本。

**建议。** 在常用说明和有效示例中明确重开传 args.context_id、目录使用 args.format=compact、job 传 after_output_seq。面向模型的目录展示可优先采用紧凑形式。capability_index 避免每次重复整套 help 地址，搜索入口默认指向 sync，或直接说明何时需要 start。

若由客户端自动缓存 context_id，应按主体、授权、项目、工作区和上下文版本隔离；失效或变化时重新返回必要上下文。不能只因同一个 MCP 会话曾经读过，就假定所有并行消费者都已经掌握内容。

**验收。** 重复读取确实省略未变化内容；变更后可重新获得上下文；未确认读过的消费者不会收到空上下文；分页和恢复字段保持可用。

### F06 · 知识地图可用性未直接呈现 · P2

**证据。** 对 MCP 的三个代表性知识查询均返回 state:missing、revision:new、空 entries、total_matches:0、refresh_required:false。每次单份业务 JSON 为 352 字符；缺失状态回包较克制，但打开项目没有直接说明索引缺失。

**建议。** 项目打开时给出紧凑的知识状态；可用时附版本、覆盖和维护状态；缺失时明确尚未初始化及合法帮助入口。missing 时不要用泛化的新鲜度文案造成“已有文件经过 SHA 核验”的印象。读取仍不隐式构建、恢复或启动维护。

**验收。** 能区分尚未初始化、已可用和选中条目过期；模型可直接判断是否使用知识查询；不把无匹配和无索引混在一起；不声明全仓库已验证。

### F07 · 错误语义与合法后续请求不够准确 · P1/P2

**证据。** 本轮 rg 缺失，退出码 127、输出为 command not found，顶层却标 INVALID_ARGUMENT。部分执行前参数拒绝返回 recovery.category=unconfirmed、inspect_without_replay，没有清楚区分尚未执行与结果未知。

**建议。** 区分参数拒绝、命令不存在、执行失败、传输中断和结果不确定。执行前拒绝可给出允许参数、默认 view 或经过校验的修正请求；已执行或结果未知必须继续查询原回执。环境缺少搜索命令时，提示当前可用的内置搜索入口。

**验收。** 不会为 command not found 反复修改正确的工具参数；不会把确定未执行误报为状态未知；不会把未知结果误报为可重新执行；后续请求在当前权限内有效。

### F08 · 搜索模式与 glob 匹配规则容易混用 · P2

**证据。** 本轮调用者把 start 的 max_results 参数带入默认 sync，被正确拒绝；这是调用失误，不是搜索实现失败。file_glob=mcp_usage.py 时扫描数为 0，改成 *mcp_usage.py 后扫描到 1 个文件；改用实际存在的 token_usage 关键字得到 3 条匹配。

**建议。** 简短帮助中列出 sync/start 的默认值、参数差异和适用场景；明确 file_glob 匹配文件名还是项目相对路径，以及它与 path 的关系。零扫描可提示过滤范围没有匹配文件。

**验收。** 常见同步搜索一次返回；参数示例不混用两种 view；无匹配、无扫描、达到扫描预算分别可辨认。

### F09 · 项目列表与 baseline 覆盖的展示 · P2

**证据。** 原稿的 28 项列表存在重复 root、空 description、相同时间和来源字段。本次 baseline 捕获 565 文件、8,369,635 字节，complete:false、truncated:true，max_bytes 为 8,388,608。基线有界并诚实报告不完整，这是优点；但整体统计不足以证明目标文件已覆盖。

**建议。** 项目列表紧凑展示别名、在线状态、模式及决策所需字段；共享元数据上移。baseline 默认返回引用、覆盖摘要和当前 Git 状态；需要时提供按路径检查覆盖或按路径采集能力。已有 context_id 去重应直接利用。

**验收。** 不以不完整基线宣称全仓库覆盖；能确定本次目标文件是否在基线中；分页和授权过滤不变。列表节省幅度重新测量后报告。

### F10 · 用量统计应覆盖任务效率与工具目录 · 持续

**证据。** `docs/mcp-token-usage.md` 明确工具文本统计不覆盖工具目录、系统提示、完整聊天和宿主实际用量。创建/更新事件工具是本次主要说明开销之一，仅用项目调用面板无法完整评估这一部分。

**建议。** 分开记录：目录展开体积、重复文本量、首次有效调用前 help 次数、参数错误率、任务总调用轮数、同一 operation 的轮询次数、重复日志量、正文/元数据比例。字符与字节可作为观测量，token 估计继续标注方法和不确定性。

**验收。** content 与镜像 structuredContent 不重复累计；调用先验、上下文情景和工具文本不能相加成账单；没有可信宿主 usage 时 actual_usage 仍未知；同一任务前后比较使用一致口径。

## 6. 对原稿建议的修订

| 原稿建议或结论 | 本版修订 |
| --- | --- |
| 只有三个工具 | 核心原生目录为三个；本次宿主还暴露两个事件工具，需要一起评估 |
| 自动记住 context_id | 支持自动复用，但需按主体、授权、项目、工作区和版本隔离，并继续核验；不能只依赖单个会话缓存键 |
| baseline 总会重复完整上下文 | 本次已验证传 context_id 可省略；改进重点是可发现性、默认策略和覆盖说明 |
