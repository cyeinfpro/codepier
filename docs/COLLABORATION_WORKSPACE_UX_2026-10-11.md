# 协作中心：围绕持续对话的工作区重构

日期：2026-10-11。实施基线：`9294434`。实际测试与集成状态见同目录验收记录。

## 1. 目标与现状诊断

用户不是来管理一组连接和数据库记录，而是来与助手一起把事情推进。主路径应当是：进入房间 → 接入助手 → 提出需求 → 看反馈和进展 → 回到同一话题继续。普通对话与执行不能被两个面板模式切断；是否执行及执行范围仍受原有授权约束。

本次检查到的断点：

| 原实现 | 对用户的影响 | 新处理 |
| --- | --- | --- |
| 专注对话隐藏全部工作导航；管理视图再次切换外壳 | 查进展前先理解产品模式，返回时重新定位 | 单一房间外壳；对话、进展、连接、监控始终可见 |
| 切标签调用整个页面渲染，替换主内容 | 输入框、详情、表单与阅读位置成为生命周期恢复问题 | 对话 DOM 常驻；详情面板切换采用本地显示与惰性创建 |
| 固定右栏重复任务和项目摘要 | 日常聊天面积被低频管理信息占用 | 取消固定重复右栏；需要时才展开上下文面板 |
| 空房间只有一般说明 | 不清楚第一步该做什么，加入过程缺少回路 | 无助手、待加入、可对话三种实际状态，各提供对应下一步 |
| 管理状态与原消息分离 | 看到结果后还要重新寻找来源 | 从真实消息回执生成进展卡，直接回到原消息 |
| 房间切换依赖隐藏菜单或整页重载 | 手机端发现困难，草稿是否保留不确定 | 明确房间按钮、可搜索列表、草稿标记和可返回路径 |

## 2. 参考案例及取舍

参考的是交互原则，不复制第三方品牌、素材或完整界面：

- **Linear UI Refresh（2026-03-12）**：统一页面标题、导航与视图控制位置。采用稳定外壳和一致导航，不把聊天做成密集的工单表。官方来源：https://linear.app/changelog/2026-03-12-ui-refresh
- **Linear 设计复盘**：减少视觉噪声、明确层级，使内容而不是大量容器成为主体。采用较平静的房间栏、主题令牌和按需详情。官方来源：https://linear.app/now/behind-the-latest-design-refresh ；https://linear.app/now/how-we-redesigned-the-linear-ui
- **Slack 侧栏与话题**：以会话位置组织协作，将相关回复留在其上下文。采用固定房间入口与来源消息返回；不把“消息已送达”解释为模型已处理。官方来源：https://slack.com/help/articles/212596808-Adjust-your-sidebar-preferences ；https://slack.com/help/articles/115000769927-Use-threads-to-organize-discussions-

这里的“进展、连接、监控”是同一房间的观察角度，不是新的聊天/任务模式。它们不改变消息的授权、投递方式或实际执行者。

## 3. 用户路径

### 首次使用

无助手时，对话区直接展示“添加第一个 dot”。点击后就地打开连接面板，沿用原始接入表单及访问范围说明。提交之后展示真实加入码和加入指令；目标 dot 的宿主确认仍在目标端完成，不自动伪造订阅或凭据。

回到房间时，尚未登记的 dot 对应“继续连接”，而不是假装已经在线。已登记后可以直接输入；示例提问只填入空草稿，不发送、不覆盖用户已写内容。连接是否真的能收到通知与模型是否已读取仍由真实回执区分。

### 连续协作

主对话、收件对象、话题锚点和输入框保持同一实例。打开进展不会结束话题，也不会提交草稿。实时回复继续通过原有 relay 到达，查看进展后可以回到原消息继续讨论。

进展投影仅使用**当前项目、当前环境、已加载消息**的 `relay_receipts`。分类为需关注、处理中、待反馈和已反馈；未知服务端状态明确标成“状态待核对”。多收件人的同一条消息采用保守优先级：需关注优先于处理中、等待与已反馈。计数是消息条数，不冒充项目全部任务统计。

“已回复”“已确认处理”“已完成”保留不同语义。已有目标、工作项和只读任务仍可查看，但回执中的已回复并不表示代码执行或验收完成。旧的批准、领取和结果证据流程不变。

### 核对连接与处理异常

连接面板先列已有助手，再提供渐进展开的添加表单。日常查看与维护动作分层；通知测试、移除连接、刷新加入码等维护内容按需打开。等待连接的进展卡提供连接详情入口。断网草稿、发送队列、丢失响应核对和话题内顺序仍由原有 relay 实现负责，不在呈现层重复实现发送机制。

### 手机与键盘

窄屏以同一详情区域暂时覆盖对话的视觉空间，但原输入框仍保留。隐藏的对话设为 `inert`，不会进入键盘焦点，也不会因为后台到达消息而误标已读。明确的返回按钮和 Escape 退出详情，恢复输入焦点及选区。房间列表可搜索；手机抽屉将焦点限制在可见控制内，关闭后返回触发按钮。

320、390、768、1024、1440 像素宽度纳入自动化检查。移动输入保持 16px；发送按钮与底部区域适配可视视口；沿用主题颜色变量与减少动画偏好。

## 4. 实现边界

新增 `web/collaboration-workspace.js` 与 `web/collaboration-workspace.css`，前者只负责呈现投影和本地导航，后者限定在 `.cc-workspace` 下。原有模块仍分别承担消息、助手接入、目标批准、实时回执和审计能力。

关键不变量：

1. 视图切换不创建凭据、不扩大权限、不提交消息、不自动创建任务；示例输入也不提交。
2. relay 的是否启用不再依赖用户正在看哪一个详情面板；发送队列与回执同步继续工作。
3. 导航不调用整页 `renderPage`，保留输入框和对话节点。详情表单惰性建立后保留，防止在“连接 → 监控 → 连接”时丢失输入。
4. 本地导航会触发有界、合并的只读状态更新。目录响应受 generation、session、space、project、environment、conversation 检查，不把旧房间响应写入新房间。
5. 权限或可见范围改变时，旧消息、草稿与新增详情缓存一起清除。既有后台授权检查仍是最终边界，不由隐藏按钮代替。
6. 进展按钮的焦点不阻塞回执更新。卡片内容与筛选数量分别刷新；只读任务记录变化时保留展开意图。活动表单不因轮询而销毁。
7. 草稿仅在当前会话内存中，不把正文写进 localStorage 或 sessionStorage。
8. `index.source.html` 显式加载新模块；生成的 index 与资源清单由既有构建脚本更新。

## 5. 验证原则

新增浏览器用例同时覆盖真实 Chromium 与 WebKit：首次接入、草稿建议不提交、不覆盖、详情切换维持同一个输入框、选区和表单、查看进展期间真实协议回复到达、回到原消息、房间搜索、焦点恢复、窄屏无横向溢出、消息投影不跨项目或环境。

沿用并回归既有测试，重点保留断网队列、丢失 ACK 不重复提交、富文本安全、中文输入法、原始领取/批准边界、过期响应与访问范围撤销等断言。不以修改旧安全断言获得通过。只更新“必须隐藏所有导航/必须切管理模式”这类被新设计明确替代的 UI 断言。

测试使用隔离 Hub、临时项目和协议消费者。通过这些测试证明的是界面和协议链路，不证明真实原生 dot 的模型行为、主动运行时长或生产订阅可用性。

## 6. 后续衡量

本次不添加真实用户遥测。上线后的可评估指标应是首次成功接入所需步骤、从消息到发现异常/返回来源的操作数、切换详情后的草稿恢复失败率和窄屏误操作，而不是单纯增加卡片或导航数量。生产发布、真实宿主接入验收与用户观察需要单独记录，不能由本地浏览器截图替代。
