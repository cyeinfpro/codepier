## 第一轮已修复

### 1. 微信通道关闭后，已准备的工作者仍可能发送

位置：`hub/collaboration/weixin_delivery.py`，`send_once()`。

原流程先检查通道开关，再在线程中执行 `mark_sending()`，返回事件循环后立即发送。若在准备完成与发送之间关闭通道，数据库里的租约已被撤销，旧工作者仍会使用已冻结的消息调用发送接口。

本轮增加发送前的 `check_send()`，复核当前通道、租约所有者、租约世代、到期时间、分项状态和当前绑定范围。关闭后立即重开也不能恢复旧工作者的权限。失效分项保留原有未知/取消回执，不自动重发。

复现：既有 `test_disable_after_prepare_prevents_external_send` 在修复前失败。扩展为“关闭”和“关闭后立即重开”两种情况，修复前两种都进入假 Provider 的发送函数；修复后均被阻止。测试只使用合成账号、临时数据库与假 Provider，没有发送真实消息。

边界：检查不能撤回已经交给外部服务的请求；这类结果继续保留未知状态，不承诺网络发送与管理员开关之间具备跨系统原子性。

### 2. 镜像通道关闭后重开，旧发送租约仍被使用

位置：`hub/collaboration/channel_router.py`，`send_once()`。

这条独立镜像路径原来在准备后只复核开关。若关闭后迅速重开，开关再次为 true，但旧分项租约已失效，旧工作者仍可能发送。

已将最后一步检查改为同时验证通道开关、发送状态、租约世代、有效期、原消息及绑定/凭据范围。该路径服务 Telegram 和微信镜像。

新增 Telegram 合成回归：在 `begin_send()` 后切换开关。原实现“只关闭”通过，“关闭后重开”失败；修复后两种情况均不调用 Provider，保留未知回执。

### 3. 已完成回填的聊天历史在每次启动时被重新读取

位置：`hub/collaboration/schema.py`，`migrate_chatroom()`。

原逻辑逐房间读取全部消息正文，再逐条查询序号和线程根；即使历史已经回填完成，也照常执行。

本轮增加局部索引 `collaboration_chatroom_backfill_pending`，只记录序号为 0 或线程根为空的消息。正常重启只处理仍需回填的房间；首次增加历史已读边界时仍处理全部旧房间。未用永久完成标志掩盖中断留下的记录。

复现与验证：两个房间各插入 128 条合成消息，测试“全部完成”和“仅一个房间未完成”。修复前两项均失败，两个房间都会被加载；修复后读取历史的房间数分别为 0、1。还检查了序号/线程根、完整房间数据、读游标、历史已读边界和实际查询计划。

边界：首次建立局部索引仍需读取历史表一次；本轮没有在生产数据库执行迁移或容量基准。

### 4. 房间操作路由重复定义两个键

位置：`hub/collaboration/rooms.py`，`Rooms.invoke()`。

`room_turn_policy`、`room_turn_policy_update` 各重复一次。目前处理方法相同，未证实造成错误分发，但会被后一个条目静默覆盖。

已删除重复条目，并在 `ruff.toml` 增加 `F601`、`F602` 门禁，防止重复字典键再次混入。没有按“未使用”告警批量删除兼容入口或测试 fixture 导入。

### 5. 初始化失败回归的替身函数签名过期

位置：`tests/test_audit_api.py`，`test_initialization_failure_releases_instance_lock()`。

生产代码调用 Runtime 时已传入关键字 `collaboration_config`，但测试替身只接收 `store`。测试因此先抛 TypeError，没有执行预期的初始化失败注入。

已让替身匹配当前显式参数，保留原 ValueError 注入与后续真实应用启动验证。没有通过扩大异常捕获或删除断言让测试变绿。

### 6. 清洁模式测试临时目录说明与过期数量

位置：`docs/DEVELOPMENT.md`。

默认清洁环境的临时目录位于 Agent 私有状态目录内。冒烟测试创建的合成项目因此触发 `PROTECTED_ROOT`，21 项均在 fixture 初始化失败。将本次命令的 `TMPDIR` 指向系统临时目录后，21 项全部通过。

已补充为测试进程单独选择临时目录的说明，保留产品路径保护，不修改 Agent 全局环境或授权范围。同时删除文档中过期的“20 个”冒烟用例数量，避免数量变更后再次失真。

## 第二轮继续修复与复核

### 7. conversation 迁移只处理待迁移分区和待回填会话

位置：`hub/collaboration/conversations.py`。

原实现逐房间读取迁移标记，并对全部会话分别查询最大消息序号。已改为在 SQL 中排除完成迁移的分区，并增加只包含 `conversation_sequence=0` 消息的局部索引；只为仍需回填、且确实存在的会话查询最大序号。

在 64 个旧分区、65 个会话的合成数据中，原实现无论是否有待回填记录，都执行 65 次最大序号查询；修复后分别为 0 次和 1 次。逐房间的 Python 标记查询也已消除。正常启动仍有一次分区反连接检查，不能把这描述为整个迁移完全没有历史成本；首次建立索引仍需扫描历史表。

新增测试检查查询计划、保留旧消息顺序/读游标、失败事务回滚后可继续完成，以及未知会话不被隐式创建。另用既有归档、移出项目和旧版迁移回归验证不会恢复已移除分区或执行权限。相关联合回归 107 项通过。

### 8. 资源锁前路径解析不再阻塞事件循环

位置：`agent/runner.py`，`Agent.project_slot()`。

原实现直接在事件循环中执行 `Path.resolve()` 和生成规范化资源键，慢文件系统响应会阻塞同一事件循环。已将这两步组成同步准备阶段，交由现有 `disk_call()` 执行；实际排队、互斥和诊断状态仍在事件循环中更新。

新增可控慢解析测试在修复前的正常/取消两种情况均失败；修复后检查心跳回调可推进、取消等待已开始的准备阶段收尾、未提前留下活动资源，以及不同路径别名仍竞争同一资源锁。7 项新增迁移/路径回归全部通过；工作目录及编码流程 36 项通过，资源语义、联合准入、取消和读取回归 51 项通过。

边界：取消仍可能等待正在执行的文件系统准备阶段结束；这次修复保证该阶段不会占住事件循环，不承诺能中断内核或 NAS 调用。其他异步入口的同步文件操作仍列在下方候选中。

### 9. 私有记录列表先按范围查询，并按需读取

位置：`agent/integration_state.py`，`Records.list()`。

原列表先 `fetchall()` 同类的全部记录，再在 Python 中核对身份和截取数量。请求 1 条记录的合成回归中，实际先读入 304 条。无关记录的绑定 JSON 损坏时，还会导致整个列表抛错。

已增加基于项目、根目录、工作区、设备及调用方的索引与查询条件。管理员仍沿用原有“同映射可查看其他调用方记录”的语义，最终完整绑定比较继续生效；未知额外字段不能通过。旧 JSON 键顺序保持兼容。

改为持有原 journal 锁迭代结果，取得足够的授权记录后停止，并在解锁前显式关闭游标。无法验证身份的损坏绑定保留原数据，不据此公开正文，也不再阻塞其他记录；没有删除历史数据或扩大授权。

4 项新回归在修复前全部失败，修复后验证了管理员/普通调用方、旧绑定键顺序、额外字段、损坏身份、索引使用和有界读取。合成场景读取的结果行由 304 条降至最多 2 条；这是实际物化行数，不代表 SQLite 完全不需要排序当前范围内的历史。记录、文件资产、浏览器关闭恢复等 102 项联合回归通过。
