# dot：一个对话入口，不让用户切换模式

> 最新的轻量对话界面、可靠发送、增量回复及恢复行为见 [传话与反馈体验](DOT_RELAY_EXPERIENCE.md)。

## 本轮产品定义

面板只负责收发消息和呈现进展。dot 根据可信房主消息及同一话题的上下文，决定直接回答、读取项目资料、追问必要信息，还是执行已授权的工作。不是在面板中增加一个“自动模式”下拉框，也不需要用户先把消息标成任务。

同一段对话可以是：讨论方案 → 用户说“按刚才的方案做” → dot 先解释步骤 → 实际执行 → 回报结果 → 继续讨论。问句并不必然是纯聊天；需要读取文件或检查日志时可以调用工具。闲聊也不被强制包装成一份工作项。

## 面板变化

双向 dot 的输入区不显示聊天/任务发送方式，不要求填写委托、验收或任务表单。普通发给 dot 的消息、dot 的回复和其工作进度，不显示要求用户手工“转为任务”的按钮。人工目标创建仍保留在其他用途的管理入口中，旧 CPJ / task-only 流程不迁移、不变更已授权用途。

添加 dot 默认只需填写名称，查看页面已展示的范围说明并点击添加。点击本身就是该范围的明确确认，不再额外勾一次同意框。服务器仍要求 authenticated panel owner 和 `confirm_tasks=true`；这是已说明含义的用户添加操作，不是把权限检查删除。

可选的只读限制与执行位置放到折叠的“项目访问与执行位置”设置。默认范围由服务端从当前房主权限及当前项目 mode / allow_tasks 计算，读取该默认值不创建或修改任何授权。表单保留呈现时的范围，不能因为后台刷新而静默扩大本次确认内容。创建和加入仍会重新核对当前授权；这里没有新增凭据或扩大既有项目访问。

## 实际修复：先回话后执行

之前成功发送普通回复会结束原消息。dot 先说一句“收到，我先看看”，随后再准备执行，就可能遇到 `DOT_MESSAGE_HANDLED`，要求用户重新发一条请求。这会把自然对话切成两套流程。

现在 `dot_message` 可使用 `complete=false` 发送阶段性回复。此回复会出现在原话题，但只把原收件记录为 read，不结束待办；dot 可以继续读上下文、交流，再从同一条可信房主消息准备原范围内的工作。

收件结果提供 `interim_reply_arguments`，包含 `complete=false` 和稳定的阶段回复幂等键。最终普通答复使用原 `reply_arguments`，默认 `complete=true`。同一条回复的重试使用同一个键；不同阶段的新消息使用不同的稳定键。普通与阶段性回复均不构成任务成功证据。

`complete` 只是插件回复的后台处理标记，面板不显示这个字段，更不让用户切换它。已经真正结束的旧讨论仍不能被迟到调用重新解释为新的执行授权；后续的人类消息可自然继续同一话题。

## 自动判断的边界

消费者说明明确要求先读原消息和话题上下文，不用问号或关键词硬分聊天和任务，不为“切换模式”重复询问。关键要求不明、目标不清或原授权不足时才提出必要问题；需要新授权或宿主原生确认时仍尊重该确认。

后台保留原有消息幂等、工作租约、执行目标、项目权限和真实回执检查。任务记录是恢复、追踪实际操作用的实现细节，不是用户发送消息前必须先填的表单。本轮不宣称取消了账户权限、连接有效期或所有运行预算。

## 验证

新增 `tests/test_collaboration_dot_seamless.py` 检验阶段回复后沿用原消息建立唯一工作、普通阶段回复到最终答复、迟到重试不能重开收件、相同回帖键不能改写完成含义，以及只读/可写/可执行项目默认范围。

新增 `tests/test_collaboration_dot_seamless_flow.py` 使用真实隔离 Hub、MCP、Agent 和浏览器：从只填写名称的一次添加开始，先纯讨论，再按原话题回复“按刚才步骤做”，dot 发阶段性回复后从同一消息准备工作，实际创建文件、读取并运行命令，最后继续纯讨论。断言面板三条消息都没有 delegation、dispatch_mode 或 automatic_policy_version，整个过程只有一份工作和三个实际操作。

这组测试的 dot 判断由明确标注的测试消费者发起，不是实际模型。代码侧验证不能替代真实目标 dot 对自然语言的自主判断及宿主收发验收；部署与真实宿主订阅确认仍需单独完成。

参考官方 MCP Events 的宿主订阅与事件处理约定：<https://developers.openai.com/plugins/build/mcp-events>。
