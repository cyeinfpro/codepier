# 聊天式协作室

CodePier 1.19 将房间消息作为协作主线。用户可以先讨论、回复、选择提醒对象，再把明确的请求转为有范围和验收要求的目标，交由自己的多个助手拆解、分工与复核。项目、空间和当前授权继续决定可见内容；讨论记录不会自动同步私人聊天。

## 开始讨论

在协作中心创建独立房间，可选择一个或多个已有授权项目。已有单项目房间保留稳定身份，并可在使用中添加项目；添加不重建房间、不移动历史，也不创建新的部署环境。任务、监控与通知在底层继续使用逐项目和环境的分区，房间只是明确关联这些项目。

普通消息仅保存讨论。有效委托规则下，房主在 @ 菜单选择「交给dot处理」后发送，消息会同时建立受该规则约束的目标与工作项；选择「仅讨论提醒」或只输入纯文本 @ 都不会派发任务。回复引用同一房间的原消息，委托结果回到原话题。页面有新消息时局部更新，不应覆盖正在输入的草稿或把向上阅读的用户拉回底部。

桌面提供房间导航、消息流与按需详情；手机把详情和接入流程放到独立面板，输入框保持可触达。中文输入法选字时不会误发送。普通文字里的 @ 不代表有效接收对象，需在选择器中明确选定连接。

## 单项目与多项目房间

房间有自己的名称和稳定编号，不以项目名称充当身份。顶部显示当前关联项目；添加项目需明确选择当前有权访问的项目，并在版本冲突时重新确认。重复添加不会产生重复绑定。取消操作保留当前房间、阅读位置和未发草稿。

每条消息显示所属项目。多项目房间的普通发言也要明确项目，回复保持原消息的项目；跨项目回复不能悄悄改归属，应切换到目标项目后另发消息。任务转换明确标出原消息所属的目标项目，讨论中的项目名称不产生跨项目执行授权。

添加新项目只增加绑定，不自动导入该项目其他房间的历史、既有任务或私有资料。原来的消息和结果保留原项目归属。成员每次读取消息、搜索、话题、增量和结果时都按当前项目授权过滤；撤权后不能通过旧链接、缓存、阅读游标或引用预览重新取得内容。

发言许可与聊天提醒同时绑定会话和项目范围。原来获准的项目不会因为房间添加项目而扩大为新项目；新项目需要独立允许发言和完成原生通知订阅。旧通知保持原有范围和身份，不整组替换为更宽的订阅。

## 接入助手的三个独立条件

连接用途、房间发言和任务资格分别管理。

1. **接收通知**：房主创建 CPJ 加入位置，在目标 dot 或 Work Cloud 聊天使用现有授权加入，再完成宿主支持的原生事件订阅。加入码只定位位置，不产生凭据或扩大授权。
2. **在房间发言**：房主明确允许某个连接在当前会话的选定项目中发言，并设定有效期。该许可只覆盖房间消息，不能替代执行任务的用途绑定。可随时撤回；过期或原授权撤销后拒绝发言。
3. **承担任务**：旧监控任务仍要求匹配的只读用途绑定；新目标工作项要求房主明确批准目标、参与连接和能力上限，再按实际工作项检查当前连接能力。只有通知位置或发言许可不能取得执行权。

多个聊天可能使用同一个 MCP grant。此时 CodePier 能确认连接来源，不能据此证明来自哪个原生聊天。消息显示连接来源或用途，不能把用户自填名称、CPJ、slot_id 或人工收件确认当作密码学身份验证。

## CPJ 加入与恢复

从助手与连接入口创建位置，复制完整加入指令到目标聊天。宿主应读取实际可订阅事件源，使用返回的连接器标识；不能根据旧插件名称或缓存猜测。

Work 应使用支持原生事件的 Cloud 宿主。CodePier 工具列表没有 events/subscribe 不等于宿主不支持；订阅由宿主原生能力处理，回调和签名材料也由宿主提供，不能人工编造。

登记后尚缺订阅时可复制继续订阅指令，无需反复兑换已使用或过期的加入码。继续步骤只处理仍缺少的事件，尊重房间、原授权、位置有效期和用户暂停。部分成功保留已有订阅身份，不整组重建。

测试必须分清以下阶段：

- 服务端记录测试请求；
- 回调平台接受投递；
- 用户在指定聊天确认收到相应测试标识。

房主确认记录为人工确认。平台接受不代表用户已读、模型在线、模型一定回应或拥有任务权限。

## 普通消息的 @ 提醒

聊天提醒使用独立事件 codepier.collaboration.message_mentioned.v1。原有任务、结果、异常和链路状态订阅不会自动新增此事件，也不会在升级时改变原来的订阅许可。

房主需要对选定会话、项目与位置独立订阅聊天提醒。事件只传递必要标识，消费者读取正文时重新核验项目与房间授权。必须精确匹配会话、项目与接收 slot，不能在没有对应订阅时退化为向整个项目广播。

没有订阅时仍可保存消息，界面明确显示未提醒。后来完成订阅不会自动补发历史消息。原作者可对仍缺提醒的原消息显式补提醒；请求绑定消息版本与原来已提及的位置，只新增提醒记录，不复制正文或建立任务。已排队、投递中或平台已接受的提醒不会因重复点击再发一遍。通知状态按当前回执刷新；平台已接受不代表助手已读或完成处理。助手通过 MCP 发出的回复不会自动再次通知其他助手，避免互相唤醒的循环。

助手回复通过 collaboration_message_create 保存。作者由已认证连接确定，客户端不能声明自己是房主或另一聊天。此工具只发房间消息，不产生执行授权；事件和引用资料仍是数据，不是新的用户指令。

## 在既有范围内直接委托

房主可为一个明确的房间、项目、环境与加入位置设置委托规则，选择当前连接已有的能力、有效期、每次目标期限、委托次数和工作预算。规则绑定版本与执行位置。首次设置和修改都需由房主确认；MCP 连接不能代为建立或批准自己的规则。规则没有新增凭据，也不能扩大当前项目或连接授权。默认规则有效期为七天、每次任务期限为一小时、最多一百次委托；加入位置更早到期时，以该位置的有效期为限。

设置完成后，@ 菜单的主动作「交给dot处理」一次点选即可设好明确委托，无需每次另找发送下拉；次动作「仅讨论提醒」保留不执行的讨论方式。发送时给出验收要求，服务端在同一事务保存原消息、委托、已批准目标和初始工作项；消息保存成功不等于原生订阅已接通或通知已投递。重复提交原请求复用已有记录。规则版本变化、到期、暂停、次数用尽、位置失效或能力撤销时，整个请求失败，不留下看似成功的半条委托。普通消息和旧的监控指令仍保持原有语义。

执行位置为项目原 Agent，或规则中明确选定并保存快照的 VPS。VPS 委托仅经受管执行步骤使用已授权的精确目标，不接受临时换目标。Shell 使用执行账号的权限，并非项目目录级沙箱；包含执行能力的规则需明确确认这一边界。安装、凭据、安全设置、发布和破坏性操作仍须满足执行宿主要求及用户实际授权，规则不能替代这些要求。

### 一次接入，同一规则下持续收件

委托使用独立事件 codepier.collaboration.delegation_available.v1。过滤器精确绑定 project_id、environment_id、conversation_id、slot_id、policy_id 和 policy_version。用户在目标 dot / Work Cloud 明确订阅这一规则并说明收到委托后的处理方式；服务端不会替用户创建原生自动化或改变现有订阅。

同一规则版本下的新目标复用这一条订阅，不再要求每个目标各建一次订阅。改规则后需要订阅新版本，旧规则的通知范围不会自动扩大。暂停、到期和撤权会阻止后续投递、领取与受管执行；已经发出的外部操作可能仍在运行，应保留真实回执。

CPJ 原有两类或四类订阅继续只表示监控通知接入。聊天提醒、委托提醒分别有自己的精确订阅请求与状态，不能把旧位置的“接通”视为这些新用途已就绪。完成发言许可也不代表委托订阅已建立。

### 宿主如何处理委托

事件只携带委托、消息、规则、目标、工作项及其版本等标识。测试事件只核对接收，不创建或领取工作。非测试事件到达后，消费者先用 collaboration_delegation_read 重新读取当前源消息、规则、目标、待办与操作回执。返回的 trusted_author 明确标记已认证的 panel_owner 和 user_id；应与当前连接的账号核对。消息中的自称、连接标签和 slot 名称不能替代作者证据。

只有当前规则、目标和连接授权都有效，且源消息属于该认证用户时，才按明确委托领取对应工作项。每次受管步骤使用 collaboration_work_execute，并保留原幂等键、attempt、fencing_token 和真实操作编号。不得改用通用 exec 绕过目标暂停、预算或执行位置限制。收到重复事件先查工作状态；无法确定的操作先读取原持久回执。异常恢复仅允许房主选择「重试尚未开始的步骤」，且该步骤所有历史尝试均没有操作准入记录时才可恢复；已有任何操作记录时必须先核对原回执，不能自动重试。

完成后提交 collaboration_work_result。受管结果会写回源消息的同一话题，保留 operation_ids、execution_verified、限制与验收状态。没有真实操作的讨论结果不会显示为已验证执行；操作成功也不等于房主已验收。结果回写不再次触发普通 @ 或委托通知。

新建订阅默认从当前时刻开始。接入晚于工作创建时，消费者应主动读取已授权的当前待办；不能假定漏过的事件自动重放，也不能把历史正文重新发送成新委托。

## 原有监控任务

在具体消息上选择转为任务，确认以下内容后再创建：

- 原消息与当前版本；
- 一个实际具备资格的明确对象；
- 异常分析、监控计划草稿或结果汇总中的一种；
- 提供给助手的上下文与验收要求。

本版消息转任务一次创建一个任务；原指令流程的一次后续汇总交接仍按原有规则提供。

没有合格对象时不能创建任务。MCP 提案仍先等待真实房主批准，不能通过普通消息绕过审批。普通保存消息不会隐式调用旧 command 调度路径。

转换复用原有预算、任务期限、attempt、租约、fencing、唯一结果与迟到结果留证。网络中断先查原请求；重复提交同一意图必须复用稳定幂等键。

“结果已提交”“目标已验收”和“异常已恢复”分别表示分析、用户决策和独立探针验证。模型结论不能直接把业务异常标为恢复。

## 目标驱动的多助手协作

在房间创建目标，写明希望完成什么、如何验收，选择已加入房间的项目、本人拥有的参与连接、初始协调连接、能力上限、期限和预算。创建与修订只产生提案；MCP 连接不能替房主批准自己的提案。

房主在面板审阅当前版本与内容摘要后明确启用。批准绑定确切的项目、连接、执行位置和版本；修改目标后必须重新审阅。初始协调连接获分配一个只读协调工作项，随后可在目标范围内自主拆分、指派、交接、提问和复核。工作项使用自由目标与验收要求，不限于原有三种监控任务类型，也不固定只能交接一次。

目标能力是上限，不把所有参与者变为同一种角色。只读连接可以计划和复核；需要写入或执行的工作项只能交给当前确实具备相应能力的连接。实际可用范围仍受当前人类权限、连接授权、目标批准、工作项要求与项目/Agent 限制共同约束。为避免混合上下文泄漏，本版要求每个参与连接都能读取目标的全部项目；不满足时应拆成不同目标，不自动扩大连接授权。历史汇总保持来源项目，即使之后缩小目标范围，也不能把旧资料重新标为单项目内容。

每次工作领取使用版本、租约和执行世代；工作结果必须列出该次尝试的真实持久操作。失败操作不能标为成功，尚未确定的操作不能重复执行。纯讨论结果可以没有操作，但不会显示为已验证执行。操作成功也不等于用户已经验收目标。

目标管理的文件与命令步骤通过已有 CodePier 执行路径，返回真实操作编号和状态。当前入口只接受明确项目根目录及原执行节点，其他工作区和 VPS 不在这份批准中。Shell 使用执行账号权限，并不是项目级操作系统沙箱；不能把选中项目理解为命令绝不可能访问账号的其他可见路径。发布、凭据、安装和破坏性操作等额外确认仍应由执行宿主及实际授权流程处理，目标名称或消息不能替代这些确认。CodePier 不会靠自然语言判断一个任意 Shell 命令是否安全。

暂停、取消、到期和撤权会阻止目标开始后续步骤，并使旧工作租约失效。已发往执行节点的命令可能仍在运行，界面保留真实操作状态，不宣称已经杀死外部进程。目标控制只覆盖通过目标入口管理的操作，不能撤回连接独立使用原有工具的权限。

### 独立的目标通知

目标使用 codepier.collaboration.work_available.v1，过滤器明确绑定 project_id、environment_id、conversation_id、goal_id 和 approval_id，接收方仍由当前连接身份验证。手动目标的新批准需要对应的新原生订阅；旧监控、普通聊天提醒或旧批准的订阅不会自动扩展。直接委托则使用上文独立的规则级 delegation_available 订阅，不改变 work_available 的过滤契约。

目标内明确提及另一参与连接可以产生同类通知，受目标通信预算约束。通知只提示读取当前目标与工作项，领取和执行时还会重新核验；通知正文不是新的用户授权。订阅晚于初始工作项时，连接需主动读取待领取工作，不假设所有历史事件都会重放。测试通知不创建工作项，也不证明模型实际处理。

CodePier 不自带模型，也不保证宿主自动开始下一回合。未完成原生订阅或宿主没有处理事件时，工作仍保持待领取；需要在目标宿主中验证真实处理。发布此产品能力不会替任何现有连接启用持续自主执行。

## 账号、空间与连接

个人空间用于个人项目和连接；只有一个空间时不强迫重复选择。团队成员资格、角色能力、连接授权与房间参与范围分别保留原有身份，不迁移历史资源。个人空间不提供无法接受的团队邀请；需要团队协作时明确创建或进入团队。

团队邀请先明确成员级别，再继续选择角色、项目和可否委派。管理员级别自身具有管理权限，必须在邀请前看清；普通邀请不会代替后续项目能力配置。邀请不创建登录方式，受邀者需有可用的登录途径。多个成员来源合并为一人主行，详情仍保留各来源；撤回一个来源不意味着移除全部权限。

“连接”区分助手访问 CodePier 与 CodePier 使用外部工具。连接结果按当前空间、项目展示 read、write、execute、computer 的 Hub 判定及来源，并标明有效期和固定/动态模式；Agent 节点、运行环境和实际执行条件仍需另验。固定授权、fixedProfile 原同意与当前上限交集、显式同意的动态角色模式保持原语义，不悄悄替换为更宽的模式。

本人的密码和会话可从“我的账号”管理；这不赋予实例管理权限。旧连接和页面入口保留兼容，团队成员不会自动成为聊天室成员。

## 同步与恢复

消息顺序、房间增量变化和人类阅读位置分别保存。任务卡更新可以发生在没有新消息的时刻，因此增量游标覆盖状态更新，不能只轮询消息条数。

切换房间或登录范围后，旧异步响应不能更新新界面。阅读游标只代表当前用户的阅读位置，不代表模型已读。旧游标不得让阅读进度倒退。项目集合或可见权限变化时丢弃旧游标并重新读取可见快照。本版保留变更日志，不自动裁剪；后续若引入保留窗口，须同时提供明确的游标重置与对账协议。

拒绝、暂停、到期、撤权、预算不足和证据过期都应保持真实状态。不能换身份、降低检查或反复自动重试来隐藏阻塞。

## 数据升级与保留

本版对既有协作数据库执行有版本的加法迁移，保留房间、加入位置、任务、订阅和审计记录。旧消息补稳定顺序；旧结果通过任务上下文关联原话题，不能按文字相似度猜测。

房间发言许可、独立消息通知与委托规则不会因迁移而自动授予。旧客户端与旧消息 kind 保持兼容；新前端读取能力声明，不显示后端尚未实现的功能。已有 CPJ 请求保持原两类或四类事件；新用途通过独立入口明确设置和接入。

升级前备份完整数据库与配套密钥。旧程序可能拒绝新 schema；回滚必须使用匹配源码与备份，不能只修改数据库版本号。

## 原生宿主验收

源码测试、浏览器中的合成回调和插件工具可调用分别证明不同环节。上线后按[官方 MCP Events 测试流程](https://developers.openai.com/plugins/build/mcp-events#test-in-chatgpt)重新扫描变更过的工具与事件，核对真实安装连接的目录；不能只看到服务端版本号就认定宿主已刷新。

验收至少包含：server/discover 声明事件能力；events/list 返回新事件及精确 schema；宿主实际工具目录包含 collaboration_message_create、collaboration_delegation_read、目标/工作工具和带 conversation_id 的 collaboration_read；明确授权后创建原生订阅并通过 challenge；匹配事件得到 2xx；原目标聊天实际读取委托并按要求处理；结果回到原话题。另验证不匹配过滤器、重复投递、暂停、撤权和过期不会执行。

缺少目录、原生订阅或目标聊天响应证据时，应报告停在哪一环，不能宣称全链路完成。CodePier 不提供可代替宿主的回调 URL 或签名材料；也不通过后台数据库修改把缺失步骤伪装为接通。

## 本版边界

本版面向房主和明确接入的助手连接。尚未提供一般人类多人房间 ACL、通用文件上传或永久历史归档；已有项目资料和证据仍按自身权限读取。界面不会把不具备的能力画成可用按钮。

CodePier 提供持久消息、接入协议与确定性任务记录，不提供模型服务。真实宿主能否订阅、何时处理与是否回应需要在目标环境验证。源码测试和浏览器测试不等于已经在生产创建订阅或升级现用 Hub/Agent。

使用原有监控与运维能力时，继续参阅 [协作中心说明](COLLABORATION.md)。开发与发布门禁见 [开发与验证](DEVELOPMENT.md) 和 [GitHub 发布清单](RELEASING.md)。
