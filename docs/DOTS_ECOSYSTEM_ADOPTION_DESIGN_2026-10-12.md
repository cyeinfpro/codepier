## 一、结论与产品目标

### 1.1 核心判断

**值得吸收的是其他项目对“最后一段用户流程”的打磨，而不是把它们的队列、授权、桥接服务重新叠加到 CodePier 上。**

本轮核对发现，作为研究基线的 CodePier 1.27.4 源码已经具备：统一规范消息、微信与 Telegram 独立投递、一次预授权后的授权码自动完成、阶段回复更新、原操作恢复、持久回执、任务活性投影，以及分层并发与公平调度。此前泛泛提出的“新增统一消息总线”“新增任务调度器”“加入 Inbox / Outbox”，不能直接变成开发清单；这些方向相当一部分已经存在。[B02–B12]

真正应优先投入的是：

1. **一眼看懂连接是否可用，并且只给出当前最必要的下一步。** 不再让用户自己拼接账号、联系人、Dot、权限、订阅、节点的状态。
2. **每条输入都有明确处理去向。** 连续补充的三条消息可以由一份回答覆盖，但不能只回复一条、其余长期显示待处理；也不能把“谢谢”强制变成任务。
3. **普通聊天轻，复杂任务稳。** 简单问题直接回答；长任务以同一张进度卡持续更新；需要用户操作时，准确说明要去哪里、处理哪件事。
4. **先消除 CodePier 自己制造的延迟。** 优化重复状态查询、重复构建视图、上下文重复传输和局部队列阻塞；不承诺突破 Dot 平台配额或调度能力。
5. **恢复原工作，而不是重新做一遍。** 页面刷新、回执丢失、通道超时、宿主重连必须落回原消息、原请求键、原操作证据。
6. **相同能力在各入口有一致体验，不同能力有诚实降级。** 面板可原位更新，某个 IM 端只能发文本，就只发送重要阶段与最终结果，而不是假装所有端都有实时流式输出。

### 1.2 产品北极星

> 用户把 Dot 带进 CodePier 后，只需要自然地说清要做什么；CodePier 负责把消息可靠地交给原 Dot，把真实进展和结果带回原对话，并在确实需要用户时只要求最少且准确的操作。

“像直接使用 Dot”应理解为**交互连续、上下文清楚、流程少**，不是声称能够复制 Dot 私有记忆、捕获所有原生审批、同步全部私人聊天或保证宿主永久在线。

### 1.3 本轮不做的事情

本稿不修改业务代码、数据库或生产配置；不创建账号、凭据、MCP grant、原生订阅；不提交、推送或发布。后续实施也不以以下事项为目标：重做模型 API 网关、接入共享账号池、引入第二个模型替 Dot 决策、默认增加飞书等新通道、把所有设置合并成“全权限”、为降低等待绕过宿主审批。

### 1.4 建议优先级

| 优先级 | 增量 | 用户直接感受 | 复用基础 |
|---|---|---|---|
| P0 | 连接就绪投影与单一下一步 | 不必猜“为什么连上了却没反应” | enrollment、joining、events、scope manifest |
| P0 | 回执语义统一、异常分流 | 不再把已接收看成已完成 | relay receipts、task liveness、channel outbox |
| P0 | 热路径量测与重复工作削减 | 输入、切换、看反馈更顺滑 | relay-sync、现有局部 DOM patch、Store.run |
| P1 | 逐输入处理记录与显式合并覆盖 | 补充消息不漏处理、不重复回答 | dot_messages、dot_ack、最终回复回执 |
| P1 | 阶段卡与原审批入口衔接 | 长任务有反馈、等待有去处 | dot_update、真实 work/operation、状态回执 |
| P1 | 内部通道能力描述与媒体清单 | 每个平台能做什么一目了然 | ChannelRouter、ChannelBinding、media/shares |
| P1 | 恢复诊断与精简读取包 | 少调用、少排队，断线后接着做 | inbox、recovery、evidence、receipt 查询 |
| P2 | 可选客户端待发持久化、长期订阅协商、新通道 | 进一步减少接入与离线摩擦 | 必须分别验证客户端、宿主及供应商能力 |

上述优先级是本稿的产品判断，不是外部项目成熟度排名；也不代表 P0/P1 功能目前全部缺失。

## 二、研究方法与代码基线

### 2.1 为什么先固定基线

本轮发现两个不同状态：

| MCP 默认映射目录 | `main`，提交 `800c05ec143cd7bccf4cdbbf788fb9c9d59f0622`，源码版本标记 1.26.1，存在多项未提交修改 | 只作为当前项目入口及历史设计参照，不据此断言新版缺功能 |
| 干净的 1.27.4 工作树 | 分支 `release/v1.27.4-unified-enrollment`，提交 `471a30ec5438117677768674b5f46558b6cd15df` | 作为本稿主要实现基线 |
| 其他并行工作树 | 可见接入、范围、低延迟等相关候选工作 | 不覆盖、不合并；正式实施前必须重新核对已合入内容 |

源码版本标记、工作树名称和已有发布操作记录均不能单独证明当前生产节点运行哪个版本。本稿未进行生产进程版本、真实微信收件、真实 Dot 消费或性能压测验证。

### 2.2 证据分层

本稿使用四种证据，不混用：

- **实现证据**：实际读取的源码、函数和数据结构；可判断实现路径，不能单独证明线上效果。
- **契约证据**：项目的协议／设计／操作文档；其中标为草案的内容不当作已实现。
- **测试证据**：实际读取的测试文件说明覆盖意图；本轮没有执行这些测试，不继承历史“通过”结论。
- **运行声明**：维护者的验收记录；仅代表其记录中的样本，不推广成普遍可靠性保证。

外部项目中，对 `dot2api` 阅读到了固定提交下的服务实现；对飞书桥接阅读了逐事件处理及审批提醒契约；对 cc-connect 阅读了明确标记为 Draft 的桥接协议；其他项目主要核验当前 README、能力边界与协议资料。未声称完成所有外部项目的完整源码审计。[E01–E14]

## 三、逐项目吸收决策

### 3.1 总览

| 项目 | 已核验的有价值机制 | 对 CodePier 的决定 | 不照搬的部分 |
|---|---|---|---|
| `Pluviobyte/dot2api` | 稳定任务标识、幂等提交、租约、任务结果与事件分离 | 吸收契约清晰度与恢复测试思路；不另建队列 | 租约到期直接重新排队；查询路径触发维护；把 Dot 包装成通用模型 API |
| `yaodiff/feishu-dot-bridge` | 逐输入处理记录、合并回复覆盖、状态卡、投递不确定性 | 最值得补充的处理语义与等待反馈范例 | 单人部署的信任假设；把卡片点击当原生审批；将一个通道回执当所有端完成 |
| `RerrentLinden/dots-wechat-bridge` | 简单 final／复杂 ack→final；固定阶段与幂等；媒体分块 | 吸收回复节奏、真实接收反馈和资源边界 | 每个请求强制两次回复；专用 Tunnel 等于逐调用者身份认证 |

| `abird-ai/dotlink` | 权限感知工具目录、明确的可恢复／致命连接错误 | 吸收能力展示与分级恢复思想 | 重建所有连接的恢复半径；宣称项目范围等于 OS 沙箱 |
| `Fanch-hui/codex-bridge` | 原会话继续、审批与输出集中呈现、项目写入互斥 | 吸收统一工作入口和写冲突表达 | 用“超限拒绝”替代既有公平队列；擅自改派另一 Agent |
| `AndreLYL/wechat2dot` | doctor、离线 demo、按能力分层的验收 | 吸收诊断与首次接入验证 | 把模拟网络 demo 当真人微信↔Dot 通过；复制其部署栈 |
| `Tencent/openclaw-weixin` | 微信通道协议参考 | 用于定向协议一致性测试和适配审查 | 与 Dot 任务编排混为一谈；认为协议说明保证账号永久可用 |
| `Wing900/dots2api` | 仓库实际对接 `dots.ai` | 排除出 OpenAI Dots 核心方案 | 因名字相似误接技术路线 |

来源见附录 B。表格中的“吸收”均指在 CodePier 原有边界内重新设计，并非直接复制代码或自动增加依赖。[E01–E14]

### 3.2 dot2api：契约值得学，超时重跑不能学

在固定提交 `66a761505ff73c5dca730260efcaeb5697db81ad` 的 `src/dot2api/service.py` 中，提交按主体与幂等键查重，领取返回租约令牌，续约受任务期限约束，结果重复提交有冲突检查。这些机制让“收到、领取、完成”分得较清楚。[E01]

但同一文件也展示了两个不适合直接移植的点：

- `maintenance()` 对租约过期的运行任务，在未耗尽尝试次数时转回 queued；它没有替 CodePier 核对某个 OS 命令是否已经产生副作用。
- `call()` 在分派 `get_task`／`list_tasks` 等动作之前执行维护。因此，不能直接把这一路径包装成 CodePier 宣称无副作用的状态查询。

**CodePier 的取舍**：继续使用原 operation journal、attempt、fencing token 和 `task_liveness`。只读查询不制造工作；未知操作先核对，不能用“租约过期”推导“可以重新执行”。[B04、B05]

此前“一 Dot 一队列、顺序执行”的描述也不能自动解释为所有服务端入口都强制队列互斥。本稿不以该表述制定 CodePier 的并发上限；上限仍须来自实际执行者能力和本地调度约束。

### 3.3 飞书桥接：最值得吸收的是“回答究竟覆盖了哪些输入”

其逐事件契约允许记录等待授权、不需要回复、由另一份实际回复覆盖，并把处理决定与外发回执分开。合并覆盖需要同一绑定中的真实回复关联，不能用“Dot 里已经说了”替代通道发送记录。[E02、E03]

**CodePier 的增量**不是新增一个任务引擎，而是在现有 `pending/read/handled` 旁补充可追踪的处理原因和覆盖关系。还必须比单一飞书通道进一步细分：回复已写入 CodePier，不代表微信或 Telegram 均已接受；某端失败不能让已经完成的解释再次交给 Dot 重做。

其等待提醒文档也明确：桥接不是原生 Dot 全部审批的反向事件源。可借鉴“告诉用户去原入口确认”，但不能承诺能自动捕获每一次审批。[E04]

### 3.4 微信桥接：吸收“轻回复节奏”，不增加仪式感

`dots-wechat-bridge` 将简单问题直接 final、复杂问题 ack→final 交给消费方选择，服务端维护阶段一致性。[E05]

CodePier 已有 `complete=false`、`dot_update` 和最终回帖。因此应优化的是**什么时候显示、怎么合并、何时提醒**：简单问题不要加一条“收到”；复杂任务在确有动作时展示进展；普通阶段原位更新，重要等待突出一次。不要再加聊天／任务开关，也不要要求用户点“转任务”。[B03、B04]

### 3.5 Hookdeck：吸收投递可观测性，不迁走消息所有权

该桥接明确无状态，持久接收、去重和重试主要依赖 Event Gateway；它仍是实验性演示项目。[E07]

CodePier 已有事务事件 outbox、签名、回调验证和重放。因此新增 SaaS 依赖并不能自动增加可靠性，反而会引入另一套身份、成本和故障边界。优先复用现有 `events.py`，补足**某次通知为什么没到、到后为什么没消费、下一次允许做什么**的投影与诊断。[B07]

### 3.6 cc-connect：吸收能力描述，不建设插件平台

Draft 中值得保留的是 `text/image/file/typing/update_message/preview` 一类能力声明，以及不支持卡片时降级为文本的思想。[E08]

在 CodePier 中先实现**编译期受控的内部通道能力描述**，不要立即引入可加载任意外置适配器的新网络端点。能力要区分“供应商理论支持、当前实现支持、当前账号可用、当前授权允许”四层；声明支持不能自行赋权。

### 3.7 dotlink 与 codex-bridge：吸收局部恢复和工作入口，保留更严格边界

dotlink 文档说明会按权限隐藏不可用工具，并对瞬时连接错误与无效凭据作不同处理；其重建运行时方案是该产品的具体选择，不能证明 CodePier 应重启所有连接。[E09]

codex-bridge 的 README 明确同项目最多一个活跃写任务，状态未知也占名额，超限时拒绝或失败而非自动排队。[E10] 对 CodePier，值得借鉴的是**未知写入不释放冲突保护**以及清晰的会话／审批入口，不是倒退为“用户自己反复重试”。已有路径锁和公平调度应继续发挥作用。[B12]

### 3.8 成熟度修正

飞书桥接当前 README 记载了有限真实文字、合并回复、图片与状态卡检查，同时仍标为实验性；其 About 摘要里的 multi-user 与当前个人自部署范围不一致，应以具体文档边界为准。`wechat2dot` 则明确自己的真人微信↔Dot 验收尚未完成。两者不能用一句“都有生产实测”概括，也不能一概说“全部没有实测”。[E02、E11]

## 四、已有能力与真实增量

### 4.1 差异矩阵

| 能力 | 1.27.4 读取证据 | 本稿新增／补强 | 明确不重复做 |
|---|---|---|---|
| 无模式对话 | `dot_chat.configuration()` 返回无需模式切换，提供原消息上下文与 task_request | 统一文案与首屏；补充消息的处理覆盖 | 不再建“聊天模式／执行模式” |
| 阶段回复 | `DotRelay.update()` 校验原作者、版本、最终态 | 进度卡呈现、合并策略、等待提示 | 不新建第二套消息更新接口 |
| 接入预授权 | `channel_enrollment` 冻结 scope digest，私聊证明后事务激活 | 可恢复向导、差异确认、统一就绪状态 | 不把后台逐目的证据压成一个同意字段 |
| 跨端同步 | `ChannelRouter.queue()` 规范消息＋独立 transport jobs | 能力矩阵、统一错误呈现、分端可见状态 | 不复制一套消息库或重复唤醒 Dot |
| 投递回执 | `dot_delivery_receipts`、原键查询、outbox 参考实现 | 统一恢复入口；明确宿主持久化证据 | 不把参考适配器说成外部宿主已安装 |
| 原工作恢复 | `TaskLiveness.recovery/evidence/work_summary` | 稳定的“仍在运行／待发表／未知”体验 | 不以查状态替代心跳，不丢弃原 fence |
| 事件可靠性 | `EventService` 事务 outbox、签名、验证、重放 | 诊断、过滤、公平性量测 | 不引入第二个必选事件网关 |
| 调度并发 | Agent 多通道＋Hub 持久准入＋资源冲突与项目公平 | 显示等待原因、控制面延迟优化 | 不新增全局串行总队列 |
| 工作区稳定性 | 保留对话 DOM，惰性详情，焦点与滚动恢复 | 减少重复构建；统一动效与状态呈现 | 不推倒重写前端框架 |
| 附件 | 原产物、分段、摘要、独立分享审批 | 清单式分享、能力可见、续传体验 | 不默认外发二进制，不重跑产物任务 |

### 4.2 已定位但尚未压测的性能候选点

**后端：** `DotRelay.receipts()` 先取收件者，再为各收件者查询回复、工作、订阅和授权。在一个页面批量渲染多个消息时，存在重复查询的优化空间。`TaskLiveness.work_summary()` 已做聚合批查询，不能笼统声称“全部状态查询都是逐条查询”。`for_messages()` 仍有按工作核验对象与权限的读取，批处理时必须保留原授权精度。[B04、B05]

**前端：** `collaboration-relay.js` 的同步会触发 timeline patch、hydrate、连接卡刷新及 workspace refresh；工作区 refresh 已有局部 patch，但仍会构建部分模板。可以进一步通过 revision／dirty set 避免“没有变化也做同一轮计算”，而不是换成更频繁的轮询。[B13、B14]

**事件：** `EventService` 当前可见一个容量为 2 的网络 semaphore。它可能成为特定并发下的等待点，但没有压测前不能判为现有卡顿根因，更不能直接增大到任意值。[B07]

上述为源码推导出的**优化候选**，不是已经复现的故障或已测量瓶颈。

## 五、架构与不可破坏的约束

### 5.1 增量架构

```text
Web / 微信 / Telegram
        │
        ▼
现有通道认证、入站校验、去重与游标事务
        │
        ▼
现有 canonical message + dot_messages
        │                         └── 新增：处理原因 / 合并覆盖记录
        ▼
现有 MCP Events + inbox / recovery 读取
        │
        ▼
原 Dot：理解、追问、回复；需要工作时使用原 task_request
        │
        ├── 普通 / 阶段 / 最终消息 → 现有消息与投递回执
        │
        └── 现有 delegation / work / operation / scheduler
                                              │
                                              ▼
                                原操作结果与验收证据
        │
        ▼
现有 ChannelRouter / channel outbox / media shares
        │
        ▼
分端呈现与回执

新增的横切层：
  只读体验投影 + 下一步动作目录 + 通道能力描述 + 性能/诊断指标
```

**不引入额外必选数据库、消息中间件、模型进程或 SaaS 网关。** 内部模型继续以现有 Store、消息和操作记录为事实源；新增投影是事实的解释，不是替代事实的第二套真相。

### 5.2 八条不变量

| 编号 | 不变量 | 违反时的处理 |
|---|---|---|
| I-01 | 消息、通知、消费、执行、验收、外发是不同事实 | 拒绝把某一层成功映射为全链路完成 |
| I-02 | 当前身份、项目、环境、绑定世代、权限每次按原边界校验 | 旧缓存失效，返回具体原因，不回退到更宽授权 |
| I-03 | 同一次意图使用原幂等键；不同意图使用新键 | 同键异文返回冲突，不静默覆盖 |
| I-04 | 未知副作用不自动重放 | 查询原回执／operation，保留未知态 |
| I-05 | 读取不是授权、领取、续租、发送或执行 | GET／query 不调用维护型写路径 |
| I-06 | 通道副本不是新用户输入 | 不二次入站、不重复派工、不互相唤醒 |
| I-07 | UI 简化不抹去目的、范围与证据差异 | 一个操作可记录多项明确同意，但不能推断未展示同意 |
| I-08 | 原宿主限制不可由 CodePier 伪造解决 | 无真实能力就准确降级，不制造 callback、委托 ID 或审批成功 |

### 5.3 身份与线程

规范消息至少能关联：空间／房主、项目／环境、conversation、thread、原输入、指定 Dot、消息版本、来源与外部绑定世代。派生结果保留其关联，不以昵称、当前选中项目、最近活跃会话或相同文本猜测路由。

用户跨端接着聊时，沿用**明确绑定的原话题**。当私聊绑定和用户提到的项目不一致，保持当前安全路由，给出“当前连接项目为 X”的说明；不能从正文中的“去 Y 项目”静默扩大可执行或可外发范围。[B08–B11]

### 5.4 建议采用的设计准则

少一个让用户理解的概念，比多一个后台模块更重要；同一信息尽量只在一个主位置展示；状态由证据驱动，动画只解释变化；正常工作不打断，真正需要人时清楚打断；可恢复错误优先恢复原对象，而不是让用户重新接入。

<a id="section-6"></a>
## 六、完整用户流程

### 6.1 首次把 Dot 加入协作室

**目标：一个持续的接入面板，完成后自然回到对话。**

```text
打开协作室
  → 添加 Dot：名称 + 当前项目/环境 + 清楚的能力摘要
  → 生成一次性加入指令
  → 用户在目标 Dot 中通过已授权 CodePier 插件提交
  → 宿主按实际能力完成原生订阅确认
  → 面板接收真实登记/订阅结果，自动进入相应就绪状态
  → 在同一输入框开始对话
```

设计要点：

- 已存在待完成 slot 时，主按钮为“继续连接”，不再默认创建第二个 Dot。
- 复制指令后面板不关闭，保留同一接入对象；无需用户反复点击刷新。
- “已登记”“可接收通知”“已有真实回复”分别展示证据，不用一个绿色“在线”覆盖全部。
- 宿主不支持原生事件时，明确提示当前只能手动读取；可以保留已授权工具能力，但不声称持续订阅成功。
- 已有同范围订阅不重复创建；暂停、撤销、过期、宿主待确认分别有独立下一步。
- 接入成功后的首个示例按钮只填充草稿，不自动发送、不创建真实业务任务。[B03、B14]

**交互验收目标：** CodePier 自有流程不出现两个以上连续的主配置页面；外部宿主的独立确认按实际要求保留，不计作可以消除的产品步骤。用户不需要理解 event、callback、grant 或 lease 才能完成接入。

### 6.2 微信／Telegram：一次集中说明，私聊证明后自动完成

这条后端能力已在 1.27.4 出现，本稿重点是把它完整呈现，而不是再开发一套“自动绑定”。[B08、B09]

```text
选择已连接账号 / 扫码或连接机器人
  → 同页确认：本人、目标 Dot、项目/环境、能力、回传、期限、撤销
  → 生成绑定当前 scope digest 的一次性授权码
  → 本人到指定私聊发送授权码
  → 服务端验证原账号/世代/对象/时效/范围
  → 同一事务完成绑定、使用已保存的本人预授权、登记通知
  → 面板自动显示结果；私聊通知另行展示实际发送回执
```

一张授权摘要包含：当前账号、允许的本人对象、准确的项目／环境、原 Dot、可使用能力、结果回传位置、授权持续方式、任务预算、撤销入口。保存凭据、服务条款、本人身份、未来任务、结果回传及持续授权等目的分别保留对应版本与记录，不能相互替代。

**减少操作的具体办法：** 同一次清楚展示的确认操作可以提交多项明确目的；不在授权码完成后再要求用户把同样内容确认一遍。若某项目要求独立选择或某项未同意，保持独立，不为了“一键”偷偷置为 true。

#### 范围变化时只确认差异

| 变化 | 交互 | 后端原则 |
|---|---|---|
| 原页面刷新、网络暂断 | 恢复原进度 | 不再建绑定或 grant |
| 同账号、同范围、原授权码仍有效 | 继续原步骤 | 使用已冻结 digest |
| 联系人／项目／环境／执行目标改变 | 展示新旧差异，重新确认相关授权 | 原预授权不能被复用到新范围 |
| 凭据世代更新 | 标记重新核验原本人 | 不继承旧 backlog 的任务资格 |
| 授权码过期 | 仅重建原范围的配对证明步骤 | 不扩权，不重放旧消息 |
| 用户撤销 | 明确“已撤销” | 不自动重新启用 |

授权码或二维码只在明确的私有接入视图展示；不进入普通消息日志、埋点、截图样本或错误报告。若私聊尚未证明身份，UI 应显示“等待本人完成验证”，而不是根据昵称先显示“已确认是本人”。

### 6.3 普通聊天：输入之后立即进入原对话

用户：“这个方案的核心是什么？”

- 本地气泡立即出现，初始状态“正在发送”。
- 服务端持久化后显示“已保存”；不能在 POST 尚未确认时写“已送达”。
- Dot 使用原上下文直接回答；无需执行任务时不创建 work，不要求用户选择模式。
- 简单回答只有一条完整回复，不先追加“已收到，请稍等”。
- 过程无任务时，不用空任务卡把聊天撑开。

当前面板已有乐观发送和原 `client_message_id` 核对，继续使用；本稿补齐文案与分层回执，不改变意图去重规则。[B13]

### 6.4 连续补充：一次回答覆盖多条输入

用户连续发送：

```text
A：检查 MCP 的连接流程，先写方案。
B：不要改代码。
C：也把微信和 Telegram 的一致性考虑进去。
```

Dot 读取原线程后，可以给出一份方案，并明确其覆盖 A、B、C。面板将三条输入关联到同一份最终回复；仍保留 B 是限制条件的来源。服务端只校验关联和证据，**不假装可以自动证明方案语义上完全满足 B、C**。

不因为 A 看起来像“任务”就提前执行，也不因为 C 较晚到达就只显示 C 已处理。用户再发 D：“按方案修改”，这是新的明确意图，才能在当前授权允许且宿主同意时沿 D 的原任务请求执行。

### 6.5 长任务：后台工作，原对话连续反馈

用户：“检查日志，定位异常，给我结论。”

```text
消息持久化
  → Dot 收取并说明已开始检查（真实消费后）
  → 需要项目操作时，从原消息取得现有 task_request
  → 核验、领取、执行、真实 operation 反馈
  → 同一进度卡更新重要步骤
  → 原结果提交 + 最终说明
  → 各已批准通道独立投递
```

用户补充“先不要重启”时，Dot 应在下一安全边界读取原 inbox，判断是否需要调整；CodePier 不从一句新文本直接杀掉进程或释放锁。停止按钮必须显示“正在请求停止”，直到原执行器证实停止，才显示“已停止”。

### 6.6 等待用户：区分“缺资料”和“缺审批”

- 缺资料：“还缺目标日期，请在这里补充。”这是对话等待。
- 宿主审批：“这一步需要在 Dot 原生请求中确认。”这是宿主等待。
- CodePier 授权：“当前只允许读取；此次修改需要新增写入授权。”这是范围等待。
- 执行状态未知：“正在核对原操作，暂不重复执行。”这是恢复等待。

不能全部归类成“待确认”，也不能用一个“继续”按钮做四种不同的写动作。完整动作与校验见第七节。

### 6.7 断线、刷新、重连

服务端已保存：恢复原会话，查原消息／工作／投递记录，不要求重发正文。

只保存在浏览器内存、尚未得到服务端确认：明确“仅保留在本页”。关闭页面前提示可能丢失，不许承诺刷新后一定存在。可选持久化见第十二节。

工作已完成但回复尚未发表：展示“执行已有结果，等待 Dot 补充说明”；恢复的是发表步骤，不重跑操作。微信发送不确定、面板结果正常：在消息详情标记微信待核对，保持面板最终结果可见。

### 6.8 多 Dot 与多项目

普通讨论可以明确提及多个 Dot；实际执行仍需要唯一、已批准的执行对象。当前 `from_message()` 已拒绝把多 Dot 收件消息直接变成执行任务。[B03]

不为了减少排队把 Dot A 的私有上下文交给 Dot B；不因项目名相同推断是同一个项目；不同 worktree 也不自动获得不同项目配额。只有明确重新分配、目标授权一致并完成上下文范围确认后，才讨论转交能力。

## 七、统一状态与下一步操作

### 7.1 后端保留维度，前端只展示一个主状态

建议新增只读 `ExperienceProjection`，其数据全部来自现有真实记录：

| 维度 | 示例证据 | 不能推导的结论 |
|---|---|---|
| transport | 通道连接、回调接受、请求错误 | 模型在线、用户已读 |
| consumption | Dot 显式 read ack、阶段回帖 | 任务已经完成 |
| handling | 回复覆盖、等待资料、不需回答、关联工作 | 外部通道已经收到 |
| execution | work/operation 当前状态与真实更新时间 | 验收一定合格 |
| acceptance | 真实检查与 result 中的验收记录 | 私聊用户已经看过结果 |
| publication | Dot 消息／更新已经提交 | 微信、Telegram 同时成功 |
| channel_delivery | 每个目标端接受／未知／拒绝 | 客户端显示或用户阅读 |

投影输出建议包含 `primary_state`、`reason_code`、`evidence_source`、`observed_at`、`next_action`。缺证据用 unknown／未核验，不用查询发生时间补齐“最近活跃”。

### 7.2 主状态映射

| 用户主状态 | 必要证据 | 主要动作 |
|---|---|---|
| 正在发送 | 客户端本次意图仍在发送 | 查看原发送状态 |
| 已保存，等待 Dot | 原输入已提交，尚无消费证据 | 无需操作／必要时核对连接 |
| Dot 已接收 | 当前 Dot 的实际收件记录 | 等待回复 |
| 正在处理 | 活跃工作证据或 Dot 实际阶段反馈 | 查看进度／补充说明 |
| 等待你补充 | 明确的资料问题 | 在原对话回答 |
| 需要授权 | 已存在真实权限原因或请求 | 打开原审批／查看范围差异 |
| 正在核对原操作 | 原 operation 未知或证据陈旧 | 查询原状态，不重复执行 |
| 执行已有结果，等待回复 | 操作已结束，但原结果／说明尚未提交 | 恢复原发表步骤 |
| 已回复 | 普通最终消息已经提交 | 查看回复 |
| 工作完成／验收待核验 | 执行成功，但验收证据不足 | 查看实际结果与待核验项 |
| 已完成 | 对应工作的成功与必要验收证据满足 | 查看结果 |
| 结果已保存，部分通道待核对 | canonical 回复存在，某端未知／失败 | 查看该端回执 |

`已回复` 与 `已完成` 不合并。普通聊天不需要伪造一个任务验收，工作任务也不能因为生成了一段“完成了”的文字就变成成功。

### 7.3 下一步动作是受控目录，不是任意工具脚本

建议动作类型：`open_original_message`、`inspect_original_receipt`、`resume_enrollment`、`open_scope_review`、`open_host_confirmation`、`copy_original_join_instruction`。这些名字是拟议 UI 动作标识，不是现有公开工具名。

所有写动作再次校验当前主体、原对象、版本、世代与权限；服务端不接受前端传入任意命令、callback、外发地址或可执行工具 JSON。导航动作不得偷偷执行写入。

| 情况 | 自动行为 | 用户动作 | 禁止行为 |
|---|---|---|---|
| 临时断网 | 有界退避，查原回执 | 通常无需操作 | 换键重发 |
| 429 | 遵守原服务重试信息、保持队列 | 查看预计可重试时间，若确有依据 | 建新连接绕限制 |
| Token／凭据无效 | 停止无意义重试，保留状态 | 更新对应凭据 | 自动扩大权限 |
| 宿主拒绝 | 记录宿主拒绝类别和可见原因 | 原宿主处理 | 伪造 delegation 或改走更宽入口 |
| scope digest 改变 | 冻结原待接入请求 | 仅确认实际差异 | 旧同意应用于新范围 |
| 外发未知 | 只核对原回执 | 标记本人已确认收到（独立证据） | “再发一次”作为默认主按钮 |
| 用户主动暂停 | 保持暂停 | 明确恢复原连接 | 后台恢复逻辑自动解除暂停 |

### 7.4 连接状态的建议表达

就绪不采用永久绿色“在线”。展示“已连接 · 可接收消息”“已登记 · 待宿主订阅”“可对话 · 执行权限未开放”等基于证据的组合。最近验证时间显示来源，例如“最近一次回帖：14:32”，而不是从轮询时间生成“刚刚在线”。

出现多个问题时按阻塞原流程的最早必要步骤选择一个主操作，其余进入详情；例如凭据无效时不同时提示重建订阅、重新扫码和重建 Dot。

## 八、逐输入处理记录与合并回复

### 8.1 为什么现有 handled 不够

当前 `dot_ack` 主要表达 read／handled；最终回帖会把所回复的原消息标为 handled，派生 work 也会把消息交接为 handled。它足以做基本接收与处理，但不足以明确解释“无需回答”“由哪一份回答覆盖”“在等资料还是等授权”。这不是否认已有回执，而是补充处理语义。[B03]

建议将新记录作为现有消息的附加事实，**不新建一套独立任务领取／续租系统**。真实项目执行依然只使用现有 work 租约。

### 8.2 建议状态

| handling_state | 含义 | 是否还需要 Dot 处理 |
|---|---|---|
| `awaiting` | 没有明确处理决定 | 是 |
| `observed` | Dot 已显式收取 | 是；不是完成 |
| `waiting_input` | 已提出具体问题 | 等待原线程补充 |
| `waiting_authorization` | 已报告授权阻塞 | 等待真实授权状态变化 |
| `work_linked` | 已交接原 work | 不再重复建 work；检查原工作恢复 |
| `reply_committed` | 对应最终回复已写入规范消息 | 通常不再生成相同回答 |
| `covered` | 被一份明确最终回复覆盖 | 不重复回答；投递独立检查 |
| `no_response_required` | Dot 明确决定不需回复，并有允许的原因 | 否，但保留决定与责任来源 |
| `legacy_handled` | 旧接口已经标为处理，但语义不足 | 保留历史，不补造细分结论 |

是否存在工作、是否最终成功、是否各端发送，均为独立维度。`work_linked` 不是 execution succeeded；`covered` 不是外部已读。

### 8.3 合并覆盖必须满足的约束

拟议输入包含原消息 ID、原版本与稳定摘要、覆盖回复 ID／版本、处理 revision、幂等键。服务端逐项验证：

1. 所有输入确实发给同一个 Dot，属于同一已授权线程和当前可见范围；单次上限建议 20，超限显式分页，不忽略尾部。
2. 覆盖回复是该 Dot 实际提交的最终消息，不是占位、阶段回复、预定任务、另一个线程的回答或仅存在于 Dot 私聊中的文本。
3. 覆盖关系只能指向直接回复，不允许 A 覆盖 B、B 再覆盖 C 的循环／链式推导。
4. 原输入若存在未完成工作，覆盖普通文字不能关闭工作或掩盖执行失败。
5. 原文或作用域变化时，拒绝陈旧写入；历史覆盖可保留为旧版本证据，但不得解释成新版本已满足。
6. 同一个 revision 的竞争写入使用 compare-and-swap；重复同键同文返回原记录，同键异文冲突。
7. 服务端不使用相同文本、时间邻近或模型推测自动标记 covered。语义覆盖由原 Dot 明确声明，面板可以追溯该声明。

### 8.4 CodePier 与单通道桥接的区别

飞书桥接的契约将合并覆盖绑定到真实 API 接受的回复。[E03] CodePier 有面板和多个外发端，建议拆成两条事实：

- **内容处理完成**：最终规范消息已经持久化，显式覆盖关系成立。
- **各端投递完成**：对应通道自己的回执满足其契约。

因此，即使 Telegram 暂时失败，也不会将同一批输入重新交给 Dot 生成答案。缺的是外发恢复，不是内容重新处理。界面仍能提示“回复已保存，Telegram 待核对”，避免遗漏用户实际接收问题。

### 8.5 不需要回复的输入

允许 Dot 对“谢谢”“收到”等作明确 `no_response_required` 决定，但 CodePier 不靠关键词自动忽略。若输入含新的明确任务、限制条件，或关联未完成工作，不允许借此直接结清工作。该决定显示于详情，不必在对话里新增“这条消息无需回复”的噪声气泡。

### 8.6 消费契约优化

在既有 inbox 返回结构中附带 handling 摘要与正确的后续请求，避免 Dot 为确认同一条输入反复查询。一次正常唤醒建议先读取原未处理输入与未完成工作的精简摘要；处理后在结束前重扫变化，不能只读取新消息而忘记已从消息队列交接出去的工作。[B03、B05]

相关契约升级必须可发现、可回退，不要求旧消费者立即理解新字段。旧的 read／handled 接口保持原兼容语义，新消费者显式使用新版处理结果，不伪装旧确认已经拥有新证据。

<a id="section-9"></a>
## 九、阶段反馈与审批衔接

### 9.1 回复节奏

| 场景 | 推荐反馈 | 不做什么 |
|---|---|---|
| 可立即回答的聊天 | 一条 final | 不机械先发 ack |
| 已实际开始较长处理 | 一条简短阶段回复，后续原位更新 | 服务端保存时不冒充 Dot 说“我开始了” |
| 连续小进度 | 合并到同一张卡 | 不按每个工具调用刷屏 |
| 关键阶段完成 | 更新明确的阶段与实际结果 | 不凭时间把进度增加到 90% |
| 需要用户操作 | 一次突出的等待卡，关联原请求 | 不把等待藏在普通日志里 |
| 最终结果 | 原最终回复＋产物／验收摘要 | 不把发送失败变成重新执行 |

本稿延用既有 `dot_update` 全量替换正文、版本校验、最终态不可修改规则。不把整段文本拆成字符后播放，冒充模型真实 token 流。[B04]

### 9.2 进度卡的数据而不是文案决定状态

建议卡片包含：阶段标题、可选真实进度计数、最近证据时间、当前阻塞原因、原工作链接、可用下一步。没有实际总量就不显示百分比。

Dot 的“正在整理结论”是消费方报告，应标识为消费方反馈；Agent 的命令完成时间是执行证据。两者可以共同呈现，但不能用前者刷新后者的操作活性。

### 9.3 重要等待只提醒一次

同一原对象、同一等待原因、同一审批版本的提醒拥有稳定 ID；普通轮询不产生新通知。等待解除后更新原卡，不自动删除历史证据。范围变化形成新审批版本时，再提示实际差异。

面板内卡片可以原位更新。外部通道是否支持编辑消息必须依据当前适配器能力：不支持时只发必要的首次等待和最终结果，不通过几十条新消息模拟更新。

### 9.4 原生审批的能力边界

MCP Events 是服务器向宿主发送事件的机制，不是服务器自动读取宿主全部审批的接口。飞书桥接也明确指出这一边界。[E04、E14]

建议分三类：

- **已有真实审批请求引用**：显示请求摘要、来源、当前状态，并使用宿主确实返回的安全链接。
- **Dot 明确报告等待，但没有可验证请求引用**：显示“Dot 报告需要在原生界面确认”，只提供已核验的官方入口；不生成虚假的专用任务链接。
- **仅可能需要审批**：写“这一步可能在 Dot 中要求确认”，不能提前标为“正在等待授权”。

点击 IM 卡片只导航，不批准原生权限。由 CodePier 自己管理的授权变更仍需通过原 owner 边界、明确差异、版本检查和审计完成。

### 9.5 不把阶段反馈变成新的阻塞条件

默认情况下，普通进度卡发送失败不能阻止已获授权的只读检查继续执行。否则为增强体验反而增加“先通知成功才能做事”的排队。

若某项业务的原授权明确要求“事前通知成功再进行外部动作”，则按该条件执行并验证真实回执。这是原业务约束，不是给所有聊天强加的统一步骤。任何实际需要原生审批的动作，仍必须等待审批，不能由进度通知取代。

<a id="section-10"></a>
## 十、通道能力与媒体体验

### 10.1 内部能力描述

建议在现有通道实现之上增加一个受控的 capability descriptor，而不是独立桥接服务。有效能力按以下条件取交集：

```text
有效能力 = 当前适配器实现 ∩ 供应商/账号实测能力 ∩ 当前授权 ∩ 当前会话可用条件
```

描述项建议包含文本长度单位、单条限制、附件类型／大小、能否原位编辑、能否显示输入状态、能否原生引用回复、能否核对发送结果、限流维度、错误类型、接收证明层级。所有 unknown 必须保留，不自动变 true。

### 10.2 能力展示与降级规则

| 内容 | 面板 | 外部通道 |
|---|---|---|
| 普通文字 | 安全 Markdown、原线程 | 按通道文本规则分段 |
| 阶段进展 | 版本化原位更新 | 支持编辑且已实现时编辑；否则合并重要阶段 |
| 任务卡 | 展示真实 work 与状态 | 可用卡片或清楚的文本摘要 |
| 引用原消息 | 原消息定位 | 有原生引用映射则使用，否则文本标识，不伪装原生引用 |
| 附件 | 授权后预览／下载 | 原收件目标获独立分享许可才发送 |
| 语音 | 明确音频与转写来源 | 没有实际转写就提示缺失，不假装已识别 |
| 审批按钮 | 当前系统允许的范围评审入口 | 仅正确导航，不授予原生 Dot 权限 |

这是目标策略，不表示当前微信／Telegram 已实现表中所有可选能力。尤其 `typing`、原生卡片编辑、音频解析等必须由适配器测试证明后才启用。

### 10.3 多端一致不等于每端逐条镜像

规范消息仍只有一份。每个目标端记录 delivery 与来源映射，收到镜像不能再次作为用户输入。中间反馈允许按通道合并；最终正文及必要限制条件必须保持语义完整，不能只把“成功”同步出去、把失败项留在面板。

当前 `ChannelRouter` 已处理旧微信 source-reply 路径与新全量镜像路径的去重兼容。抽取适配接口时必须保留这一单一投递所有者，不让两个 worker 各发一份。[B10]

### 10.4 附件从“技术传输”变成“可操作成果”

建议在原结果下提供文件清单：名称、类型、大小、来源工作、内容摘要、可预览性、保留期限、各端分享状态。用户无需从正文里复制 artifact ID 或私有文件路径。

分享按钮打开**当前确定文件集合**的审阅：具体文件、具体联系人／通道、具体项目／线程、到期方式。一次明确确认可产生多份逐文件许可记录，但许可仍绑定实际版本与摘要；后续新增文件不自动加入批准集合。[B11]

只有元数据镜像批准时，外部端显示“有文件，可到面板查看／批准分享”，不直接发送文件内容。文件读取权限、缓存可读、外发分享权限不是同一件事。

### 10.5 有界媒体通路

```text
实际字节来源
  → 原产物身份 / 内容摘要
  → 授权暂存或原产物引用
  → 有界分块 / 分段读取
  → 完整性校验
  → 当前目标分享复核
  → 通道上传
  → 通道消息发送
  → 分别保存上传与发送证据
```

借鉴分块与资源限制思想，不照抄某个项目的固定容量或把整个 Base64 放入模型上下文。[E05、E06] 同时避免以下错误：

- 把另一个执行环境的 `sandbox:` 或本地路径当成服务端已收到字节。
- 上传成功就显示“文件已送达”。
- 文件内容过期后重新执行任务来再造同名文件，而不说明原内容已不可用。
- 将允许一次外发扩展成所有后续产物自动外发。
- 缓存命中后跳过当前主体、绑定、项目与分享授权校验。

### 10.6 文件重试与文本重试不能混成一类

传输一个还未产生外部副作用的分块，可以在原上传会话内按已确认 offset 继续；最终发送请求超时可能已经送出，必须进入原发送回执核对。不得因为文件可重新上传，就推导文件消息也可以重新发。

<a id="section-11"></a>
## 十一、性能、并发与上下文成本

### 11.1 先拆分延迟，不用“Dot 慢”解释所有等待

建议把一次交互拆成以下观察点。并非每条消息都会经历执行步骤。

| 观察点 | 实际含义 | 测量来源 |
|---|---|---|
| T0 | 用户提交输入 | 浏览器本地单调时钟 |
| T1 | 输入已在 Hub 提交 | 服务端事务提交记录 |
| T2 | 原消息事件开始投递 | 事件投递记录 |
| T3 | 宿主回调接受事件 | HTTP／业务回执，非模型读取 |
| T4 | Dot 显式收件或实际回复 | dot ack／消息回执 |
| T5 | 原工作被合法领取 | work 的当前 attempt/fence |
| T6 | 原操作实际开始 | Agent 操作记录 |
| T7 | 原操作获得终态 | 原 operation journal |
| T8 | 最终回复写入 Hub | publication receipt |
| T9 | 某个外部通道接受结果 | 该通道分项回执 |
| T10 | 客户端确认展示／已读 | 只有确实具备该回执时才记录 |

浏览器气泡延迟、Hub 保存耗时、事件队列等待、宿主消费等待、执行等待和外发耗时分别统计。不能将 T3 当成 T4，不能假设 T10 总是存在。跨机器时间戳带来源和观测时间；优先统计同一进程的单调耗时，时钟偏差未知时不做精确跨机相减。

### 11.2 后端：批量读取，但不批量跳过授权

优先对 `DotRelay.receipts()` 设计内部批量版本，按本次可见消息集合一次取得收件记录、最近回复、关联工作与订阅摘要。复用 `TaskLiveness.work_summary()` 已有聚合，而不是再查询全部操作日志。[B04、B05]

实施约束：

- 仍由当前主体得到可见消息集合；不能先查全空间再仅由前端过滤。
- 只在一次请求中复用相同 room、Dot、绑定和授权版本的核验结果；不得用跨请求长期缓存维持已撤销权限。
- 批量上限继续受当前同步预算约束。查询数量随集合种类增长，而不是随“每消息×每收件人”重复增长。
- 保留多收件人、部分项目不可见、过期绑定、撤权中、缺旧数据等保守结果。
- 使用真实查询计数及查询计划判断收益。读事务不得跨网络等待，不能为减少 SQL 将阻塞网络放进 SQLite 事务。

建议先实现相同输入下的新旧结果对照，确认状态语义与权限过滤一致后再切换。批量实现出现不一致时回退旧路径并记录脱敏差异，不能以“性能优化”为由删除安全校验。

### 11.3 前端：减少无变化时的工作

现有工作区已经保留对话 DOM、输入框和惰性详情，不需要为了“丝滑”重写为另一套框架。[B13、B14] 增量分为三步：

1. **按版本判断数据变化。** 消息以 ID＋version、连接以绑定／订阅版本、任务以真实状态及证据版本识别变化。纯服务端时间变化不触发全部正文重建。
2. **只更新受影响的视图。** 输入、导航、正文、回执、任务卡、连接表单使用各自 dirty set；未打开的管理面板不重复构造完整模板。
3. **把必要计算合并到一帧。** 同一轮同步的相邻 UI 通知合并处理；避免读布局→写布局→再次读布局的循环，保留选区与滚动锚点。

轮询仍采用现有活动／空闲／错误退避策略作为兼容基础，而非直接改成更高频。只有数据证明需要更低延迟时，才评审增量推送；浏览器自己的只读推送与原生 MCP Events 的宿主投递是不同协议，不能混淆。[B13、E14]

### 11.4 精简消费上下文，减少工具往返

当前 inbox 已返回下一步参数、线程读取、工作收件与恢复入口。应保留其原授权语义，增加可选的**有界上下文读取包**，而不是让 Dot 每次重读全部接入说明。[B03]

建议读取包按当前请求返回：未处理输入摘要、显式请求的原线程片段、原在途工作摘要、待核对的投递引用，以及各集合各自的继续位置。首次返回完整能力说明；后续能力版本未变时只返回版本与必要差异。协议关键的安全边界不能因压缩而消失。

该读取包必须：

- 只读，不顺带 acknowledge、claim、heartbeat、创建任务或修复订阅。
- 共享总字节预算，同时保留每一集合的分页，不能“工作列表挤掉了输入列表”却不告知截断。
- 支持结果为空但仍有下一页的权限过滤场景；不以本页空白推断全量无待办。
- 线程正文按需读取，不将原生 Dot 私聊或其他项目的历史作为自动上下文。
- 不以省调用为名合并需要不同授权的写操作；处理结果仍用明确、幂等的动作提交。

### 11.5 并发：沿用现有分层调度

当前 Agent 已有文件、执行、远程通道，以及项目公平、路径资源锁和资源压力调节；Hub 则承担持久准入。排队窗口扩大不等于实际并发扩大。[B12]

本稿建议：

| 等待类型 | 优化方式 | 必须保留 |
|---|---|---|
| 原话题前序消息尚未保存 | 同话题保持因果顺序；独立话题不连带阻塞 | 原 client_message_id 与线程关联 |
| Dot 宿主尚未消费 | 合并合理唤醒、展示最近真实回执 | 宿主能力和配额边界 |
| 文件／执行资源不足 | 现有公平调度、控制／读取余量 | 节点真实容量、项目上限 |
| 同一路径写入冲突 | 先等待资源锁，再占执行名额 | 未知写入仍保留冲突保护 |
| 某个 IM 通道限流 | 独立冷却与队列，其他端继续 | 供应商限流与原发送顺序 |
| 某个通道结果未知 | 只阻塞其有因果依赖的后续项 | 不重复外发，不影响原业务完成事实 |

查询和取消不能因为大量普通工作排队而完全失去入口，但也必须有界，不能给“控制请求”无限绕过额度的权利。不得自动将原 Dot 的任务交给另一 Dot、另一 grant 或另一项目来提高吞吐。

### 11.6 不根据一个 semaphore 直接调高并发

`EventService` 中的网络 semaphore 是量测对象，不是已证实瓶颈。[B07] 只有当事件排队时间显著、回调端没有限流、Hub 资源健康且公平性可保持时，才评审容量与分组策略。优先隔离慢目标、设置有界超时，防止单一目标占据所有机会；不以多发通知代替真实消费。

### 11.7 成本与收益记录

性能报告同时记录：SQL 数量、响应字节、工具调用次数、有效事件与重复唤醒数、DOM 更新量、主线程长任务、实际队列等待。没有宿主提供的可信用量时，不把字节数估算成精确 token 账单；如展示估算，明确估算方法与误差，不承诺因此节约多少费用。

<a id="section-12"></a>
## 十二、事件、恢复与持久化边界

### 12.1 事件只负责提醒，事实留在持久记录

官方 MCP Events 文档明确：接收回调与异步处理不同，客户端需要处理乱序和幂等；目前 ChatGPT 集成采用 webhook，并非草案中的所有投递及控制消息都受支持。[E14]

CodePier 继续通过事件传递授权对象的引用；Dot 从原 inbox／recovery 读取当前事实。事件成功不把输入设为已读，事件丢失也不删除已经保存的业务记录。

**必须区分两种重复：** 同一个 webhook 的网络重试保留原 event ID，并按协议重新生成有效签名；一次独立、有界的恢复提醒可以使用新的事件 ID，但它仍引用同一条原消息／工作，不能成为第二次业务意图。恢复提醒受原授权、暂停、永久拒绝和频率预算限制。[B04、B05、E14]

### 12.2 订阅生命周期

保持当前宿主提供回调与签名材料、原生确认、原范围续订及 checkpoint 的流程。暂停不能被自动续订解除，撤权后不得继续投递；单次 410／413 等永久拒绝不应被无限重试。[B07、E14]

需要修正一个过度概括：**官方协议允许请求 `ttlMs: null` 并由服务端决定是否授予无固定到期；不能把“原生订阅必须永远固定 24 小时”当作普遍规则。** 但协议允许不等于当前 CodePier、当前宿主、当前账号组合已支持并启用。P0 保留当前有效期和续订策略，P2 再对同范围的长期订阅进行能力协商、撤销验证和实际恢复测试。[E14]

长期通道授权、长期订阅和工作租约是三个独立概念。即使未来采用长期订阅，也不能无限延长工作、自动复活失效 grant 或伪造消费者心跳。

### 12.3 不同位置的数据有不同恢复保证

| 数据位置 | 可以保证什么 | 不能保证什么 |
|---|---|---|
| 浏览器尚未提交的内存意图 | 当前页面存活且原状态未清除时继续核对／发送 | 关闭、刷新、浏览器崩溃后仍存在 |
| Hub 已提交输入／回复 | 当前授权允许时可按原记录补拉 | 外部客户端已读 |
| Agent 已持久化 operation | 在原执行器和日志恢复协议内核对原操作 | 仅凭节点在线断言操作成功 |
| 外部宿主实际集成的持久发件箱 | 在其存储与恢复实现经验证后补投原正文 | CodePier 单方面证明宿主已经集成 |
| 尚未到 Hub、宿主也未保存的回复 | 如实报告缺少内容 | 凭空恢复原答复或拉取私人聊天 |
| 外部通道已开始发送但无回执 | 保留 unknown 并核对 | 无条件安全重发 |

仓库中的 `shared/dot_outbox.py` 是可选参考适配器，测试也明确使用合成宿主回调。它不是“安装 CodePier 后所有 Dot 自动具备持久回复队列”的证据。[B06]

### 12.4 原回复恢复顺序

```text
保留完整原正文、身份与请求键
  → 查询原回执
  → 已提交且摘要匹配：关联原消息，不再发送
  → 权威确认未提交：当前授权仍有效时，发送同一原请求
  → 查询未知／摘要冲突／授权失效：保留待核对，不发送
```

即使一次查询确认未提交，后续发送也必须使用原幂等键以处理并发竞争。与内部幂等接口不同，外部供应商可能没有同等强度的幂等／查询能力，因此不能宣传跨所有系统的“恰好一次”保证。

### 12.5 局部恢复，不连带重启业务

借鉴 dotlink 的错误分类，但把恢复半径限制在故障对象。[E09] 临时网络故障只重建对应连接／发送会话；某个通道失效不重启其他通道，也不终止原工作。无效凭据、权限拒绝、绑定变化进入明确的需要处理状态，不作为瞬时错误不断重试。

恢复只读取 checkpoint 和原 journal；已经运行的进程按原有有界执行、停止与回执协议处理。不能因为 UI 显示“正在重新连接”就在后台启动第二条相同命令。

### 12.6 可选浏览器持久待发：P2，非默认

后续确有跨刷新恢复需求时，可评审显式开启的浏览器持久待发机制。默认仍保留现有仅内存策略，避免将项目正文长期留在共享设备。[B13、B15]

候选方案只保存用户**已经明确点击发送**的原意图，不默认保存全部输入过程。记录绑定当前用户、空间、会话、授权世代和原键；退出、撤权、切换账号时隔离或清除，设置容量与保留期，允许用户查看并清理。恢复后先核对原提交，不直接重发。

浏览器侧加密不能被宣传为能够抵御同源脚本被攻破；XSS、防跨账号泄露和共享设备风险须独立评审。既有用户不得因升级而自动开启正文持久化。

### 12.7 恢复提示不制造新的“待确认”负担

可自动且安全核对的事项由系统核对，只在原对象真实阻塞时要求用户。不同情况明确写成“需补充资料”“需原生授权”“需重新验证联系人”“原发送结果未知”，不全部堆入笼统待确认列表。用户明确选择“我已收到”只能增加人工证据，不能伪装为供应商回执或已读证明。

<a id="section-13"></a>
## 十三、界面与动效设计

### 13.1 保留一个工作区，不增加模式

当前主要导航已经是“对话、任务与结果、连接”，监控与异常位于次级入口。[B14] 延续这个结构，把新能力嵌入现有位置，不新增“传输中心”“消费中心”“处理账本”等用户需要学习的页面。

```text
┌ 房间列表 ┬ MCP / 当前环境                 对话  任务与结果  连接 ┐
│ 房间 A   │ Dot：可接收消息       连接详情                          │
│ 房间 B   ├───────────────────────────────────────────────────────┤
│          │ 你：检查流程，先写方案                                │
│          │ 你：不要修改代码                                     │
│          │                                                   │
│          │ Dot：方案正文……                                    │
│          │ 已回应上面 2 条输入 · 查看来源                        │
│          │                                                   │
│          │ [真实任务进度，存在工作时才显示]                       │
│          │ 已完成检查 · 最终说明已保存 · 微信回执待核对            │
│          ├───────────────────────────────────────────────────────┤
│          │ 给原 Dot 发消息……                       附件    发送   │
└──────────┴───────────────────────────────────────────────────────┘
```

主对话保持阅读连续；详细传输记录在消息详情中展开。普通输入不被迫附带任务表单，任务结果也不与原对话断开。

### 13.2 视觉层级

第一层是用户与 Dot 的正文，第二层是真实进度和需要用户处理的事项，第三层是时间、来源、分端回执和技术详情。降低重复边框、卡片嵌套与状态标签数量；同一结果不要在聊天、右栏、顶部浮条同时重复一整份。

“需要授权”应比普通等待明显；“已保存但微信待核对”不能被画成整个任务失败。颜色只作辅助，状态必须能通过文字与图标区分。主题沿用现有设计令牌，不复制第三方品牌或素材。

### 13.3 输入与阅读稳定性

- 输入框、草稿、选区和输入法组合过程保持同一个实例。收到消息、切换详情、状态同步不能清空正在输入的内容。
- 上翻阅读时保留顶部可见消息与相对偏移；新消息以“有新回复”入口提示，不强制滚到底部。
- 更新同一条阶段回复时保留代码块横向位置、展开状态和用户文本选择；确需延后正文更新时，先更新轻量状态提示。
- 从任务卡返回原消息后，用户可以继续回到先前阅读位置，不把整个房间重置到最新。
- 未读、待处理和失败是不同计数。当前“已加载消息”计数不能冒充全部项目或全部房间统计；新增全量摘要必须有独立、正确授权的查询。[B13、B14]

### 13.4 动效规范：仅解释已发生的变化

以下为拟议设计参数，需在真实页面验证后调优，不是当前测量结果。

| 交互 | 建议方式 | 禁止做法 |
|---|---|---|
| 新本地气泡 | 120–160 ms 的轻量透明度／小位移 | 等待服务端才显示输入 |
| 详情展开 | 160–200 ms，保持布局锚点 | 整页闪白或销毁对话 |
| 状态改变 | 约 120 ms 的局部过渡 | 多处同时闪烁、不断跳动 |
| 阶段回复更新 | 原位更新，必要时短暂弱强调 | 用打字动画伪造逐 token 生成 |
| 网络恢复 | 单一提示恢复到稳定状态 | 每次轮询弹 toast |
| 减少动态效果 | 取消位移和非必要过渡，立即完成状态变化 | 强制弹性动画或持续脉冲 |

主要动画只采用不会反复触发布局计算的属性；不把大面积实时模糊、阴影变化和无限加载动效叠到长列表上。没有新鲜工作证据时，停止“正在思考”式表现，改为最近实际回执与待核对说明。

### 13.5 键盘、移动端与辅助技术

保留中文输入法 `isComposing` 等保护；桌面 Enter 发送与换行操作清楚可见，移动端优先避免误发送。详情层正确设置焦点、返回位置和 `inert`，Escape 不取消原业务任务。适配 320、390、768、1024、1440 像素宽度；关键按钮使用足够触控区域，输入区不被软键盘与安全区遮住。

状态变化使用合适的辅助技术提示频率，不对每次计时刷新反复朗读。错误提示和动作必须能用键盘完整到达；只读权限仍允许阅读和复制已获准内容，不能因输入禁用把整段历史变得不可访问。

### 13.6 接入向导的完成感

完成页应总结“连接到谁、哪个项目、允许什么、结果到哪里、如何撤销”，并直接回原对话。只在实际证明后显示相应完成标记。扫码登录完成但本人私聊尚未核验，显示下一必要步骤，不提前庆祝全链路完成；通知尚未发送时，将它与绑定成功分开显示。

<a id="section-14"></a>
## 十四、数据与接口契约

### 14.1 说明

本节全部新表、新字段和内部接口均为**设计候选**，尚不可当作现有工具调用。实施时优先扩展原服务与版本化契约，避免将既有公开动作改名或删除旧兼容入口。

### 14.2 逐输入处理附加记录

建议新增 `dot_message_handling`，与现有 `collaboration_dot_messages` 一对一关联。

| 字段 | 用途与约束 |
|---|---|
| `dot_id, message_id` | 复合主键；必须对应现有收件关系 |
| `source_version, source_digest` | 处理决定针对的原输入版本和摘要 |
| `handling_state, reason_code` | 有限枚举；不能由任意前端字符串改变任务状态 |
| `revision` | 比较并交换，拒绝迟到覆盖 |
| `reply_id, reply_version` | 真实规范回复引用，可空；不得指向其他 Dot／线程 |
| `work_item_id` | 已有 work 的引用，可空；本表不创建工作 |
| `evidence_source, actor_ref` | 明确是当前消费者、历史兼容结果或用户明确动作 |
| `observed_at, updated_at` | 真实处理／提交时间；迁移时不补造历史联系时间 |

不添加独立执行租约、独立任务 attempts 或新的授权 token。现有工作领取系统仍是唯一执行控制面。

合并覆盖建议单独保存 `dot_message_coverage`，记录每条原输入版本到最终回复版本的直接关系，使用唯一约束防止相同关系重复写入。保留处理 revision 的审计历史，禁止覆盖链和跨线程覆盖。历史回复若未来允许修订或删除，必须使原覆盖证据失效或进入待核对，不能继续引用已不存在的最终内容。

### 14.3 原子提交顺序

```text
开启短事务
  1. 刷新当前授权、绑定、世代和原输入可见性
  2. 核对幂等键、正文摘要、原版本和 handling revision
  3. 保存实际最终回复或验证既有最终回复
  4. 写入逐输入处理决定与直接覆盖关系
  5. 仅对满足契约的输入更新旧 handled 兼容字段
  6. 记录原 publication receipt、审计及已有通道投递项
提交事务
事务外执行网络投递
```

任一步冲突，整次处理决定回滚；不得只将输入标为已处理而没有回复证据。`waiting_input` 的提问、`waiting_authorization` 的说明不是最终解决，因此不能因它们写入了一条文字就自动关闭所有原输入。

若扩展现有回复动作的原子能力风险较高，可先提交最终回复，再以其不可变 ID／版本幂等提交覆盖关系；失败时仅重试覆盖记录，不重新生成回答。该兼容路径必须在 UI 区分“回复已保存，输入处理关系待补齐”。

### 14.4 体验投影返回示例

以下 JSON 仅说明目标形状；标识均为合成示例。

```json
{
  "schema_version": 1,
  "read_only": true,
  "message_id": "example-input-01",
  "projection_revision": "opaque-version",
  "primary_state": "result_saved_channel_uncertain",
  "consumption": {"state": "observed", "observed_at": null},
  "handling": {"state": "reply_committed", "reply_id": "example-reply-01"},
  "execution": {"state": "not_applicable"},
  "publication": {"state": "committed", "receipt_ref": "example-receipt-01"},
  "channel_deliveries": [
    {"channel": "weixin", "state": "unknown", "read_verified": false}
  ],
  "evidence_source": "durable_receipts",
  "next_action": {
    "kind": "inspect_original_receipt",
    "target_ref": "example-delivery-01",
    "mutates": false
  }
}
```

`observed_at: null` 表示缺少可用时间，不用当前查询时间填充。示例的 execution 不适用，不能展示工作成功。投影版本仅用于减少重算，不能作为新的授权凭证。

### 14.5 接口分层

| 层 | 处理方式 |
|---|---|
| 原 `dot_message`／`dot_update` | 保持原作者、最终态、原版本和幂等约束；新覆盖能力使用显式版本协商 |
| 原 inbox／recovery／receipt | 保持只读与原继续位置；可添加可选处理摘要 |
| 有界上下文读取包 | 复用已有精确读取函数与总预算；不形成具有隐式动作的“万能工具” |
| UI 下一步动作 | 只返回受控动作与原对象引用；真正变更仍走原校验入口 |
| 通道适配 | 内部类型化接口，绑定当前 capability descriptor 与独立回执 |
| 旧公开工具与缓存目录 | 保持原权限和语义；新目录通过宿主正规刷新发现，不静默升级旧通知消费者 |

不同集合的分页位置分别绑定主体、范围、版本及查询条件。普通数据库自增序号不能直接成为可跨房间复用的读取凭据；空页也必须正确传递后续位置与截断说明。

### 14.6 数据量与清理

处理记录与消息生命周期关联；审计和未确认外发不得被“清理已读”删除。覆盖关系可以压缩索引与冷数据，但不能留下无法核验的假引用。新增索引前量测实际查询计划及写入成本；没有证据时不把全部正文复制到新的物化投影表。

默认不新增长期保存私聊正文、原生审批内容、完整 callback URL、密钥或二维码的表。诊断所需的有限来源与错误代码优先使用现有审计记录。

<a id="section-15"></a>
## 十五、诊断与可观测性

### 15.1 面向用户的五层诊断

借鉴 wechat2dot 的 doctor 与分层验收，把“连接失败”拆成可定位的检查；检查本身不自动接入真实账号或执行任务。[E11]

| 层 | 核对对象 | 用户看到的结果 |
|---|---|---|
| 1. 账号与范围 | 当前登录、项目映射、绑定版本、本人授权 | 当前能做什么，是否需重新核验 |
| 2. 通道 | 微信／Telegram 开关、凭据世代、供应商错误 | 哪一端不可用，是否需要更新凭据 |
| 3. 宿主订阅 | 原订阅范围、期限、最近回调结果 | 可通知／待确认／暂停／需续订 |
| 4. 消费与工作 | 原 inbox、实际 ack、work、operation | 未接收／处理中／原结果待核对 |
| 5. 回复与外发 | 原 publication receipt、分端 outbox | 已保存／某端未知／待分享批准 |

默认入口为只读，不为诊断自动生成新订阅、测试消息、本人授权或任务。需要主动测试时必须明确显示测试对象与副作用，复用已获准的业务通路，不用伪造“ping 通过”证明模型可自主执行。

### 15.2 用户提示包含三个元素

每项问题只需要“事实＋影响＋下一步”。例如：

> 原回复已保存，微信发送回执暂未确认。面板内容不受影响；请查看这一次发送的回执，不必重新交办任务。

> 当前 Dot 已登记，但还没有有效消息订阅。请在原 Dot 中完成宿主确认；已有项目授权不会因此扩大。

> 此操作仍缺少最新状态证据。正在核对原操作；没有重新执行命令。

最后一句只有系统确实处于核对流程且没有重放时才允许显示，不能作为无条件安抚文案。

### 15.3 诊断导出

提供“复制诊断摘要”而不是“复制全部日志”。内容建议包含版本、错误类别、原对象的脱敏定位、最近有效观察时间、当前恢复阶段与明确未验证项。导出前可预览，用户只能得到当前有权查看的对象。

默认排除正文、私人路径、Token、授权码、签名材料、完整 callback、下载凭据以及其他项目信息。高基数消息 ID 不直接成为全局指标标签；需要按单次调用定位时走受权限保护的 trace，而非把每条正文塞入遥测。

### 15.4 指标与异常提醒

建议指标：输入保存延迟、事件排队与接受延迟、未消费年龄、原操作待核对数、最终回复提交延迟、各端 unknown 比例、每请求查询数、同步响应字节、前端无变化重算次数、接入重复创建率。

指标的对象和分母必须清楚：未消费年龄不是模型思考耗时，外部 accepted 比例不是用户阅读率，“已加载消息”不能作为全部工作数量。无真实宿主用量时不统计伪造在线时长或精确 token 成本。

异常提醒只在状态有意义变化时产生，按原连接／对象合并；重复轮询不反复提醒。订阅即将到期可提示原宿主续订，但不得让监控任务自行扩大过滤器或建立新凭据。

### 16.3 第二阶段：P0-B，完成低风险体验闭环

退出条件：首次接入不重复创建对象；网络恢复不要求重新填写范围；已保存、已回复、工作完成与外发未知不混淆；输入法、滚动与焦点没有回归。

### 16.5 第四阶段：P1-B，阶段卡、通道能力与可操作成果

## 十七、迁移、灰度与回滚

### 17.1 先处理并行基线，不覆盖旧目录

当前默认目录与干净 1.27.4 参考树不同，且存在相关并行工作。本稿仅保存新的设计文件。后续实施必须选定可追踪基线、检查已有未提交修改，再决定增量集成；禁止把参考树直接覆盖到默认目录，也不对未知并行工作执行清理。

### 17.2 加法迁移

新表和可选字段不改变旧枚举含义。缺少历史处理原因的 handled 映射为 `legacy_handled`，不猜测是否回复覆盖；没有原时间就保留 null，不用迁移时间当 Dot 最近联系时间。

旧绑定不因迁移取得本人任务、完整镜像、until_revoked、文件外发或原生长期订阅许可。新 UI 摘要反映旧授权本身；范围扩大必须重新明确批准。[B08、B09、B11]

### 17.3 灰度顺序

| 阶段 | 行为 | 可退出条件 |
|---|---|---|
| 影子投影 | 同时计算新旧结果，只呈现旧结果 | 权限与语义差异已解释，无异常写入 |
| 只读界面灰度 | 启用新状态和详情，不改变处理终态 | 状态误导、性能、辅助技术检查通过 |
| 处理语义灰度 | 对明确支持新协议的消费者启用新处理记录 | 覆盖、幂等、旧客户端兼容测试通过 |
| 通道呈现灰度 | 按具体绑定启用已验证能力 | 无重复外发、拒绝与未知正确分流 |
| 扩大范围 | 最终同一提交验证后扩大 | 回退路径仍可用，关键指标无回归 |

特性开关属于实施与运维控制，不必全部做成用户设置。新功能不能根据一个来自前端的布尔值跳过授权，也不能自动升级 notification-only 消费者为执行模式。

### 17.4 回滚原则

只读投影可以关闭并回退旧显示；原消息、回执、操作、审计和通道投递项继续保留。涉及新处理语义时，旧客户端可读不等于旧写入器可以无损理解新记录；回滚前验证旧写路径，必要时暂停该新语义入口，而不是丢弃新关系。

**不能用恢复旧数据库快照作为一般 UI 回滚方式。** 快照可能缺少已经产生外部副作用的回执，从而使旧任务或外发再次执行。数据库事故恢复必须有原 journal、未知外发隔离和专门核对，不允许“回到昨天再跑一次”。

### 17.5 保留与清理

未确认发送正文、未知操作证据、版本冲突及覆盖来源不得在灰度结束时自动删除。已确认记录按现有保留与审计政策清理，新的索引和派生缓存可以重建，但原事实不可用缓存覆盖。

只有服务端事实确实更新才失效相关投影；权限、绑定、账号或 scope 改变时则立即使旧敏感缓存不可用于展示和动作。旧页面迟到响应不能把原空间内容写入新空间。

### 18.3 初始性能目标

以下是**提议的验收目标，而不是本轮实测结果或对公网服务的 SLA 承诺**。正式采用前需固定测试设备、浏览器、数据库样本、网络条件与并发负载。

| 指标 | 初始目标 | 测试口径 |
|---|---|---|
| 点击发送到本地气泡可见 | p95 ≤ 100 ms | 不等待网络；主线程含长对话样本 |
| 已加载详情之间切换 | p95 ≤ 100 ms 出现可交互状态 | 复用原 DOM，不等待非必要查询 |
| 隔离环境的输入持久化接口 | p95 ≤ 300 ms | 指定硬件与局域测试条件，含真实授权与事务 |
| 无变化同步的大块 DOM 替换 | 0 | 正文、输入框、活动表单不重建 |
| 单条更新的渲染范围 | 仅相关正文／回执／摘要 | 不按房间全量重算全部消息 |
| 回执 SQL 数量 | 相对固定基线显著减少，给出实数 | 分别测试 1／24／100 条和多收件人 |
| 消息／任务错路由、授权泄露、重复副作用 | 0 个可接受缺陷 | 属于发布阻断项，不用平均数抵消 |
| Dot 原生响应与公网外发 | 记录分位数，不承诺固定秒数 | 分离宿主、供应商与 CodePier 自身耗时 |

UI 与后端的绝对时间目标若在目标设备达不到，应基于数据调整设计或说明边界，不能通过删除授权校验或缩小样本伪造通过。

### 18.4 性能样本与对比方法

建议使用固定规模的短／长正文、代码块、表格、1000 条历史消息和若干在途工作；分别测 1、5、20 个并发会话的隔离样本。结果包含预热规则、请求数量、错误率、分位数、内存变化及比较提交。事件与供应商网络可以受控模拟，但必须明确此时没有测试真实平台延迟。

每个性能报告绑定最终集成提交及配置。新旧实现使用相同数据与权限场景；至少记录足够样本以避免单次偶然值，默认建议每个稳定接口场景不少于 1000 次请求。重负载安全上限按实际设备设置，不为达标把测试机运行到失去控制。

### 18.5 真实宿主与真实账号门槛

在用户明确批准的原账号／原连接范围内，分别验证：一次实际消息收到并回复、连续补充的覆盖、原生审批的真实导航、断连后的原消息恢复、每个端的实际收件、文件分享及撤权后的停止行为。只进行获准的测试，不因本稿自动创建机器人、订阅、凭据或发送消息。

没有完成某层验收时，在发布说明与能力描述中明确列为未验证；不能用现有测试文件名、历史 CI 或模拟消费者替代。针对持久宿主 outbox 的保证，必须有宿主真实安装与重启恢复证据。

### 19.2 主要风险

**状态过度抽象。** 一个漂亮主状态可能隐藏不同失败。缓解方式是保留证据详情、来源时间与原对象，主状态只做排序，不覆盖事实。

**模型未遵守处理契约。** 服务端能验证身份、引用、版本和事务，不能自动证明一份回答语义完整。覆盖属于消费者明确申报，不标为自动质量验收；用户可以沿原输入指出遗漏，后续输入保持新意图与审计。

**兼容导致终态冲突。** 旧 handled 可能来自转任务或普通回复，不能在迁移时全部当成最终回答。新旧写入并存必须使用明确兼容规则、版本检查及灰度。

**简化同意造成范围误解。** 一次界面操作不等于取消独立目的；冻结摘要、差异评审、实际本人证明和撤销入口必须保留。默认展开的信息应足够让用户理解授权，不把关键范围藏进低可发现性的链接。

**性能优化削弱权限。** 批量查询、缓存、推送与客户端持久化都可能泄露旧范围。当前权限优先，scope／generation 变化使缓存失效；性能优化不得以“用户之前看过”为授权依据。

**供应商和宿主变化。** README、主分支协议及官方平台能力会变化。实施前重新核验所依赖接口并固定兼容版本；不要把本稿日期的能力永久写死为平台事实。[E01–E14]

### 19.3 第三方代码与许可

本稿主要吸收设计思想，不引入第三方源码或依赖。后续实际复制代码时，按所取文件和固定提交检查许可证、版权通知与依赖要求；不能用 CodePier 自身的许可证推断所有候选代码的许可要求。特别是 codex-bridge 仓库标注 Apache-2.0，应单独保留对应义务；其他项目也以实际取得版本为准。[B01、E10]

### 19.4 仍需验证但不阻止 P0 的事项

真实 Dot 是否支持所需持久发送适配、原生审批是否提供可定位请求引用、当前账号是否支持长期订阅、各通道原位编辑是否满足实际业务、实际性能瓶颈排序，均需定向验证。P0 可采用原协议、普通文本、有限订阅与只读诊断先完成，不以这些未知事项作为重新询问用户或无限延迟交付的理由。

### 20.2 产品完成定义

用户可以在同一入口完成接入、连续交办和看结果；每条输入有可解释的去向；普通聊天不产生多余任务卡；长任务的状态来自真实证据；需要用户时动作明确且最少；断线后沿原记录恢复；某端失败不会重复整个工作；多端差异有清楚降级；所有简化都没有扩大旧权限。

“页面更漂亮”“有更多设置”“测试文件存在”“插件目录能列出来”“回调返回 2xx”均不单独构成完成。

### 20.3 本轮设计交付的边界

本稿交付的是一份可据以评审、拆分实施和验收的设计，包含已核验基线、吸收／不吸收决定、流程、状态、数据契约、性能候选、代码落点、灰度与测试计划。本轮不运行业务测试、不改业务源码、不迁移数据库、不改变真实接入或授权、不提交推送发布。

这条路线的关键不是把多个桥接项目拼起来，而是**让 CodePier 已经具备的可靠性真正呈现为更少的操作、更清楚的反馈和更连续的对话**。
