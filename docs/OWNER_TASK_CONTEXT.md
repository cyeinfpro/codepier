# 本人任务上下文与原渠道澄清

## 目标：原处交办，原处继续

已接入并获得有效任务同意的双向 dot，应直接处理房主在面板、已验证本人微信或 Telegram 私聊中的明确请求。日常任务不因为要读取项目、调用插件或从聊天转成工作而多问一次“是否确认”。面板仍然是一个对话入口，不新增聊天／任务模式开关。

本功能修复的是请求上下文、方案与本人回复的关联，不是取消宿主审批。文件及命令通过 CodePier 项目 Agent 或已批准 VPS 执行，不是宿主桌面控制。不能因为项目名是电脑名称，就要求打开另一套桌面访问权限。

## 两条正常路径

要求清楚、原权限足够时：

```text
本人：检查 README 并修正文档中的拼写错误。
dot：读取当前本人请求和相关上下文 → 使用原 task_request → 实际处理 → 原话题回报。
```

只有关键要求确实不清，或方案确实需要本人决定时，才使用精确问题记录：

```text
本人：都验证一下，先说明测试范围。
dot：仅创建独立测试文件、读回并运行只读命令，不修改业务代码。按此范围继续吗？
本人：可以。
dot：核验这条回复对应的原方案 → 继续同一份工作 → 原处回报实际结果。
```

单个、仍处于当前话题的待澄清事项可以使用简短肯定／否定回复。多个事项同时等待、已经切换话题、方案失效或指代不明确时，不猜测“可以”对应哪一项。面板可点击“回复这个问题”；私聊可使用问题自带的“确认 编号”或“取消 编号”。编号只帮助定位，不是授权令牌。

普通新请求不需要编号。任务结束后的新要求仍是新请求，不因为回复了旧话题而强行并入旧任务。谢谢等礼貌回复不会撤销此前的否定决定。

## 消费者契约

每次 `dot_inbox` 都返回一份轻量 `task_context_protocol`，与首次接入配置使用同一契约。已有消费者可以在读取原待办时看到新的上下文与精确问题用法，不需要重新加入、重置 checkpoint 或更换凭据。契约每页只出现一次，不把完整接入长说明重复到每条消息中；暂停任务策略时也可只读获取，不会恢复执行权限。服务器返回契约不代表真实宿主已经采用它；旧工具目录仍需原宿主同步。

`collaboration_query(action="dot_inbox")` 的输入项增加：

- `execution_context`：有来源区分的本人原话、助手方案、关联回复和附近的同 dot 上下文；每项有原消息 ID、版本、正文摘要及读取入口。
- `execution_route`：CodePier 实际执行目标和独立宿主审批状态。`not_evaluated` 不是拒绝，也不是批准。
- `response_request_options`：原请求版本、正文摘要及当前范围摘要。只对当前已验证本人请求提供。
- `task_continuation`：精确问题或回复的当前关联状态；不授予新权限。
- `task_blocked_reason`：区分等待补充、回复歧义、方案过期／变化、明确拒绝和已有回复，不能一律要求回 Dot 确认。

`execution_context` 是证据，不是额外授权。助手的建议必须由本人明确采用，不能从引用、附件、外部联系人或其他助手的发言推导同意。原消息和既有 task_request 仍经过服务器的身份、范围、版本和当前权限检查。

仅在确实需要输入时，发送 `dot_message` 或 `dot_message_v2` 的阶段回复：保留原 `reply_to_id`，设 `complete=false`，将当前 `response_request_options` 放入 `response_request`，并选择 `reason=clarification` 或 `plan_confirmation`。可选问题有效期为 60–3600 秒，默认 1800 秒。不得使用 `host_approval` 作为问题类型，也不能将原生审批伪装成这里的方案确认。

如果原任务已创建，原消息不在消息收件箱中，从该任务的 `delegation` 读取当前上下文及 `response_request_options`，不重发原请求、不重新加入。

后续仍用服务器返回的 `task_request`。已关联工作时返回原 delegation；没有工作时从原始本人请求建立唯一工作，不把“可以”当成任务目标。继续原 claim／execute／heartbeat／result 流程。重复事件、重复回复和相同幂等请求不能创建第二份工作或重复操作。

连续多轮澄清沿显式的“原请求 → 问题 → 本人回复”链关联。第二轮及后续补充同样进入原任务上下文；任一仍有效的链上问题未回答、被否定或版本变化，都停止原任务的新步骤。没有问题关系的其他话题不会被并入。明确回复较早的方案时，该方案不受附近消息预览窗口影响，仍保留精确版本与读取入口。

## 版本、身份与范围边界

问题记录绑定原房间、dot、原始本人请求、方案消息、各自版本及正文摘要、来源身份与当前任务范围。范围摘要另外覆盖实际项目根目录、设备、读写执行设置以及委托策略版本，不仅依赖面板展示名称。

同渠道简短回复必须来自当前验证的本人、同账号／联系人／凭据世代，并处于仍明确关联的当前话题。外部平台的创建时间早于问题的迟到消息不能批准后来才提出的方案。跨面板和已验证本人私聊的精确回复可以关联同一房间的指定问题，但不会扩张房间或联系人权限。

同一会话内明确引用已授权的历史项目分区时，沿用现有会话读取规则，保留来源项目及正文出处；完整正文读取请求仍指向原项目，并检查当前读取权限。历史引用不会扩大本次执行项目范围，也不能跨其他会话读取。来源项目撤权后，旧上下文和依赖它的新步骤同样被阻止。

原请求、方案、项目映射、授权或回复发生变化时，旧确认不继续提供新步骤准入。两个同名联系人、不同 bot、不同房间或不再有效的授权不能继承原确认。普通外部消息和旧积压、修改、删除、引用及附件不会因包含“确认”而取得本人身份。

已结束的普通讨论不能被迟到调用重新解释为待执行任务。旧客户端未使用 `response_request` 的阶段回复仍保持原有含义，不被后台自动升级成方案确认。

## 等待、取消和恢复

问题尚未回答或本人否定方案时，任务读取及原操作回执仍可查询，但不领取新尝试、不消耗一次新的工作租约，也不准入后续执行步骤。收件箱返回明确原因，不能把等待当成完成或把排队当成执行成功。

“取消方案”停止该方案的后续步骤，不承诺已经终止先前启动的 OS 进程。存在 pending／unknown 操作时，继续核对原 operation_id；不能通过重领、重复投递或另建任务恢复。需要改变方案时在原渠道明确讨论，旧证据不被抹除。

问题、回复和原工作关联存入现有数据库事务。服务重启不需要新的加入码、凭据或订阅，也不会重置消费基线。新增记录是工作流程信息，不更改原 grant、项目权限、本人通道授权、服务条款同意或外发许可。

## 面板呈现

问题消息显示轻量的原任务关联卡和“回复这个问题”，操作只将焦点与回复对象带回现有输入框。回答后卡片显示已关联、拒绝、过期或待澄清，不显示虚构的执行成功。实际完成仍来自工作和操作回执。

连接页的“继续对话”是选择已有授权接收对象的本地导航，不再被等待中的详情读取或保存请求吞掉；它不会取消原请求、清空原任务状态或绕过接收对象的当前范围检查。手机端可直接回到输入区，迟到的详情响应也不会把页面切回旧位置。

旧的“等待授权”提示改为“授权待核对”。如果只是任务范围或方案补充，在原面板／私聊回复即可；只有实际的宿主原生审批才去宿主处理。旧 `host_approval_required` 字段继续表示独立边界存在，同时提供 `host_approval_requirement_scope`、`host_approval_state` 和 `host_approval_required_this_task`，不再把一个固定布尔值当成每次原生审批的证据。

## 性能与完整性

正常消息页面只在存在服务器生成的问题关联标记时查询这项投影，不为每条历史聊天新增问题状态查询。每条明确问题链最多 16 轮、每份上下文最多 40 个引用、内联正文最多 12 KB；整页输入上下文累计内联正文最多 24 KB。超出预算保留完整读取请求，不裁掉半段正文后假称已经读完。

附近上下文只是有界预览，`history_complete=false`；需要更多内容时继续原话题分页。任务执行前仍核对相关版本和当前状态，不把缓存摘要当作持久授权。

## 验证与上线

`tests/test_owner_task_context.py` 验证直接工作、精确回复、原工作复用、歧义和旧客户端兼容。`tests/test_owner_task_context_chains.py` 验证较早方案的明确采用、多轮限制传递及同任务复用。`tests/test_owner_task_context_boundaries.py` 覆盖身份／版本／目录映射、迟到消息、取消、领取前准入、微信／Telegram、读取预算和权限不变。`tests/test_owner_task_context_flow.py` 使用真实隔离 Hub、Agent 与 Chromium／WebKit，验证原处回复、服务重启、同任务去重、真实读写和命令回执，以及下一个明确任务不增加确认。

这些测试中的 dot 是明确标注的测试消费者，不代表真实模型已经理解新契约，也不代表真实微信／Telegram平台投递或宿主审批已经完成验收。应分别记录代码回归、真实隔离浏览器／Agent、生产部署及真实宿主消费者验证。

上线需要批准后的 Hub 更新和工具目录同步。新字段未出现在宿主目录时，应使用原宿主的 Rescan 发现它们，并在原连接范围内读取、保存新的消费者说明；不要创建新高权限连接来解决目录缓存。已有通知模式不能因此升级为执行模式。CodePier 不能代替宿主记录原生批准，也不能保证所有高风险动作不再需要确认。
