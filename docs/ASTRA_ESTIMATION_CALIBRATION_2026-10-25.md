# 6astra 实际调用与 CodePier 估算校准分析（2026-10-25）

## 结论

采用“调用分轮 + 真实样本的每轮先验 + 滚动上下文”的估算方案，优先建立经验次数基线，再校准新旧输入与缓存。简单基线的默认 95% 缓存假设暂时保留。只使用 Sub2API 的 total_cost 标价 USD；不纳入用户、分组或账号倍率。

本次完成香港 Sub2API PostgreSQL 只读核查、现有估算源码检查、时间留出样本对比，并保存脱敏聚合快照与可重复运行的 SQL。随后已在本地实现调用经验估算，尚未发布或部署。

## 已实现的本地版本

`shared/call_estimate.py` 提供 `codepier-call-prior-v1`，主卡、趋势及导出统一使用新字段 `call_estimate`。工具调用先归模型轮次；中情景每轮输入取 135,431 与可见历史重放量的较大者，输出取 487 与工具参数加隐藏输出情景的较大者。快速串行调用不再仅凭时间接近合并，轮询仅在目标已知且相同时合并。工具返回在完成后的下一轮消费，临时收尾随新活动重算。

缓存百分比为上限，新消费文本不能被全部按缓存价折扣：C=min(I×p/100,I−F)，N=I−C。参考费用使用所选模型单价对 N、C、O 逐轮计价。历史均价 $0.209832 是校验基线，没有硬编码为当前费用；默认95%假设下一轮普通先验约 $0.2207。中情景旧历史不自然衰减，约240K触发情景压缩。

未新增真实计费 API 接入、对话正文采集或数据库迁移。原工具文本、上下文对照与 actual_usage=null 继续保留；缺少文本时只有独立新字段提供明确标注的次数估算。实现契约见 [mcp-token-usage.md](mcp-token-usage.md)。以下分析中的“当前项目算法”指本次修改前的基线；建议中尚未落地的会话冷启动、effort 分层及真实请求关联继续作为后续验证项。

## 根据调用记录直接估算：本次补充验证与推荐方案

目标是在没有真实 usage 的项目里，利用已有 MCP 调用、时间、窗口和可见文本估算 token 与标价。Sub2API 样本用来训练参考系数，不要求项目先接入真实账单才展示估算。

### A. 先建立可复查的“按次数”基线

前 23 天训练、后 7 天验证，预测时不读取验证期真实 token：

| 训练/验证范围 | 每次输入先验 | 每次输出先验 | 每次历史标价均值 | 后 7 天 token 聚合偏差 | 后 7 天标价聚合偏差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 所有 Codex 类 usage 记录，含全零 token | 133,557.68 | 480.36 | $0.207068 | +3.55% | −4.54% |
| 带 token 的 Codex 类记录 | 135,431.27 | 487.10 | $0.209832 | 约 +4.51% | −3.70% |

第二组训练 23,310 条，验证 8,079 条。仅按调用次数预测费用，分日 WAPE 为 14.02%；分日输入 WAPE 为 6.28%、输出 WAPE 为 11.53%。10月23/24日的费用分别低估约 44.58%/54.63%，说明较小的全期偏差掩盖了缓存与流量构成变化。

另比较按会话序号分成 1、2–5、6–20、21–50、51–100、101+ 的模型：同一验证集费用分日 WAPE 为 13.80%，输入 WAPE 反而升至 9.52%。仅添加“第几次调用”分档，尚不足以证明整体优于简单均值。

部署时可先使用带 token 样本训练的先验，建立独立“经验次数估算”情景：

    R = 根据项目调用分组推断的模型评估次数，含一次可被后续活动替换的临时收尾
    估算输入 = R × 135,431
    估算输出 = R × 487
    估算总 token = R × 135,918
    经验标价估算 = R × $0.209832

例：100 条工具调用，经批量/并行归组后推断为 60 轮，加 1 次临时收尾，则 R=61；经验参考约 829.10 万 token、$12.80。不能直接把 100 次 MCP 调用代入 R。

这里的每次均值来自真实 API 记录。上述验证也使用真实 API 记录数，因此迁移到推断的 R 后还会增加分轮误差；14.02% 不是项目估算的已验证精度。每次历史标价均值包含样本实际档位构成，只适用于该 Astra 样本的经验费用；参考模型或价格档位变化时，应使用 token 桶与对应单价重新计价。

### B. 改进现有上下文估算：分轮 + 经验先验 + 新旧输入分开计价

1. **先分模型轮次。** 同一相关窗口内，可能属于同批生成的并行工具按一轮情景；串行依赖进入下一轮；不同目标的轮询不合并。低/中/高保留不同分组假设。工具调用数仍作为原始观测保留。
2. **用真实分布校准上下文先验。** 窗口起点未知时，使用约 135K/轮的成熟流量先验，不从 12K 起步就假设所有历史可见。明确知道是新会话时再使用启动阶段先验。已知工具历史和经验完整输入不能直接相加，因为完整输入均值已经含有工具内容。
3. **逐轮重放新旧输入。** 定义 F 为本轮新可用工具返回及新增用户文字的估算，H 为重读的系统/历史输入。只在下一次模型评估时消费已结束的工具返回；后续它转入 H。
4. **分别估缓存。** 新文本首次消费按低缓存情景，旧历史按高缓存情景；全体输入统一乘 95% 仅保留作简单基线。新旧拆分模型的 h 需要校准，不直接把本次 95.76% 后续记录占比当成“历史部分命中率”。
5. **独立估算输出。** 只有次数时使用约 487/轮的完整输出先验；有可见参数时，它是完整输出的一部分，应估计剩余不可见输出，避免再把 487 整体加到参数上。effort 可知时再细分。
6. **费用从同一套 token 桶计算。** 普通输入、缓存读取、缓存写入和输出分别计价；不再把工具文本成本和含上下文成本相加。经验每轮均价作为校验基线，与细分模型的计算金额分别标注。

普通档公式：

    普通输入估算 N = F + (1−h) × H
    缓存读取估算 C = h × H
    费用估算 = (10×N + 1×C + 12.5×W + 50×O) / 1,000,000

这里“新增文字缓存低”属于情景假设；F/H 也只是估计，不能标记成真实 usage。W 无依据时保持未知。

例如：本轮估计有 10K 新工具文本、120K 历史重读，历史命中假设 95%。输入标价约为 10K×10/M + 120K×1.45/M = $0.274。若把全部 130K 都按 95% 缓存计价，则是 $0.1885；会漏掉新返回文本首次进入上下文的成本。工具返回越大，这项差异越重要。这是公式示例，不是实测单请求。

### C. 推荐落地顺序与验收

- 第一版：增加上述经验次数情景，修正轮询合并目标，输出 R 的低/中/高和经验 token/费用。无需新增计费 API 对接即可使用。
- 第二版：在现有 replay 中校准上下文保留，分别估计 F/H 与缓存。以经验次数模型为基线，评估是否真正改善；不只扩大 64K 阈值。
- 有可信新会话标记才启用冷启动分档；匿名窗口第一次出现在项目日志中，不等于宿主真正会话起点。
- 费用参考值与其参数版本、来源模型、样本窗口一起输出；输入/输出分开列示，范围称为情景范围。
- 评估按日/会话计算输入、输出和费用 WAPE，另看短会话与大返回场景。真实 API 关联是进一步测量项目误差的验证手段，不是提供经验估算的前置条件。

补充证据：docs/evidence/sub2api-astra-count-validation-2026-10-25.json（含每日、阶段聚合及四种基线的训练/验证结果）。


## 数据范围与口径

- 固定窗口：北京时间 [2026-09-25 15:40, 2026-10-25 15:40)。
- 目标模型：usage_logs.model = gpt-6-astra。
- 全网关共 39,759 条记录；其中 User-Agent 含 codex 的客户端共 31,754 条。
- Codex 类样本用于编程助手场景的参考校准。User-Agent 是客户端声明，不能证明其全部使用 CodePier，也不能把这些费用归属当前项目。
- Codex 类样本 31,389 条带 token，365 条 token 全零。其中 360 条全零记录仍有标价，合计 $3.60；其收费来源未在本次确认，保持单独列示。
- 调用数指 usage_logs 记录数，不代表全部 HTTP 尝试、上游重试数或成功完成数。没有 usage_logs 的失败尝试不在样本内。
- SQL 仅导出数字聚合和固定分类；没有导出 API 密钥、请求正文、原始 session ID、用户 IP 或请求 ID。

**Sub2API 数据库 token 口径：**

普通输入 N = input_tokens；缓存读取 C = cache_read_tokens；缓存写入 W = cache_creation_tokens；输出 O = output_tokens。

完整模型输入 = N + C + W；总 token = N + C + W + O。数据库 input_tokens 已是扣除缓存后的普通输入，不能将其当成完整输入。

在本次样本中，普通档各 token 桶对应每百万 $10 / $1 / $12.50 / $50：

    Standard 标价 = (N × 10 + C × 1 + W × 12.5 + O × 50) / 1,000,000

实测 38 条 priority 记录的各桶单价为 $20 / $2 / $100（无缓存写入），属于档位标价差异；其余带 token 记录与 Standard 单价精确对应。比较真实标价时直接汇总 total_cost，不另加 token 公式计算出的费用。

## 2. 当前项目算法与偏差来源

源码位置：

- shared/token_estimate.py：字符启发式估算；不是模型 tokenizer。
- shared/context_estimate.py：SCENARIOS 和 replay。
- hub/context_usage.py：把重放贡献映射到所选统计区间。
- shared/token_cost.py：参考单价、默认 95% 缓存假设。
- web/token-usage.js：headline 使用 wire_attempts 显示“次调用”。

| 维度 | 当前行为 | 实际证据与调整方向 |
| --- | --- | --- |
| 次数 | 显示 MCP wire_attempts；时间接近/重叠和轮询用于推断模型轮次 | MCP 调用数、推断模型轮次和真实 API 记录数需要分别显示。并行工具、多 agent、无工具回复及宿主重试没有固定换算比例 |
| 上下文 | 中情景底座 12K、64K 压缩触发、近 8 轮保留、旧历史每轮保留 98%；高情景触发 128K | Codex 输入中位数约 130K，P90 约 209K。64K 情景可能过早压缩，高情景也不能代表单请求输入的实测上界 |
| 缓存 | 所有模型输入统一假设 95% 命中 | Codex 加权 95.60%，最近 7 天 94.66%；95% 是较稳妥的现有默认。冷输入与热历史仍应分开建模 |
| 输出 | 工具参数 + 隐藏输出常数（中情景 120），收尾 400 | 带 token 的完整输出均值约 494；low/xhigh/max 的均值约 284/655/711。应校准工具参数之外的残差，不能再把完整输出均值加一遍 |
| 标价 | Standard 短上下文参考价、缓存写入未知 | 单价基本正确。实测档位和缓存写入应在可信 usage 可得时逐请求处理；未知保持未知 |
| 覆盖 | 最多 30 天、10,000 条工具指标，其他宿主流量不可见 | 分开报告 API 关联覆盖、MCP 指标覆盖与历史保留缺失，不把缺失条目填零或乘常数 |

以上能证明“参数与真实请求分布不匹配”，不能直接量化当前 CodePier 整体估算误差。实际 API 轮数与 MCP 轮次尚未关联：高情景可能通过更多推断轮次补偿较小的输入，不应仅凭输入分布断言总金额低估某个固定倍数。

额外的次数校准问题：replay 支持 round_hint / poll_key，但当前 token_dashboard 查询没有给它们提供可信字段。poll_key 缺失时相等的 None 会满足“同目标”判断，因此短时间内不同目标的轮询也可能归入同一推断轮次。应使用服务端派生、权限范围内的轮询目标关联值，缺失时保留不确定性；JSON-RPC request_id 仍不能充当模型轮次 ID。

## 3. 时间留出验证：先保留 95%

前 23 天为观察段，最后 7 天为留出段；仅验证“给定真实 token 后，固定缓存假设的金额表现”。

| Codex 样本 | API 记录数 | 真实标价 | 真实 token + 95% 缓存公式 | 相对偏差 | 改为 96% 的相对偏差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 前 23 天 | 23,637 | $4,894.455778 | $5,145.221480 | +5.12% | −0.68% |
| 后 7 天 | 8,117 | $1,760.747934 | $1,725.002448 | −2.03% | −7.38% |
| 全 30 天 | 31,754 | $6,655.203712 | $6,870.223928 | +3.23% | — |

95% 公式：

    完整输入 × $1.45/M + 实际输出 × $50/M

这项对比忽略写入/档位差异并把写入也纳入固定输入混合价，结果是简化公式的总体偏差；不等于缓存假设本身的纯误差。它更不代表 CodePier 已达到 ±2% 精度，因为这里直接使用了 API 的真实输入/输出和次数。

另做输入规模的敏感性计算：保留真实输出，把每次输入最多按 64K 计算，并使用 95% 缓存，最后 7 天为 $933.655705，较实际标价低 46.97%。这只是说明上下文规模对金额的影响；当前 replay 不是简单硬截 64K，该数字不能标成现有项目实际低估幅度。

## 4. 冷输入与连续历史

对具有 session_id 且完整输入大于零的 Codex 记录，按 API key + session 分组，在窗口内排序：

| 阶段 | 记录数 | 平均完整输入 | 加权缓存读取占比 |
| --- | ---: | ---: | ---: |
| 窗口内首次观察到 | 231 | 32,195.95 | 7.6742% |
| 同组后续记录 | 31,158 | 134,669.12 | 95.7583% |

窗口内首次记录不一定是会话真正首轮。这里只支持“新输入与连续历史缓存行为不同”，不能把 32K 直接定为系统提示底座，也不能把每次工具调用当成冷启动。

中期估价方向：

    输入金额 ≈ 新增且未缓存输入 × $10/M + 可复用历史 × [(1−h)×$10 + h×$1]/M

冷输入、历史保留量、命中率 h 都需要同请求样本校准；重复文本不能证明真实缓存命中。缓存写入用量未知时不推定。

## 5. 建议实施顺序

### P0：次数口径与可验证样本

1. 首页“次调用”改为“MCP 工具调用”；另列“推断模型轮次（含临时收尾）”。真实 API 次数仅在存在可信关联时展示。
2. 独立保留三类数据：已测工具文本、模型上下文情景、来自 Sub2API 的实际标价。三者不能相加成一个更大的费用。
3. 在宿主能提供可信请求关联的场景，建立 API 请求到模型轮次、工具活动与项目的明确映射。Sub2API 服务端提供真实 usage；任意客户端 _meta 不能宣称真实计费。
4. 关联遵循现有项目、actor、grant、Space 权限。API key 名称、时间相近、session_id 都不能单独证明项目归属。
5. 本次 Codex 样本的 upstream_request_id 全为空，session_id 有 31,394 条，但与 CodePier 的匿名 window_key 没有已确认映射。当前不能完成项目级误差校准。

### P1：增加单独的 Codex 编程助手校准情景

1. 保留通用情景；新增显式选择的 coding 配置及版本、来源窗口、样本数。不能通过连接标签擅自认定宿主产品。
2. 用实测单请求输入 P10/P50/P90 ≈ 60K/130K/209K 作为校验目标；这是目标分布，不是固定底座或总量乘数。
3. 在同请求配对数据上比较 128K / 192K / 240K 压缩触发候选、不同底座和历史保留参数，选择能在留出期还原输入分布与费用的组合。不能直接把 130K 作为每轮新增底座。
4. 连续历史不再无条件每轮衰减 2%；由真实重放误差和压缩事件决定是否调整。240K 也只是候选，不是已证明的默认阈值。
5. 输出先保留已测工具参数；使用“实际 output_tokens − 同轮已测参数”的残差拟合隐藏部分、收尾与 effort。output_tokens 已经是输出总桶，不额外重复加 reasoning。
6. 95% 默认暂保留，并以冷/热拆分作为可校准的下一步。不要用全量均值 95.60% 简单四舍五入到 96%。

### P2：验收与长期统计
