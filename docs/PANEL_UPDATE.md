# 面板一键更新

入口：管理员页面顶部的版本按钮。登录后自动检查 GitHub 正式发布；发现可用版本时显示“更新面板至 vX”，单击立即提交该版本的面板、Hub 与 Agent 分发文件更新，在当前页显示进度，不跳转设置页、不清除草稿。顶部快捷更新不自动更新已安装的 Agent。需要同时更新当前空间已授权受管 Agent 时，可在详情或**系统设置 → 面板更新**中选择 Agent 范围并确认更新。此功能不会发布 GitHub Release，也不会自动执行未发布分支。

自动检查仅在管理员会话、页面可见、更新服务已连接且没有运行中、结果待核实或待恢复操作时执行。只读发现接口缓存 5 分钟，不创建宿主机持久检查任务，避免后台轮询耗尽更新记录配额；失败后退避重查。检查只读取发布信息，绝不自动安装。登出或失去管理员权限会停止监控；重新登录后先核对原请求。检查中、已是最新、尚未检查、检查失败与需恢复分别显示，旧 Agent 更新失败不会遮挡新的可用面板版本。

单击时固定所见版本、Release ID 和 SHA-256。若宿主机尚未核查这一候选，同一次点击会先创建一次持久检查，成功且三项完全一致后继续更新，无需第二次点击。候选改变或检查失败时停止，必须重新点击确认新的目标。该意图与原请求编号一同保存在当前会话，断线只核对原编号；不会因为收到新发布而扩大目标或自动重放更新。

## 首次启用

支持 Linux/systemd 宿主机、Docker Compose v2、单实例 Hub、独立外部命名数据卷，以及默认 UID/GID 10001 的非 root Hub 容器。Compose 必须支持 `up --wait`。Rootless Docker、userns-remap、自定义 Hub 数据 bind mount、多副本 Hub、非 systemd 宿主机不属于当前支持范围；这些部署继续手动更新。

先把包含本功能的源码部署到服务器。建议使用 `/opt/codepier`：部署目录、父目录和宿主机 Python 必须由 root 拥有，且组与其他用户不可写。不要在可由普通用户替换的目录中安装 root 服务。

新安装或重新部署时可一次启用：

```bash
sudo bash install.sh --enable-panel-update
```

面板已经使用新版 Compose 启动后，也可在相同部署目录单独安装：

```bash
sudo python3 scripts/panel_updater.py install --root "$PWD"
```

安装器验证现有 Compose 选择、外部数据卷和只读更新套接字挂载，生成独立 systemd 服务，并检查 Hub 容器能否访问它。重装服务时会阻止新的更新提交；存在运行中或需人工恢复的操作时拒绝重装，不会直接杀死更新进程。

`.codepier-updater/run` 以只读方式挂载到 `/run/codepier-updater`；仅此目录进入 Hub。Docker socket、宿主机配置副本、源码候选目录、历史日志都不暴露给网页进程。Hub 通过固定 Unix socket 协议提出检查和更新请求，不能传递任意命令、URL、Docker 参数或主机路径。

默认来源固定为 `cyeinfpro/codepier`。自建 fork 只能由宿主机管理员在安装时通过 `--repository owner/repository` 设定，网页不能更换来源。重新安装自建 fork 的更新服务时应继续明确指定该参数。

## 发布包要求

使用 GitHub 的最新正式 Release；拒绝 draft、prerelease、同版本重装和自动降级。目标版本必须是三段式正式版本，并上传名为 `codepier-VERSION-source.zip` 的附件，不能只创建 Git tag。

从 1.14.1 起，正式 Release 另附完整开发源码 `codepier-VERSION-source-full.zip`。面板仍选择 `source.zip`；该包仅省略旧更新器不接受的 8 个开发专用顶层配置文件，所有运行代码与依赖锁文件一致。完整开发与回归请使用 `source-full.zip`。1.14.0 的原附件不兼容 1.13.0 更新器；遇到“源码包包含未允许的顶层文件”时，重新检查正式 Release 并选择 1.14.1 或更新版本。检查结果可能缓存 60 秒。

附件必须由源码打包器生成，含 `MANIFEST.sha256`，GitHub Release 资产元数据必须提供 SHA-256 digest 与准确字节数。更新器先校验 GitHub digest，再检查 ZIP 路径、大小、文件类型、重复文件、清单覆盖及源码版本。整个下载与解压设置上限；不会执行下载包中的宿主机安装脚本或 Compose 文件。

正式发布前运行：

```bash
python scripts/check_release.py
python scripts/build_source_bundle.py --public
python scripts/check_release.py --bundle dist/codepier-VERSION-source-full.zip
python scripts/build_source_bundle.py --public --panel-update
python scripts/check_release.py --panel-update --bundle dist/codepier-VERSION-source.zip
```

上面的 `VERSION` 应替换为 `shared/util.py` 与 `RELEASE.json` 中一致的发布版本。发布流程仍由维护者执行，更新按钮不会自动创建或推送发布。

没有正式 Release、缺少附件/digest、GitHub 限流、网络失败、发布内容在确认后改变时，面板会明确显示原因，不会退回 `main` 分支执行未校验代码。正向版本检查短暂缓存 60 秒，确认信息 15 分钟过期；过期后重新检查。

## 更新顺序与数据保护

更新服务独立于待替换的 Hub 运行。操作编号、请求幂等键和阶段状态持久保存在宿主机，关闭浏览器不会取消操作。

1. 下载并校验候选源码，在独立镜像标签下构建。预检候选 Hub 的版本，并生成、校验配套 Agent 安装包；此时旧 Hub 继续服务。
2. 启用宿主机拥有的维护标记，拒绝新操作和新 Agent WebSocket。等待已进入的请求、原生控制请求及排队/执行中的操作结束；未能排空时停止本次更新，不取消现有任务。
3. 停止旧 Hub，把完整数据卷复制到新命名卷，验证文件内容、权限和 SQLite 完整性。账号、会话、配对、项目、附件、主密钥及其他运行数据随完整卷复制；原卷保持不变，作为回退备份。
4. 使用安装时捕获的可信部署配置，只替换 Hub 镜像和数据卷。保持端口、环境变量、网络和现有代理配置，不重建无关服务。
5. 检查新 Hub 健康状态、运行版本及 `/agent/manifest.json` 的版本、大小和 SHA-256。成功后更新 `.env` 中三个受管项：`CODEPIER_HUB_IMAGE`、`CODEPIER_HUB_SOURCE`、`CODEPIER_HUB_DATA_VOLUME`。其余设置保留。
6. 先持久记录新版本已提交，再开放请求。提交前切换失败会恢复旧镜像与原数据卷；提交后绝不自动恢复旧数据，因为新版本可能已经接受新的写入。

更新后服务器提供新的网页、Hub、Agent ZIP、安装脚本和生命周期文件。**已经安装在各台电脑上的 Agent 不会被强制更新或重启**；仍可使用节点管理中的 Agent 更新功能单独升级。

新版 launcher 将宿主更新器与 Hub 镜像分离：当前 engine 完成当前事务，校验并暂存同一已确认 Release 的下一 engine，成功且空闲后再切换。旧版没有该能力；不能把升级 Hub 说成宿主更新器也已升级。详见兼容矩阵与信任边界。

## 断线与恢复

浏览器提交回执丢失时只查询同一个请求编号，不自动重复 POST。若更新服务确认没有该编号，页面允许显式“重新提交原请求”，仍使用原幂等键。刷新页面会继续读取持久记录；更新期间离开设置页，也会继续跟踪同一操作。

当更新操作明确成功，且当前响应 Hub 的运行版本与目标版本一致后，旧页面会自动重新加载，并保留当前页面位置。Hub 重启、更新服务暂不可达、版本尚未切换、失败、回退或需要人工恢复时不会误触发成功刷新，也不会重新提交部署。已经加载目标版本的页面不再刷新；URL 中仅保存非敏感的更新标记，即使浏览器存储不可用也不会反复刷新。

检测到文件或会话草稿、未保存表单输入、打开的弹窗、进行中的按钮操作时，会暂缓刷新。处理完这些输入后自动继续；“刷新到新版本”保留为手动入口，丢弃未保存输入前仍需确认。保存授权设置不会清掉同页的地址或密码输入。

首次部署含自动刷新逻辑的版本时，已经打开的旧标签页仍使用旧 JavaScript，需要刷新一次以加载新逻辑；之后通过新版页面发起的更新不再需要手动刷新。

守护进程重启不会重放未开始的下载或部署命令。切换前中断会标记失败；未提交的切换会尝试恢复原镜像和原数据。已提交的新版本只验证和恢复新版本，不回退旧数据。自动恢复不能完成时保持 `recovery_required`，保留保护标记与备份，并禁止再次更新。

在原部署目录查看宿主机状态：

```bash
sudo python3 scripts/panel_updater.py status --root "$PWD"
```

实际服务名称保存在 `.codepier-updater/config.json` 的 `unit` 字段，也会在安装成功时输出。通过 `systemctl status` 与 `journalctl -u` 检查该服务；每次操作的详细命令输出在 `.codepier-updater/jobs/操作编号/commands.log`。这些文件可能包含敏感运行配置，只供宿主机管理员读取，不应公开上传。

人工恢复前先阅读操作阶段和 `commit_decided`，核实镜像、当前数据卷及服务状态。停止该更新服务后，可运行：

```bash
sudo python3 scripts/panel_updater.py recover --root "$PWD"
```

完成核查后重新启动该 systemd 服务。不要为了恢复网页而直接删除维护标记、手工覆盖 `.env`、删除安装锁或把旧代码接到已迁移的数据卷上；已提交的新数据不能用旧备份直接替代。

## 运维边界

原镜像、原数据卷、候选源码与任务记录不会自动清理。主机源码区开始更新前至少需要 512 MiB 空闲空间，但 Docker 镜像层和完整数据副本还需要额外空间，容量取决于实际部署。数据副本不足、构建失败或配置被其他人修改都会终止或进入恢复流程。

不要在更新期间手动运行另一条部署命令或执行 Docker prune。更新器与安装脚本共享部署锁；网页同时只接受一个操作，幂等键不能用于不同请求。记录达到上限后会要求管理员归档，不会自动删除备份。归档前确认哪些镜像、数据卷、源码目录和任务仍被当前配置引用，尤其不能删除 `CODEPIER_HUB_SOURCE` 所指向的在用源码。

本功能不等同于异地备份。重要服务仍应有独立、已验证的备份与恢复方案。正式用于生产之前，应在与生产相同的 Linux/Docker/systemd 环境完成实际镜像构建、健康切换、故障回退及重启恢复验收。

## 备份 Hub 数据

Hub CLI 可以一致性备份数据库及对应主密钥。在部署目录执行：

```bash
backup="codepier-$(date +%Y%m%d-%H%M%S).zip"
docker compose exec -T hub python -m hub backup --output "/app/data/backups/$backup"
umask 077
mkdir -p backups
chmod 700 backups
docker compose cp "hub:/app/data/backups/$backup" "./backups/$backup"
chmod 600 "./backups/$backup"
```

将备份放到另一处可信存储，并验证可恢复性。数据库与对应密钥必须一起保留；这个 ZIP 不包含全部附件、Agent 本机状态或原生 CLI 配置。完整迁移还需规划数据卷、部署配置和各节点的备份。面板更新保留的旧数据卷也不能替代独立备份。

## 可选：代码与数据库快照，附件原件独立保留

旧宿主更新器仍按原完整卷流程兼容更新 Hub；新安装的 launcher 更新器在用户确认一次版本更新时，默认在同一事务中启用新存储布局，不再需要额外开关。仅发布代码不会替用户操作生产：

- `/app/data`：原有稳定外部卷，保存附件原件、旧备份包及其他非数据库文件；不随版本切换，不纳入历史版本清理。
- `/app/state`：独立外部状态卷，`HUB_STATE_DIR=/app/state`、`HUB_DATA_DIR=/app/data`。保存 Hub SQLite、native CLI SQLite、匹配的主密钥/密钥环和初始化回执。
- 代码由已校验 Release、独立镜像和源码清单保留；附件不再递归放入每个新状态卷。数据库中的已有内容不删行、不改语义，不能把“附件不备份”解释为删除数据库记录。
- 每次更新只更换状态卷，稳定附件卷的挂载和名称必须不变。两个逻辑挂载不得指向同一实际 Docker 卷。旧版本没有明确声明 `split-state-v1` 能力时，在停止服务前拒绝更新。
- 旧 Hub 排空并停止后，逐字节校验复制数据库及其 WAL 到新卷，再仅在新卷合并 WAL、转换独立数据库并检查完整性；不对源库 VACUUM，不更改 ROWID，不忽略包含已提交写入的 WAL，不把源 SHM 带入新卷。该操作不是压缩，不能承诺数据库显著缩小。
- 回执最后发布；无有效回执、缺失数据库或密钥时拒绝启动，不退回稳定卷中的旧数据库，更不创建空数据库顶替。

### 首次迁移：离线准备与显式事务激活

先部署支持新布局的代码与宿主机更新器。保留原 Compose、环境配置、原卷以及当前版本恢复路径；原卷中已有旧数据库暂时保留，不能据此宣称立即释放该空间。准备阶段不会切换服务、删除或移动任何附件。

可信源码树提供只读规划器（路径是已核实的源卷与空目标卷挂载，不是任意猜测的宿主机目录）：

```bash
python -m scripts.panel_state_migration SOURCE_MOUNT EMPTY_STATE_MOUNT
```

规划输出需复核，再经过维护窗口与明确迁移审批：关闭新请求、排空任务并停止旧 Hub，独占 Hub/密钥锁后，才可使用同一工具的 `--prepare --confirm-offline` 准备独立状态。工具仍不修改 Compose 或激活新卷；失败目标原样保留，不自动重试覆盖。已有密钥轮换恢复材料或未知状态文件会阻塞，不能静默跳过。

生产首次激活由宿主机专用 `migrate-state` 事务执行，不是网页更新接口，也不能把 `--prepare` 当成已上线。先将 Hub 正常升级到支持新布局的版本并安装对应宿主机更新器；同版本迁移不下载、不构建新版本。经过审批与维护窗口，停止**更新器服务**（不是提前停止 Hub），使用固定请求编号：

```bash
sudo python3 "$ROOT/.codepier-updater/service/panel_updater.py" migrate-state \
  --root "$ROOT" --confirm-layout-migration --request-key "$REQUEST_KEY"
```

命令必须取得更新器守护进程锁；服务仍运行会拒绝，不会强行终止。先检查镜像能力、现有任务/恢复记录和维护标记，再按原有维护门禁排空、停止 Hub、准备新卷和验证。旧数据卷继续作为附件原卷；新的状态卷通过 `CODEPIER_HUB_STATE_VOLUME` 指定。未确认结果只查询/恢复同一请求，不更换编号重跑；再次提交同一编号只返回原回执。

提交时在宿主机私有 `.codepier-updater/layouts/<job>.json` 保存完整可信 Compose，更新 `COMPOSE_FILE` 与状态卷环境项及 current.json，原 Compose 文件与 env.before 保留；再持久写入提交决定，最后开放流量。验证不仅检查同版本健康状态，还核对镜像 ID、状态/附件实际挂载与 HUB_STATE_DIR，避免同版本旧布局误判成功。提交前任一中断恢复原配置和原卷；提交后只恢复新布局，禁止覆盖新写入。查看该请求状态并按“断线与恢复”处理后再启动更新器服务。

新配置继续由原安装器捕获，不需要手工猜测重建当前配置。未知维护标记、未结束或待恢复记录、无布局能力的镜像会阻止迁移。上线前必须在真实 Docker 环境完成迁移与故障恢复演练；合成 Docker 边界单测不等同于生产验收。

后续 rekey 的恢复材料默认保守阻塞状态复制，需要管理员单独核对、归档并保留可恢复记录；本补丁不会为了瘦身删除 `.rekey` 或轮换密钥。

### 历史保留规划：当前版本之外，最近两个成功历史版本

`python scripts/panel_update_retention.py trusted-inventory.json` 只生成清理候选清单与摘要，不删除、不调度、不自动实施。输入必须是完整且可信的当前部署/所有容器引用/任务状态/锁/恢复 pin/对象标签元数据；不能用目录修改时间或任务数量代替成功版本。调用方必须将实际独立附件卷列为保护对象。

当前版本单独保留；最多两个**不同的成功历史版本**作为普通保留目标。所有运行或停止容器引用、当前配置、稳定附件卷、非终态或 `recovery_required`、维护/部署锁、恢复 pin、未知/冲突/旧版无标签对象一律保护或转人工检查。幂等键、任务状态和审计回执不在此清理范围。强制保护可能使实际保留数量超过两个，不能为满足数量删除恢复依赖。

执行删除仍需要针对冻结清单的当次确认、锁内重新核验与独立执行器；本实现没有删除执行器，也不会自动启用清理。宿主机更新控制代码不会随 Hub 镜像自动升级。

### 容量边界

2026-10-24 的只读测量发现该部署约 3.26 GB 数据卷中，约 792 MB 是历史备份 ZIP；拆分可以避免将它们继续复制进每轮状态卷，但不会删除已存在的原件或旧副本。Hub 数据库约 2.437 GB，free-list 为 0，主要是操作持久结果与审计/事件。不能承诺通过 VACUUM 回收数 GB，也不能把结果记录视为可任意删除的缓存。

状态准备及分离模式复制均检查目标卷上数据库与 WAL 大小加 512 MiB 安全余量；管理员仍需核实 Docker 数据盘足以容纳镜像与恢复空间。更新器原有宿主机源码区 512 MiB 检查不代表 Docker 数据卷容量充足。本文方案不替代异地备份。

### 可选离线压缩归档（不接入自动回退/清理）

`scripts.panel_state_archive` 提供已完成离线状态快照的无损导出、校验和恢复。只接受规范状态文件集合；拒绝锁文件、WAL/SHM、轮换恢复材料、未知文件、符号链接和不安全权限。不接受运行中的数据库目录；导出需要 `--confirm-offline`。该工具不会替换在线卷、停止服务或删除原始快照。

```bash
python -m scripts.panel_state_archive export OFFLINE_STATE backup.cps --confirm-offline
python -m scripts.panel_state_archive verify backup.cps
python -m scripts.panel_state_archive restore backup.cps EMPTY_PRIVATE_STATE
```

归档包含逐文件长度、SHA-256 与压缩流边界，恢复严格限制允许路径和展开大小，检查 SQLite 完整性与密钥配对；完整验证后才在空私有目录发布，初始化回执最后发布。文件默认只允许所属用户访问，跨宿主机恢复需按部署 UID/GID 安排目标目录所有权；不能把归档或密钥放入公开仓库。哈希检测意外损坏，不代替可信存储与访问控制。

该独立工具**没有**自动替代旧数据卷的生命周期；只有经审批的真实恢复演练、回滚引用切换与冻结删除清单确认后，才可考虑删除已归档旧卷。现阶段保留原卷，不声称已释放空间。只读测量的一个历史库（2,437,218,304 字节）使用 gzip level 3 可压缩至 713,788,159 字节，完整解压 SHA-256 一致；这是样本结果，不是所有部署的保证，且测量未生成生产归档、未修改数据。

### 新版单次确认流程与旧版兼容矩阵

| 现有宿主能力 | 面板点击能完成的范围 | 是否自动获得新宿主能力 |

管理员首次安装本版宿主服务是明确的信任边界：之后确认固定仓库的正式 Release，也允许其中经校验的三份 host engine Python 代码以宿主 root 执行。GitHub asset digest 与 MANIFEST 保证来源绑定与内容完整性，不是独立发布者签名，也不是 Python 沙箱。固定文件集合与禁止自定义 hooks 不会消除发布者代码的 root 权能。网页不能更换仓库、安装路径、执行参数或下载任意 URL。

Launcher 和验证 helper 只由管理员安装改变；Release 的 `host_updater` 协议/min-launcher 必须匹配已安装策略。当前 engine 下载并验证固定 Release ID、版本、资产 SHA-256 和文件清单，在私有不可变身份目录暂存 `panel_updater.py`、`panel_update_runtime.py`、`panel_update_source.py`，再完成 Hub 升级与默认分离。该事务未终结或需恢复时不更换 engine。成功后锁住新请求接收，提升同一 Release 的 selector，在空闲边界启动下一 engine；新 socket readiness 回执才证明 engine 已就绪，selector 写入不算完成。

Launcher 连续持有同一服务锁，子进程继承已锁文件描述符；所有未结束/待恢复任务固定其原 engine 身份。恢复不能改用最新代码、旧安装脚本或另一个请求编号。旧 engine、旧卷、旧配置和回执不自动删除。未知协议、文件被替换、身份冲突或新 engine 无法启动都失败关闭；不会靠自动降级掩盖可能已经接收的新工作。

专用宿主管理绑定可作为未来面板兼容初始化桥接，但必须另行设计管理员确认、确切同主机身份、项目绑定/revision、部署根和最小维护权限；本版没有实现该桥接，也不会借用任意已保存 VPS 连接。旧版能更新 Hub 与旧版能引导宿主是两个不同承诺。

2026-10-24 补充真实宿主引擎验收：未改动的 launcher 在隔离测试根以实际子进程、继承锁与 `-I -B` 启动并建立 Unix socket；随后通过同一面板协议执行默认分离更新，核验新镜像、原附件、数据库内容与普通 Compose，再完成 engine 空闲晋级和新 engine readiness。网络 Release 获取由本地固定合成发布替代，候选镜像从与开发机字节一致的公开包单独构建后复用；不将此测试称为真实 GitHub 最新发布下载或生产升级。8 个清单测试对象与专用测试镜像已清理，原生产镜像及健康状态未变。
