# 并发与低延迟优化验收计划

## 范围和当前状态

本批为 v1.25.0，发布状态以同一提交的完整 CI 和 Release 为准，发布不证明实际部署。保留 v1.24 的自适应 Agent 调度、持久操作、幂等账本、授权复核和输出游标。平台同时调用数量由客户端决定，本项目不修改平台并发限制。

实施顺序：

1. 已授权的接入诊断、批量文本读取和能力拆分先完成独立正确性验收。
2. Gateway 只对明确协商的 modern 无状态协议开放有界并发，复用 HTTP client；未知/legacy 会话继续串行，不能假定支持多会话。
3. Hub 投递采用有界准备与每设备有序发送，并在实际发送前重查授权；跨设备候选公平取出。
4. 先测量 Store 单工作线程的排队/执行耗时，再合并热路径查询或缓存纯静态元数据。不盲目增加 SQLite 写线程。
5. 仅对相同授权、版本与安全读取语义考虑 singleflight；每个调用方仍须重新验权。普通写入、命令、GUI 输入不去重或重放。
6. 基于已有 MCP Events 的事务 outbox 增加操作完成提示；2xx 只表示接收，不表示宿主消费或自动续聊。
7. 多 Hub 先明确共享持久存储、租约、身份版本失效和连接归属需求，本批不部署多实例。

## 基准约束

同一台机器、同一解释器和依赖、同一数据/请求分布，交替运行修改前后版本。源文件快照与 SHA 保留在本隔离工作区的 .work/performance-baseline；不覆盖原始样本。没有真实前后数据时，不宣称达到了排队 P95 降低 50% 或吞吐 2 倍的目标。

并发档位为 8、16、32、64、128。超过产品有界容量时记录明确拒绝和错误率，不能把拒绝当作成功吞吐，也不能悄悄调大产品限制。

工作负载分别为：
- 独立只读请求
- 有顺序约束的读写混合
- 长命令与短查询混合
- 相同版本读取竞争，以及不同授权/不同版本请求
- 断线、取消、撤权、重连与原操作续查

每轮记录样本级开始、排队、投递和完成时间，P50/P95/P99、成功吞吐、错误/拒绝数、不同设备/身份的公平性、CPU、峰值内存与宿主负载。保留原始 JSON/JSONL 及运行参数、代码 SHA、Python/依赖版本。Hub 时间与 Agent 相对时间分别报告，不相减伪造跨主机精确延迟。

Gateway MockTransport 用于确定性生命周期和安全测试；另以纯 loopback HTTP/1.1 检查真实 TCP keepalive。两者都不等同于第三方上游或真实 ChatGPT 验收。真实 Hub/Agent loopback 基准另列，不混成一个数字。

## 当前测量边界

2026-10-10 实施期间宿主同时有较重的真实桌面工作。按协调窗口串行运行功能测试，避免额外叠加。高负载下的测试结果保留，但不能作为安静生产容量结论；若始终无法获得可比窗口，交付代码和原始受干扰结果，并明确目标尚未验证。

Store.worker_metrics 只在进程内保留固定容量的数字样本和计数，不保存 SQL、参数、身份或路径，不是授权缓存。取消等待者仍等待已经进入 DB worker 的原阶段结束，不声称已提交写入被撤销。
