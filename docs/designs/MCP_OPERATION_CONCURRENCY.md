# CodePier 的 MCP 操作为什么排队，怎样提高并发

对这次出现的慢查询，**优先拆解 Hub 首次投递前的等待**。五个目录查询在这个阶段各花了约 70 秒，到达 Agent 后均在 70 毫秒内开始执行。增加 Agent 文件槽位，很难收回这批调用的大部分等待时间。对另一类常见慢请求——长任务占住源码根目录——优先缩短持锁时间。两种情况可以用同一条操作的 trace 区分。

## 1. 这次慢在哪里

2026-11-18，读取 MCP 项目五个不同目录时，保留了同一时段五条成功的 `fs_tree` 回执，每条均为一次尝试。在线诊断报告的 Hub 与 Agent 均为 **1.33.23**。下文源码分析对应项目 `发布前实验快照 7bc9836ba8d3`。它在 `v1.33.25` 标签之后还有两个未发布的提交，不等于 1.33.25 发布版，README 的 1.33.25 标记不代表这份源码。这两份证据回答不同问题：前者定位当时的等待阶段，后者用于选择下一轮测量位置。

观测版本与分析源码之间，投递路径本身已有改动：

- `2dd0d22`（发布前快照）：`_prepare_for_send` 保留已解密的请求（`retain_source=True`）。发送锁内的最终复核 `_delivery_packet_current` 只比对密文是否变化，不再重新解密。这正是第 4 节要测的发送临界区。
- `7bc9836`（发布前快照）：把面板启动时的读取移出 SQLite 写线程，影响“DB 排队”这一假设。
- 1.33.25：诊断开始用 `queue_reason` 区分 `hub_delivery` 与 `agent_pending`，可直接用于拆分首次投递前的等待。

因此在 1.33.23 上测到的约 70 秒，不能直接当作当前源码的基线。

| 同一操作内的时间段 | 五条记录的范围 | 说明 |
| --- | ---: | --- |
| Hub `hub_received → dispatched` | 69.3–76.5 秒 | 当前源码在发送锁内完成最终复核时记 `dispatched`。这个标记早于对端确认，期间可包含候选等待、DB 排队、准备及等发送锁。 |
| Hub `dispatched → hub_completed` | 1.607–4.218 秒 | Hub 最终复核通过至保存本次操作结果。 |
| Agent `accepted → executing` | 57–68 毫秒 | 使用同一次尝试的 `elapsed_ms`，包含本地启动前的开销。 |
| Agent `accepted → result_ready` | 96–157 毫秒 | 包含上一行及本地执行、保存结果的时间。 |
| Hub `hub_received → hub_completed` | 72.4–78.1 秒 | Hub 保存最终结果时结束，客户端随后取得响应。 |

这是一次现场观察。五个样本定位了这一批的长等待，数据库、投递循环、连接状态和锁争用还需用分段计时区分。原始回执已逐条复核，公开记录保留去标识的逐条阶段值。Hub 阶段用同一回执的 Hub `at` 相减，Agent 阶段用同次尝试的 `elapsed_ms` 相减。

## 2. 用容量和等待时间做决定

把一次操作看作依次消耗几种资源：Hub 数据库写线程的毫秒数、设备连接发送临界区的毫秒数、Agent 通道的槽位秒数，或某个路径的独占秒数。对固定的请求组合，若每个成功操作平均占用资源 `i` 的时间为 `Dᵢ`（包含重复访问），该资源有 `cᵢ` 个可并行单位，则它给出的理想吞吐上限约为 `cᵢ / Dᵢ`。全链路受最小上限约束。失败、探测和重复轮询还会消耗同一份预算。独立目录增加一个工作槽可能有用，同一文件的两个条件写仍须依次核对版本。

用同一队列、同一口径的稳定窗口估算 `Lq = λ × Wq`。例如每秒有 20 个操作通过，平均排队 3 秒，平均就有约 60 个操作在等。若希望平均只等 0.5 秒，同样流量下的平均排队数约为 10。**把 pending 上限改成 10 并不会自动达到目标**：只要到达速度持续超过完成速度，积压就会转移到调用方或变成拒绝。要缩短等待，可以减少每次请求占用瓶颈的时间、给瓶颈加独立容量，或减少到达瓶颈的工作量。突发用有界队列吸收，持续过载则要反馈给调用方。

## 3. 按等待位置选改动

| 看到的证据 | 优先动作 | 如何判断有效 |
| --- | --- | --- |
| `hub_received → dispatched` 长，Agent 启动快 | 先拆分投递计时。区分已经可投递却未被选中、数据库阶段排队、同设备有序准备、发送锁和连接不可用。见第 4 节。 | 同设备短读的首次投递 P95 下降，Agent 和客户端的等待没有同步上升。 |
| `waiting_resource` 集中到一个长任务，其他通道尚有空位 | 例如测试只读 `src/`、`tests/`，报告可写入 `CODEPIER_RUN_DIR`，则如实声明读范围，把临时库及报告移入独立目录。若会写源码或共享服务，保留相应写声明。依赖 Git 的任务可用已注册 worktree；支持写时复制的节点上，合适的本地命令可用 `isolation="snapshot"` 缩短主树持锁时间。 | 根路径阻塞时长下降，较早的冲突写者按序完成；仍可复核输入版本及产物。 |
| `lane_capacity` 多、对应通道满，节点还有 CPU、内存及 I/O 余量 | 在“设置 → 任务 → 并行与队列”核对实际 `reported.lanes.*.capacity`。仅逐档增加受限通道并复测。`project_limit` 查项目额度及预留，`remote_target_limit` 查远端实际承载力，`resource_pressure` 先缓解节点压力。 | 成功完成数/秒增加，短读 P95、其他项目最长等待、CPU 节流及内存压力均在约定范围内。 |
| 多个调用花在重复准备、逐文件往返或状态查询 | 已知路径且允许同批观察的文本读，用 `query(file, args.items)`，每批最多 8 个，并逐项校验结果。按需读取范围。可等任一完成时用多 ID 等待和输出游标，长外部 CI 用间隔查询释放本地执行资源。 | 每个业务动作的 Hub 操作数、轮询数和 DB 工作量下降；短结果可见时间仍满足需求。 |
| 突发时或持续高负载时出现 `PROJECT_BUSY`、`DEVICE_BUSY` 或 `HUB_BUSY` | 分别统计新请求与原回执续查。对明确 `admitted=false` 的新请求按 `retry_after_seconds` 退避并错开发送；已接纳或结果不确定时，续查原 ID，必要时按原幂等键恢复。调用方限制同时在途数。 | 同时报成功吞吐、排队、拒绝、超时和调用方等待，避免通过快速拒绝制造低延迟。 |

Hub 的 `durable_admission` 控制待完成数量及字节数。没有有效资源报告时回退到项目 32、节点 64；收到有效报告后按节点容量减去预留扩展，硬上限为节点 512、项目 256；Agent 执行、文件、远程通道另有实际容量。例如文件通道容量为 8 时，即使未配置更低的项目上限，当前调度器仍为其他项目保留位置，单个项目最多使用 7 个。若在途命令都竞争同一写资源，增加以上任一额度都不能让这些写同时完成。[持久准入](../../hub/admission_policy.py) · [Agent 调度器](../../agent/scheduler.py) · [配置与压力降级](../ADAPTIVE_SCHEDULER.md) · [路径声明及快照支持范围](../QUEUE_CONTENTION_IMPLEMENTATION.md)

## 4. Hub 投递的第一轮工程改动

> 本节以 `发布前实验快照 1eb0d0e` 的投递实现为起点。实现、实验结果与灰度配置见第 6 节。

该基线的 `delivery_loop` 每轮按设备轮转选出最多 128 个到期候选，正在处理一批候选的设备暂时排除。一个设备一次拿走本轮属于它的全部候选；只有一个设备有到期项时，这一批最多可达 128 个，轮转排名并不限制单设备批量。该设备要等整批串行发完才会再次入选。候选还包括 `running`、`reconnecting`、`cancelling` 状态的操作，它们的 probe 与 cancel 和新 call 排在同一条队列里。每个设备有序发送，单设备预取 2。全局槽 `delivery_slots` 为 8，在准备前获取，到发送返回后才释放，限制的是“已准备加正在发送”的总数；单个设备最多占 2 个，至少 4 个设备同时投递时它才可能成为瓶颈。`_prepare_for_send` 在设备投递锁内提交一次 DB 阶段；真正写连接前，`_send_prepared` 还要持发送锁完成复核。循环已有事件唤醒和一秒兜底。仅凭约 70 秒的现象，无法认定是轮询间隔，也不足以支持把全局槽调大。[候选选择与权限复核](../../hub/runtime.py) · [有序投递流水线](../../hub/delivery_pipeline.py)

| 建议顺序 | 实施与证伪方法 |
| --- | --- |
| **先在当前源码上复测** | 用含 `2dd0d22`、`7bc9836` 的构建，在同一节点重跑同样的五目录读取，并按 `queue_reason` 拆分等待。若首次投递已明显缩短，以新结果为基线，再决定是否进行后续改动。 |
| **再加分段计时** | 复用现有 trace 和 DB worker 指标，在 Hub 内用单调时钟量出“到期可投递至首次入选”、等待全局槽、设备锁、DB 排队与实际执行、准备好至轮到发送、等发送锁、锁内复核和发送耗时。分开首次 call、probe、cancel 与离线退避。用有界直方图和慢样本，不逐事件追加同步写库。若 DB、锁和候选等待都很短，检查 Hub 事件循环延迟与连接更替。 |
| **若主要等候选或批次** | 在隔离夹具造一个有旧积压的设备，持续插入短读，并给另一设备同时发读。记录每轮候选数、当前批次年龄、首次入选等待。若慢样本集中在设备旧批次未排空，试验有界滚动补位，每次从持久队列取最早可投递项，保留单设备顺序、跨设备公平及控制/恢复机会。队列重启后仍由持久记录重建。 |
| **若主要等 DB 或发送锁** | 将 `queue_ms` 与 `phase_ms`、事务时间分开看。检查候选 SQL 的查询计划，以及循环内周期性清理是否挤在投递前；仅在实测占时后优化索引或给清理分批。若发送临界区占时长，先减少重复取数、移出纯组包工作；在锁内保留当前连接、撤权、取消、期限及操作状态的最终复核。 |
| **若主要等全局槽** | 单设备场景下全局槽很难成为瓶颈，先确认确有 4 个以上设备同时投递。确认 DB、发送锁、网络及 Agent 有余量后，在夹具中只改变一个参数，例如单设备预取从 2 到 4；注意预取项在发送期间也占全局槽。观察成功吞吐、已解密待发字节峰值、其他设备等待和取消延迟。若瓶颈只是移到发送锁，恢复原值。 |

当独立项目已经耗尽单台 Agent 的实际资源，可把已授权且数据能独立放置的项目分配到另一台 Agent，再看两台的成功吞吐之和。同一工作区和同一外部服务仍有各自的一致性要求。多 Hub 需要持久状态、连接所有权、租约及故障接管都可验证，属于单 Hub 经上述优化后仍持续饱和时的后续设计。[多 Hub 扩展条件](../HORIZONTAL_SCALING.md)

## 5. 怎样验收，以及何时回退

1. **建立基线。** 对同类工作负载先取一个滚动 24 小时窗口。分别报告短读、写、长任务的成功完成数/秒，Hub 首次投递、Agent 开始前等待及端到端 P50/P95/P99；并列给出每类样本数、最老排队年龄、拒绝、超时与取消。分开设备在线/离线、冷启动/准入就绪。复用项目的队列争用报告和原操作 trace。[争用报告用法](../QUEUE_CONTENTION_IMPLEMENTATION.md)
2. **一次检验一个假设。** 在隔离的 Hub/Agent 夹具用同一机器、解释器、源码基线及输入，交替跑前后版本。用已有 `read`、`read_write`、`long_short` 负载，按 8、16、32、64、128 并发逐档比较；额外为目标假设构造同路径冲突、单热设备与双设备场景。脚本支持固定 worker 闭环及固定速率开环。用开环从计划到达时刻量到结果，另报发送滞后、客户端丢弃和突发排空。两种结果分别报告。[基准脚本](../../scripts/benchmark_hub_agent.py) · [完整命令与样本量要求](../PERFORMANCE_BENCHMARKS.md)
3. **按问题验收。** 对本次同类短读，建议首轮目标为相同到达负载下，首次投递 P95 较基线至少下降 50%，端到端 P95 同向下降，成功吞吐不降，拒绝及超时率不升。扩容实验另看满足同一延迟目标时可持续的最大成功吞吐。为写入、其他设备和项目分别核对最长等待，避免把积压转嫁给少数调用方。门槛按每个同负载的对照格评估。
4. **小范围启用并保留回退。** 先在一个节点启用一项改动，与基线按相同负载和时段复核。验证撤权后待发调用被拦截、取消释放槽位、断线重连沿原 ID 得到唯一结果、同路径条件写不丢更新。出现重复副作用、顺序错误或审计缺失即回退；若成功吞吐无改善而尾延迟或拒绝持续上升，恢复原调度参数或原投递实现，让既有操作按原回执收敛。

## 6. 实现、验证与灰度

| 改动 | 实现与证据 |
| --- | --- |
| 分段计时 | `/api/queue-diagnostics` 的 `delivery` 仅实例管理员可读。按首次及重试 call、probe、cancel、cancel_pending、离线退避和失败等分别统计。计量覆盖到期至入选、设备批次等待、全局槽位、设备锁、DB 准备与复核的排队和执行、有序发送等待、连接锁与 socket 发送。诊断同时记录候选查询耗时、活动批次最老年龄、已解密待发原文字节峰值、维护时长和连接更替。超过 1 秒的样本最多保留最近 32 条，可按原 ID 对照持久 trace。聚合仅存在 Hub 进程内，重启复位。 |
| 选择与底层查询 | 调度候选使用一次 WAL 只读快照。它只提供调度线索，写线程重新核对操作状态、到期时间、设备和权限。局部索引限定活跃操作，先排窄列再读取入选的完整记录。65,536 条历史操作的隔离实验中，单热点候选 P95 为 0.457 → 0.366 ms，八设备候选 P95 为 3.668 → 2.674 ms。99% 活跃项尚未到期的场景出现约 0.02–0.03 ms 回退。 |
| 滚动补位 | 按设备启用后，每轮初选与补取默认最多 16 条。历史顺序为 `created,rowid`，每个设备任务最多处理 128 条后交回调度循环。补位读取可与发送重叠，读取失败时交还持久队列。已处理操作收到新的取消请求时，在批次边界交回全局选择。热点夹具的取消和恢复探测从第 129、130 次提前至第 17、18 次，另一设备的独立短读保持第 2 次投递。 |
| 维护让出写线程 | 过期媒体维护移出投递循环，按格式每轮最多处理 64 条，每个写阶段最多处理 4 条。64 条 256 KiB 媒体的对照里，单次占用写线程中位数从 70.11 ms 降到 4.60 ms，最大值从 75.52 ms 降到 5.05 ms。整轮中位数从 70.34 ms 增至 76.00 ms，清理数量和保留回执相同。 |
| 发送锁与回执 | 同一准备或最终复核阶段复用当前项目映射与主体，避免复制完整请求和反复解密。锁内核对现有连接、账本、授权、取消、期限和操作状态。固定一条首次 `read` 的 SQLite 语句计数中，准备 86 → 51，发送锁内复核 79 → 44。回归覆盖撤权、断线沿原 ID 恢复、取消后归还槽位和同路径相同旧 SHA 的条件写。 |
| 开闭环与滚动基线 | 开闭环压测分别提供短读、写和长任务的各阶段分位数、样本覆盖及失败计数。实例管理员可从 Hub 数据库的只读副本生成滚动 24 小时报表，查看已接纳操作的首投、Agent 等待、完成、最老排队和取消。前置拒绝及客户端超时来自客户端测量，旧回执缺少的维度显示为未知。 |

同机 Hub/Agent 五目录实验两侧各成功 50 次，首次投递 P95 从 16.574 ms 降至 10.442 ms（37%），端到端 P95 从 168.681 ms 降至 163.206 ms。闭环 15 格中，候选版本完成 2,976 次操作，基线完成 2,817 次，另有 159 次准入拒绝。纯读在 64 和 128 并发时的首投 P95 有所上升。开环 20 和 40 次/秒的两侧样本全部成功，首投 P95 分别下降约 23% 和 25%。这些隔离对照未达到 50% 的首投门槛。

在单个 Hub 上用 `HUB_DELIVERY_ROLLING_DEVICES=<设备 ID>` 启用一台设备。多个 ID 用逗号分隔，`*` 启用全部。配置留空并重启 Hub 恢复固定批次，已有操作沿同一原始 ID 续查。`HUB_DELIVERY_DEVICE_CHUNK` 可在 1–128 间试验，滚动默认 16。全局槽 `HUB_DELIVERY_SLOTS` 默认 8，范围 1–64。单设备预取 `HUB_DELIVERY_PREFETCH` 默认 2，范围 1–8。在每秒 40 次读取加 32 次突发的单参数试验里，预取设为 2 与 4 时，成功吞吐均为每秒 44 次，已准备请求峰值均为 2，因此本轮保留默认预取。每次调整一项，按相同负载比较首投、取消、成功吞吐和待发字节峰值。

多 Hub 仍是单 Hub 经过测量后持续饱和时的后续设计。上线需收集实际节点的滚动 24 小时基线和灰度数据。
