# CodePier 的 MCP 操作为什么排队，怎样提高并发

对这次出现的慢查询，**优先拆解 Hub 首次投递前的等待**。五个目录查询在这个阶段各花了约 70 秒，到达 Agent 后均在 70 毫秒内开始执行。增加 Agent 文件槽位，很难收回这批调用的大部分等待时间。对另一类常见慢请求——长任务占住源码根目录——优先缩短持锁时间。两种情况可以用同一条操作的 trace 区分。

## 1. 这次慢在哪里

2026-11-18，读取 MCP 项目五个不同目录时，保留了同一时段五条成功的 `fs_tree` 回执，每条均为一次尝试。在线诊断报告的 Hub 与 Agent 均为 **1.33.23**。下文源码分析对应项目 `main@7bc9836ba8d3`，README 标记 **1.33.25**。这两份证据回答不同问题：前者定位当时的等待阶段，后者用于选择下一轮测量位置。

| 同一操作内的时间段 | 五条记录的范围 | 说明 |
| --- | ---: | --- |
| Hub `hub_received → dispatched` | 69.3–76.5 秒 | 当前源码在发送锁内完成最终复核时记 `dispatched`。这个标记早于对端确认，期间可包含候选等待、DB 排队、准备及等发送锁。 |
| Agent `accepted → executing` | 57–68 毫秒 | 使用同一次尝试的 `elapsed_ms`，包含本地启动前的开销。 |
| Agent `accepted → result_ready` | 96–157 毫秒 | 包含上一行及本地执行、保存结果的时间。 |
| Hub `hub_received → hub_completed` | 72.4–78.1 秒 | Hub 保存最终结果时结束，客户端随后取得响应。 |

这是一次现场观察。五个样本足以定位这一批的长等待，区分数据库、投递循环、连接状态和锁争用仍需更细的计时。复核时用原 `operation_id` 调 `query(action="job", view="trace")`。Hub 阶段用 Hub 的 `at` 相减，Agent 阶段用同次尝试的 `elapsed_ms` 相减。跨机器时间戳、不同样本的最大值和各阶段 P95 均不能直接相加减。[Hub 投递实现](../../hub/runtime.py) · [回执与阶段的解释](../CONCURRENCY_OPTIMIZATION.md)

## 2. 用容量和等待时间做决定

把一次操作看作依次消耗几种资源：Hub 数据库写线程的毫秒数、设备连接发送临界区的毫秒数、Agent 通道的槽位秒数，或某个路径的独占秒数。对固定的请求组合，若每个成功操作平均占用资源 `i` 的时间为 `Dᵢ`（包含重复访问），该资源有 `cᵢ` 个可并行单位，则它给出的理想吞吐上限约为 `cᵢ / Dᵢ`。全链路受最小上限约束。失败、探测和重复轮询还会消耗同一份预算。独立目录增加一个工作槽可能有用，同一文件的两个条件写仍须依次核对版本。

用同一队列、同一口径的稳定窗口估算 `Lq = λ × Wq`。例如每秒有 20 个操作通过，平均排队 3 秒，平均就有约 60 个操作在等。若希望平均只等 0.5 秒，同样流量下的平均排队数约为 10。**把 pending 上限改成 10 并不会自动达到目标**：只要到达速度持续超过完成速度，积压就会转移到调用方或变成拒绝。要缩短等待，可以减少每次请求占用瓶颈的时间、给瓶颈加独立容量，或减少到达瓶颈的工作量。突发用有界队列吸收，持续过载则要反馈给调用方。

## 3. 按等待位置选改动

| 看到的证据 | 优先动作 | 如何判断有效 |
| --- | --- | --- |
| `hub_received → dispatched` 长，Agent 启动快 | 先拆分投递计时。区分已经可投递却未被选中、数据库阶段排队、同设备有序准备、发送锁和连接不可用。见第 4 节。 | 同设备短读的首次投递 P95 下降，Agent 和客户端的等待没有同步上升。 |
| `waiting_resource` 集中到一个长任务，其他通道尚有空位 | 例如测试只读 `src/`、`tests/`，报告可写入 `CODEPIER_RUN_DIR`，则如实声明读范围，把临时库及报告移入独立目录。若会写源码或共享服务，保留相应写声明。依赖 Git 的任务可用已注册 worktree；支持写时复制的节点上，合适的本地命令可用 `isolation="snapshot"` 缩短主树持锁时间。 | 根路径阻塞时长下降，较早的冲突写者按序完成；仍可复核输入版本及产物。 |
| `lane_capacity` 多、对应通道满，节点还有 CPU、内存及 I/O 余量 | 在“设置 → 任务 → 并行与队列”核对实际 `reported.lanes.*.capacity`。仅逐档增加受限通道并复测。`project_limit` 查项目额度及预留，`remote_target_limit` 查远端实际承载力，`resource_pressure` 先缓解节点压力。 | 成功完成数/秒增加，短读 P95、其他项目最长等待、CPU 节流及内存压力均在约定范围内。 |
| 多个调用花在重复准备、逐文件往返或状态查询 | 已知路径且允许同批观察的文本读，用 `query(file, args.items)`，每批最多 8 个，并逐项校验结果。按需读取范围。可等任一完成时用多 ID 等待和输出游标，长外部 CI 用间隔查询释放本地执行资源。 | 每个业务动作的 Hub 操作数、轮询数和 DB 工作量下降；短结果可见时间仍满足需求。 |
| 突发时或持续高负载时出现 `PROJECT_BUSY`、`DEVICE_BUSY` 或 `HUB_BUSY` | 分别统计新请求与原回执续查。对明确 `admitted=false` 的新请求按 `retry_after_seconds` 退避并错开发送；已接纳或结果不确定时，续查原 ID，必要时按原幂等键恢复。调用方限制同时在途数。 | 同时报成功吞吐、排队、拒绝、超时和调用方等待，避免通过快速拒绝制造低延迟。 |

Hub 的 `durable_admission` 控制待完成数量及字节数。保守预算为项目 32、节点 64；Agent 执行、文件、远程通道另有实际容量。例如文件通道容量为 8 时，即使未配置更低的项目上限，当前调度器仍为其他项目保留位置，单个项目最多使用 7 个。若在途命令都竞争同一写资源，增加以上任一额度都不能让这些写同时完成。[持久准入](../../hub/admission_policy.py) · [Agent 调度器](../../agent/scheduler.py) · [配置与压力降级](../ADAPTIVE_SCHEDULER.md) · [路径声明及快照支持范围](../QUEUE_CONTENTION_IMPLEMENTATION.md)

## 4. Hub 投递的第一轮工程改动

当前 `delivery_loop` 每轮按设备轮转选出最多 128 个到期候选，正在处理一批候选的设备暂时排除。每个设备有序发送，单设备预取 2，全局准备信号量为 8。`_prepare_for_send` 在设备投递锁内提交一次 DB 阶段；真正写连接前，`_send_prepared` 还要持发送锁完成复核。循环已有事件唤醒和一秒兜底。仅凭约 70 秒的现象，无法认定是轮询间隔，也不足以支持把全局信号量调大。[候选选择与权限复核](../../hub/runtime.py) · [有序投递流水线](../../hub/delivery_pipeline.py)

| 建议顺序 | 实施与证伪方法 |
| --- | --- |
| **先加分段计时** | 复用现有 trace 和 DB worker 指标，在 Hub 内用单调时钟量出“到期可投递至首次入选”、等待全局槽、设备锁、DB 排队与实际执行、准备好至轮到发送、等发送锁、锁内复核和发送耗时。分开首次 call、probe、cancel 与离线退避。用有界直方图和慢样本，不逐事件追加同步写库。若 DB、锁和候选等待都很短，检查 Hub 事件循环延迟与连接更替。 |
| **若主要等候选或批次** | 在隔离夹具造一个有旧积压的设备，持续插入短读，并给另一设备同时发读。记录每轮候选数、当前批次年龄、首次入选等待。若慢样本集中在设备旧批次未排空，试验有界滚动补位，每次从持久队列取最早可投递项，保留单设备顺序、跨设备公平及控制/恢复机会。队列重启后仍由持久记录重建。 |
| **若主要等 DB 或发送锁** | 将 `queue_ms` 与 `phase_ms`、事务时间分开看。检查候选 SQL 的查询计划，以及循环内周期性清理是否挤在投递前；仅在实测占时后优化索引或给清理分批。若发送临界区占时长，先减少重复取数、移出纯组包工作；在锁内保留当前连接、撤权、取消、期限及操作状态的最终复核。 |
| **若主要等准备槽** | 确认 DB、发送锁、网络及 Agent 有余量后，在夹具中只改变一个参数，例如单设备预取从 2 到 4。观察成功吞吐、已解密待发字节峰值、其他设备等待和取消延迟。若瓶颈只是移到发送锁，恢复原值。 |

当独立项目已经耗尽单台 Agent 的实际资源，可把已授权且数据能独立放置的项目分配到另一台 Agent，再看两台的成功吞吐之和。同一工作区和同一外部服务仍有各自的一致性要求。多 Hub 需要持久状态、连接所有权、租约及故障接管都可验证，属于单 Hub 经上述优化后仍持续饱和时的后续设计。[多 Hub 扩展条件](../HORIZONTAL_SCALING.md)

## 5. 怎样验收，以及何时回退

1. **建立基线。** 对同类工作负载先取一个滚动 24 小时窗口。分别报告短读、写、长任务的成功完成数/秒，Hub 首次投递、Agent 开始前等待及端到端 P50/P95/P99；并列给出每类样本数、最老排队年龄、拒绝、超时与取消。分开设备在线/离线、冷启动/准入就绪。复用项目的队列争用报告和原操作 trace。[争用报告用法](../QUEUE_CONTENTION_IMPLEMENTATION.md)
2. **一次检验一个假设。** 在隔离的 Hub/Agent 夹具用同一机器、解释器、源码基线及输入，交替跑前后版本。用已有 `read`、`read_write`、`long_short` 负载，按 8、16、32、64、128 并发逐档比较；额外为目标假设构造同路径冲突、单热设备与双设备场景。现有脚本采用固定 worker 闭环；要测突发排空时间，再用固定到达率单独发一段流量，并从计划到达时刻计算端到端延迟。两种结果分别报告。[基准脚本](../../scripts/benchmark_hub_agent.py) · [完整命令与样本量要求](../PERFORMANCE_BENCHMARKS.md)
3. **按问题验收。** 对本次同类短读，建议首轮目标为相同到达负载下，首次投递 P95 较基线至少下降 50%，端到端 P95 同向下降，成功吞吐不降，拒绝及超时率不升。扩容实验另看满足同一延迟目标时可持续的最大成功吞吐。为写入、其他设备和项目分别核对最长等待，避免把积压转嫁给少数调用方。以上是拟定门槛，尚无前后压测结果。
4. **小范围启用并保留回退。** 先在一个节点启用一项改动，与基线按相同负载和时段复核。验证撤权后待发调用被拦截、取消释放槽位、断线重连沿原 ID 得到唯一结果、同路径条件写不丢更新。出现重复副作用、顺序错误或审计缺失即回退；若成功吞吐无改善而尾延迟或拒绝持续上升，恢复原调度参数或原投递实现，让既有操作按原回执收敛。
