# CodePier：项目运行时抽象与连续执行研究

日期：2026-10-16（Asia/Taipei）
状态：源码研究、现场探测与定向验证完成；本文的新运行时方案尚未实现或部署。
前置设计：`docs/MCP_PROJECT_VIEW_AND_AUTHORIZATION_DESIGN_2026-10-15.md`

## 1. 结论

这次不应再以“隐藏 device_id、把电脑改叫节点”为主要改造方向。当前普通项目视图已经做了这些工作；剩余问题集中在执行环境、正文与日志、工具选择和任务连续性。

推荐目标是：**Dot 只需理解项目、任务和结果，无需知道具体个人电脑；即使在真实源码或日志中看到系统线索，也根据实际授权和回执继续处理任务，而不是自行增加桌面访问前置条件。**

不能承诺同时实现以下三件事：保留任意账号级 Shell、完整提供真实文件和日志、保证模型永远无法推断运行环境。源码本身就可以明写平台或部署位置。隐藏身份信息也不等于隔离系统权限。

因此分两层建设：

- 第一层：可预测的项目执行环境。减少个人登录脚本、环境变量、工具探测和大段日志对开发流程的干扰；保持原授权、命令结果和文件内容真实。
- 第二层：按需启用真正受限的项目运行时。通过执行账号、容器或虚拟机等实际边界，减少对个人文件、凭据、进程和网络的可达性；不是把原生 Shell 改名为沙箱。

任何已知的平台拒绝、任务范围撤销、过期租约和房间删除都继续生效，不得更换入口绕过。

## 3. 将“识别环境”与“阻塞原因”拆开

应分别记录三个事件：模型看到环境线索、系统收到动作请求、动作被哪一层拒绝或完成。前者不能单独当作后两者的原因。

建议复用既有审计和操作回执，给失败诊断明确关联：`request_id`、`operation_id`、项目/工作区、原任务、授权修订、工具目录摘要和实际阶段。

| 类型 | 需要的证据 | 正确处理 |
| --- | --- | --- |
| 模型自行声称“需要连接电脑” | 会话行为与已有回执；没有可信拒绝证据 | 解释文件/命令与桌面控制的区别；不伪造授权，也不新增无依据确认 |
| 调用平台真实拒绝 | 平台原生反馈或可信接入 | 保留拒绝，沿平台允许的授权方式处理 |
| CodePier 当前范围拒绝 | scope、目标、租约等机器错误码 | 按原权限体系恢复或停止，不换工具逃逸 |
| 执行启动失败 | COMMAND_MISSING、启动错误、实际退出码 | 修复项目执行配置或依赖，不要求无关桌面访问 |
| 业务测试失败 | 测试输出与退出码 | 修改项目代码并验证，不把它误报成连接问题 |
| 响应丢失或仍运行 | 原 operation_id 和输出序列 | 查询原操作，不创建新幂等键重放 |

CodePier 未观察到调用平台决定时仍是 `not_observed`。这个状态既不等于许可，也不等于拒绝。产品自身的元数据不能代表客户端作出批准。MCP 架构将安全策略和用户授权决定保留在 Host 层。[S1]

## 4. 最优先：可预测的项目执行环境

### 4.1 不再让常规开发依赖个人登录终端

新增有版本的执行配置，建议内部称 `project_clean_v1`；现有配置保留为兼容路径，不静默替换用户配置。

对于确定的工具调用优先使用程序与参数数组，而不是拼接大段 Shell 字符串。当前具名 task 已有 argv 执行基础，应先复用。需要管道、重定向等 Shell 语法时，使用明确配置并验证过的非交互、非登录 Shell。

重点不是简单给 zsh 加 `-f`。zsh 官方文档明确说明，系统 zshenv 仍会读取；因此这种改动不能保证消除本次 `/etc/zshenv` 错误。[S2] 本轮没有读取或修改系统启动文件正文，也没有猜测其错误代码。

所有命令仍经过现有 `enforce_argv`、项目/目标检查、执行预算和原任务租约。用 argv 直接执行不是把执行动作变成只读，也不消除脚本本身的副作用。

### 4.2 环境是运行时配置，不是一个布尔开关

必须由同一配置构造器为能力诊断、依赖解析和实际进程启动提供环境：

- 明确工具链与 PATH 来源，避免诊断发现一个 Python、实际运行另一个 Python。
- 项目独立 HOME、临时目录与缓存；保留操作系统实际需要的变量，不能机械套用 Linux 环境。
- 不自动继承个人代理、Shell 启动钩子、用户插件和全账号凭据。
- 项目所需证书、代理、SSH 或发布权限采用明确的项目绑定，不把“兼容”实现为重新注入全部个人环境。

上述 HOME/缓存分离主要改善确定性。只改环境变量不会更改真实 UID、文件系统访问权限或其他系统接口，所以原生账号执行仍须如实显示其权限边界。

环境修订进入运行时描述与缓存指纹。正常执行不新增每步强制全环境探测；只在配置改变、工具链改变或具体故障时刷新相关诊断。最终启动仍验证具体命令和当前权限。

### 4.3 兼容迁移

需要逐项目验证 nvm/pyenv/Homebrew、虚拟环境、Git helper、证书、网络代理、签名与原生构建工具。不要通过清空全部环境让原本可工作的构建突然失效。

原生兼容配置可以继续存在，但选择必须显式且可审计。严格隔离运行时失败时绝不能自动回落到个人账号 Shell。已有运行中的操作固定使用其原配置和预算；新配置仅影响满足相应授权条件的新步骤。

## 5. 把高频操作提升为项目能力，而不是电脑探测

项目已有搜索、读取、差异、符号/LSP、验证及具名 task 基础。优先修整这些入口及发现方式，不另建一套通用代理、任务队列或权限模型。

| 用户意图 | 推荐接口方向 | 要减少的无关步骤 |
| --- | --- | --- |
| 定位代码 | 现有项目内容搜索、目录、符号/LSP | 临时探测 `rg`、打印系统信息再决定搜索方式 |
| 查看改动 | 现有 changes/Git 只读能力，必要时扩展严格类型入口 | 拼接命令、解析混合启动日志 |
| 执行测试或构建 | `exec(task=...)`、现有 validation，具名并绑定项目 | 每次猜虚拟环境、工具路径和命令模板 |
| 读取产物 | 原 artifact 与操作回执 | 让模型猜宿主绝对路径 |

语义化工具的收益是减少环境依赖与解析成本，不是隐藏副作用。测试、构建仍可运行项目代码，不能因为名称叫“验证”就标记 `readOnlyHint=true`。

需要自由命令时保留真实 `exec`；不是为了不可识别而禁止所有 Shell，也不是把所有查询偷偷包装成通用 Shell。

## 6. 结果分层：结构化摘要、真实证据、按需诊断

建议让产品自己生成的结果先提供明确摘要。例如下面是拟议结构，不是当前已支持的调用参数：

```json
{
  "operation_id": "opaque-operation-id",
  "state": "failed",
  "exit_code": 1,
  "diagnostics": [{
    "path": "src/example.py",
    "line": 23,
    "code": "ASSERTION_FAILED",
    "message": "Expected result differs from actual result"
  }],
  "log_ref": "opaque-authorized-log-id",
  "truncated": false
}
```

路径摘要由可信解析器生成，明确它不是原始 stdout。解析失败时回到真实有界输出，不杜撰诊断。退出码、失败状态、截断情况与原始回执保持一致。

对于本产品自己的包装器，应在生成元数据时使用项目相对路径或稳定 artifact/ref，减少不必要的绝对路径。保留管理审计所需真实路径，并应用其既有访问权限。MCP 支持 `structuredContent` 与输出 schema，可承载这种明确区分的结果。[S3]

不得对任意正文执行全局路径替换：它会影响补丁定位、快照、堆栈解释、命令复制与 SHA 语义。原有凭据脱敏继续保留；不能借“输出保真”停止已有 SecretOutput 保护。

日志取回、分页、标准 Tasks、协作嵌套回执、错误包装和 `_meta` 都必须审查。摘要删掉的元数据不能从另一个默认入口重新自动披露；但经过正常权限读取的原始内容仍保持真实。

## 7. 中途唤醒仍应看到同一个项目契约

当前 `hub/collaboration/dot_chat.py` 已提供每轮刷新的 `task_context_protocol`，强调保留连接、checkpoint、原消息和任务范围。本轮不建议叠加另一套超长唤醒提示词。

应复用既有任务对象，用小型、可验证的运行时描述持续提供必要事实：确切项目/工作区、原 task/work_item、目标映射修订、原 operation_id、当前状态和适用执行边界。

将来新增 `runtime_ref` 时，它只能是指向服务器对象的标识，不是授权令牌；每次仍核对访问者和原任务范围。当前协议对有状态工具也强调显式句柄和逐次授权。[S3]

对用户的正确解释应类似：

> 该任务使用已选项目的文件与命令接口，不要求桌面控制。此次命令返回缺少依赖，将按原任务处理依赖问题。

而不是：

> 发现这是你的电脑，因此需要重新开启电脑控制。

上述行为只适用于没有实际拒绝、且原授权允许继续的情形。已知拒绝不能用解释文本解除。

工具目录、运行时描述和权限版本分开管理。升级后确认实际目录已刷新，保留原订阅/任务，不通过重新加入自动扩权。旧聊天中已经看见的环境信息无法被服务器更新撤回；新会话和旧会话必须分别验收。

## 8. 开发与设备管理分开，但不能只做视觉隐藏

建议常规开发使用明确的项目能力集合，设备、桌面控制及全局管理通过其真实独立授权入口提供。减少无关领域进入默认开发上下文，也减少模型把文件操作误当电脑控制的机会。

必须同时保留真实权限检查。只从工具列表删掉 `computer`，并不能阻止一个仍拥有账号级 Shell 的执行器接触其他系统资源。

目录内容应由当前请求的授权及明确配置决定，排序稳定；不能仅因调用过 open，就偷偷切换同一连接的工具权限。当前 MCP 工具规范允许按所呈现授权改变目录，但不允许把目录变化做成连接状态或其他请求的隐式副作用。[S3]

不修改工具 annotations 来影响审批，不把“命令执行”伪装成“只读数据库查询”，不把本机执行谎称云沙箱。

## 9. 强需求采用真实项目运行时

### 9.1 目标结构

```text
Dot
  → 项目接口 / 原授权与任务状态
  → 受验证的运行时适配器
  → 工作区文件、指定工具链、受限网络和进程
```

运行时可以实际拥有 `/workspace`、独立 home/tmp，而不是在返回值里把真实路径替换成这些字符串。

仅挂载或同步确切批准的项目内容；不默认暴露宿主 home、根目录、SSH agent、Docker socket、其他项目或管理网络。根据后端能力落实账号权限、资源限额、进程、网络和凭据策略。容器的实际边界还取决于挂载、权限及运行配置，不能仅凭“使用了 Docker”宣布隔离完成。[S4]

### 9.2 保证命令和文件操作看到同一份数据

最重要的正确性约束是：文件工具写入的内容必须被随后的测试看见；命令产生的内容也必须被文件工具正确读取。

可选两条路线：

- 受限的项目挂载：数据一致性直接，但写入会改变被挂载的宿主项目文件，必须明确这是批准的副作用。Docker bind mount 默认可写；不能把它说成完全不影响宿主。[S5]
- 独立工作区：所有开发读写统一落在独立工作区，按真实 SHA/差异发布回目标，冲突则停止合并。不要建立无版本的双向同步，避免旧数据覆盖新改动。

需要检查符号链接、Git worktree 的外部 `.git` 指向、文件权限、大小写与 Unicode、CRLF/BOM、文件监听、原子替换、缓存平台差异。运行时视图相同不代表锁和任务归属相同，仍应按原资源协调规则处理。

### 9.3 跨平台现实边界

Linux 容器不等同于 macOS 原生运行环境。需要 Xcode、签名、系统媒体工具或桌面能力的项目，应配置相应原生/虚拟化执行目标，不能承诺无差别迁移。Docker Desktop 的 Linux 容器运行在 Linux VM 中，相关文件挂载由 Desktop 处理。[S5]

专用账号可以减少共享个人配置，但也不是默认不可访问其他目录的沙箱。选择容器或虚拟机，应以实际工作负载和已验证边界决定，不以营销名称决定。

真实隔离减少个人宿主身份与资源暴露，但运行时本身仍可被识别为某类系统或虚拟环境。项目源码也仍可能说明其作者的开发环境；这不应被视为失败。

### 9.4 对接现有严格范围

现有 `require_os_isolation` 缺少驱动时拒绝执行是正确行为。新增适配器必须提供可验证的后端能力和边界证据，经过项目目标映射及原范围检查后才能支持该模式。

不能由模型传入 `isolated=true` 取得权限；不能缺少证明时退回原生 Shell；不能因为新运行时名称而给旧任务扩展目标。运行时变更、文件写回和凭据使用都需要符合原授权边界。

## 11. 验收不能只看“有没有电脑两个字”

### 11.1 功能与权限

1. 文件新建、读取、SHA 冲突、唯一编辑、原子替换；中文/空格路径、BOM/换行、链接与越界场景。
2. 命令 argv、管道/重定向、非零退出、超时/取消、输出截断与序列恢复；父子进程清理与结果不确定性。
3. 诊断发现的工具、环境、运行时修订与实际启动一致；缺依赖有明确错误，不触发无关授权。
4. 受管任务的撤销、租约、fencing、原目标与房间删除仍生效；幂等回执恢复不重复写入。
5. 强隔离下验证个人 home、凭据、其他项目、管理 socket、网络与进程边界；只挂载项目仍须验证其写入影响。

### 11.2 真实 Dot 长流程

新会话与已有历史会话分别运行多步开发任务：读 README、搜索、改文件、执行测试、故意遇到依赖错误、取日志、修复、再次测试、等待后恢复、输出结果。

测试素材应故意包含真实平台词和合成绝对路径。要求不是“永远看不到”，而是“不根据这些词自行增加桌面控制授权”。遇到真实平台拒绝则必须停止，不能把绕过拒绝计为完成率提升。

记录：没有证据的重复确认次数、真实拒绝次数、有效完成率、重复副作用数、恢复失败数、默认响应字节数和必要调用数。优化幅度必须实测，不预先承诺固定百分比。
