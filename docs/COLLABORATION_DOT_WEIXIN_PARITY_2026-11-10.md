# 协作中心：房间与微信同权直达 dot（2026-11-10）

> 实施方案 v2，补齐批量续办、独立回复调度和自动续期的验收条件。原缺陷复现基线为 `a15b899`（v1.33.3），本次核对基线为 `07d006e`。原复现和位置保留在第 2、3 节，建议代码、实施顺序和验收标准以第 4–9 节为准。
>
> 旧版提到的独立补丁在当前工作区未找到。本文内的代码是实施参考，验证记录区分历史原型、本次文档核验和后续联调。

## 1. 目标与使用流程

1. 房主在协作房间连接 dot，完成读取和回复探测，再配对自己的微信私聊。
2. 启用「跟随房间」后，界面一次性说明本人身份、房间、可访问项目与能力、回传去向。配对和本人任务许可各自有明确状态，已有授权继续按其范围生效。
3. 在房间或微信发明确任务，两条入口使用同一套规则。已授权的任务由 dot 直接开工，无需逐条确认。闲聊正常回复。缺目标、范围不足或许可失效时，给出具体原因；超范围的事由房主在面板主动调整权限。
4. dot 暂停、离线或房间暂时没有主责时，两端消息都可保存并显示等待原因。恢复后按顺序投递，同一来源沿用同一工作。房主暂停某个具体工作时，该工作保持暂停，直到房主点击继续。
5. 房间任务在房间回传。微信任务在房间留记录，并回到发起任务的原微信私聊。房主能分别看到任务是否完成、微信是否已送达。
6. 房主重新授权时可一次勾选「同时继续未完成的任务」，选定清单随此次授权保存。后台核对回执后续办，已完成步骤直接复用。只更新权限时旧任务保持原状态。

**同权的定义**是同一房间、同一授权规则与相同的开工体验。消息入站时记录可用权限上限，开工及后续动作按当前有效范围继续核验。日常扩权自动作用于新消息，撤权立即拦截尚未派发的动作。房主也可在授权界面明确批准选中的旧任务续办，形成新的续办凭证。成员暂停和暂时离线可恢复，取消的工作保持终止。微信自定义权限模式可以比房间更窄。

## 2. 复现基线的链路

房间输入：

```
room_runtime.send
  → room_consumers.enqueue        写 dot_mailbox_entries，dirty_revision+1
  → room_consumers._wake          写 mcp_event_outbox（ROOM_INBOX 事件）
  → events.tick / reserve / deliver   带 wake_ticket 的 webhook 回调
  → dot：room_consumer_begin → room_inbox → room_reply 或 room_work_start → room_consumer_yield
```

微信输入：

```
weixin.tick → poll_once → commit_updates → channel_inbound.isolate
  → room_weixin_native.ingest     写 collaboration_messages，之后与房间输入同路
dot 回复：room_runtime.reply → weixin_delivery.queue_reply → weixin_parts → send_once
```

权力判定在 `channel_owner_authority.author()`：

- 面板消息（`origin='panel_owner'`）：作者是房主就算本人，执行范围在 dot 开工时按成员当前权限取。
- 微信消息（`origin='external_channel'`）：要有 `room_channel_owner_inputs` 记录，且入站时冻结的范围与现在的范围完全相等。

两条路在“入队之后”是同一套机制，所以第 1 类问题两边都受影响；第 2、3 类只影响微信。

## 3. 缺陷清单

级别按“离目标多远”排：高 = 消息丢在半路或回不去；中 = 同权不成立或接入不稳；低 = 体验和边界。

| B2 | 高 | 微信任务许可撤销或范围变动后，dot 的回复不回微信 | `weixin_delivery.py:54`、`room_weixin_native.py:747-761` | 是 | P5 |

| B4 | 高 | 房间唤醒回调重试时投递已过期的 `wake_ticket` | `events.py:879` 只检查旧邮箱事件 | 是 | P1 |

### B1 暂停或无主责期间的房间消息不入队

`send()` 只在 `routing.state=='queued'` 或原因是 `member_not_connected` 时入队。成员暂停（`member_paused`）和房间没有可用主责（`lead_member_required`）时，消息只保存。之后恢复成员或设定主责的路径都不补投。

复现：暂停成员 → 发消息（界面显示“已保存，等待恢复连接”）→ 恢复成员。`dot_mailbox_entries` 里没有这条消息，推进 20 分钟并反复 tick 后仍然没有。

### B2 回复不回微信

`queue_reply` 里，原生房间的来源走 `reply_author()`。来源有 `room_channel_owner_inputs` 记录时调用 `author(source)`，许可被撤销或范围变了会抛错，外层 `except DevError: return None` 直接放弃投递。

没有被授权过的微信消息反而能收到回复（走的是另一条不抛错的路径）。也就是说，被授权过的消息在授权失效后待遇比从未授权的还差。

复现：开通微信交办 → 微信发“请检查项目”→ 面板点“仅撤销工作许可”→ dot 回复“许可已撤销”。回复保存在房间里，`weixin_deliveries` 为 0 行。收件箱说明（`ROOM_HANDLING`）恰好要求 dot 在这种情况下用 `room_reply` 说明原因。

### B3 明确未发送被当成未知

`finish()` 只看分项状态：处于 `sending` 的失败一律记成 `unknown`，不看错误类型。复现使用微信接口明确拒绝发送的 HTTP 429，消息也被记成 `unknown`。实际重试须按第 5 节 P4 核对响应语义。`tick()` 选件时要求同一联系人更早的分项全部终结，`unknown` 不算终结，后面的回复全部排队等人工处理。

复现：两条微信消息各回复一次，发送端返回一次 429 后恢复正常。推进 6 分钟后两条都没发出，状态是一条 `unknown`、一条 `queued`。

### B4 过期票据被投递

`ready()` 里“票据过期就不发”的检查只对 `MAILBOX_EVENT` 生效。`ROOM_INBOX_EVENT` 的票据同样只有 600 秒，重试时复用同一个事件体（`issue_ticket` 注释：重试保持字节一致，即使已过期）。重试间隔是 30、120、600、1800 秒，第三次起就可能带过期票据。

复现：回调先返回 503，推进 700 秒后恢复。dot 收到两个回调，其中一个的票据在 `room_consumer_begin` 时报 `DOT_WAKE_TICKET_EXPIRED`，而这次投递被记成 `accepted`。

### B5 提醒只有三次

`recover()` 的条件是 `wake_count<3`，间隔 30、120、600 秒。三次之后只有新消息入队才会把计数清零。宿主离线十几分钟以上，消息就一直躺着。

复现：发一条消息，dot 不处理。前 40 分钟共 4 次回调（1 次初始加 3 次提醒），之后 5 小时 0 次，而 `dirty_revision > drained_revision` 一直成立。

### B6 微信消息的权限是冻结的

入站时把当时的范围写进 `room_channel_owner_inputs.scope`。`_author()` 要求 `current == saved`，范围里包含每个项目的版本号和摘要，所以任何变动都会不等。

复现：同一时刻发一条微信消息和一条面板消息 → 在权限设置里给同一项目、同一能力加一个 7 天后的截止时间 → 微信消息 `authenticated=False`（`CHANNEL_OWNER_SCOPE_CHANGED`），面板消息仍然是 `True`。

常规自动处理保持“新增权限用于新请求”。房主也可以明确续办选中的旧任务。当前偏差来自两端使用了不同的取权时机，以及微信用整份快照相等代替逐项核验。第 5 节 P8 给出统一规则。

### B7 无关输入让回复被拒

`guard_session` 要求 `expected_inbox_revision` 严格等于当前 `dirty_revision`。任何入队都会加一，包括别的话题的消息、别的工作的通知。连续发几条消息时，dot 要反复重读才能回上一条。

复现：发 A → dot 读收件箱 → 发无关的 B → dot 回 A，报 `ROOM_INBOX_CHANGED`。

### B8 订阅 24 小时过期后的表现

- `subscribe()` 把有效期上限定在 86400 秒。宿主不续订就过期，成员变成“需要恢复连接”。
- 过期后 `send()` 仍然只看 `grant_id` 和 `connection_proof_hash`，给房主显示“已发送，等待 dot”。
- 重新订阅时 `reset_verification=not active`，探测状态清空，写入类接口在重新完成读取和回复探测前都不可用。

复现：推进 86401 秒 → 成员状态 `degraded`，新消息的路由仍是 `queued` → 重新订阅后状态 `verifying`，`probe_replied_at` 为空。

### B9 微信不跟主责

`ingest()` 用的成员来自 `binding['native_member_id']`，绑定时写入后只有重新绑定才会变。面板默认投给房间当前主责（`recipient()`）。

该成员暂停或移除时，`_valid()` 抛 `WEIXIN_MEMBER_REMOVED`，`claim_poll()` 每 60 秒退避一次，微信这边完全不收件；同期的面板消息至少会保存。

复现（暂停部分）：暂停绑定成员后 `claim_poll` 返回空，账号原因码 `WEIXIN_MEMBER_REMOVED`，退避 60 秒。换主责后微信仍投旧成员这一点来自读代码，旧版原型对拟议行为有测试（`test_wechat_follows_the_room_lead`）。

### 其他观察（未复现，供排期参考）

- `_visible_message()` 判定不可见的消息不会出现在收件箱，也不会被确认，界面一直显示“已发送，等待 dot”。引用了某个项目来源的面板消息，在成员没有该项目读权限时会落入这种状态。
- `ingest()` 的 200 条积压上限按“未确认”计数，上一条说的不可见消息也算在内。
- `recover()` 每轮最多唤醒 4 个成员，但翻页游标按整页推进，成员很多时后面的要等一整圈。
- 原生路径把缺失的微信时间戳存成字符串 `'0'`，旧路径存空串。`room_weixin_native.py:611` 的 `prior['provider_created']` 因此恒为真，“首版没有创建时间、修订版有”的消息会报 `WEIXIN_DUPLICATE_CONFLICT`。这是批次级错误，会保留游标。微信是否真会发出这种消息我没有证据。

## 4. 两条入口的共同规则

| 场景 | 两边都采用的规则 | 微信另外核验 |
| --- | --- | --- |
| 明确任务 | 有可验证的本人身份、目标明确、操作在有效授权内，直接开工 | 有效私聊绑定、账号和联系人匹配、本人交办许可有效 |
| 消息已经排队后扩权 | 旧消息自动处理仍使用原权限上限。此次明确选择续办的旧任务使用新的续办凭证 | 独立权限模式还要服从该微信渠道的限制 |
| 收窄、到期、撤销 | 先停止受影响的后续动作。重新授权可批量续办明确选中的任务 | 单独撤销微信交办立即阻断该入口的工作；续办要重新具备有效的原来源授权 |
| 暂停、离线、无主责 | 先保存，记录具体等待原因。恢复后投递一次 | 私聊绑定仍有效时继续收件。解绑、账号失效、房间停用走各自的停用逻辑 |
| 主责变更 | 新消息走当前主责。已投递、指定成员、已开工的任务保留原归属 | 跟随房间模式只变路由。独立授权仍绑定原指定成员 |
| 结果回传 | 同一个工作记录及状态，支持定位原消息 | 返回原绑定私聊；任务授权失效时只允许受控的状态回执 |

房间和微信的传输限制继续由各自通道执行。微信引用消息映射到 `work_id` 需要先核对真实协议字段，当前可以用房间继续已有工作。

## 5. 建议代码和改动位置

以下新增函数和字段是拟议接口。片段分为可独立验证的纯函数和用于说明事务顺序的接入伪代码。实施时沿用项目的授权、收件箱、游标、幂等回执和房间事件机制。

### P1 过期票据停止发送（B4）

在 `hub/collaboration/events.py::ready` 将现有的过期检查扩展至房间收件箱事件，保持探测事件行为：

```diff
-            if event['name'] == MAILBOX_EVENT and not json.loads(event['data']).get('test'):
+            if event['name'] in {MAILBOX_EVENT, ROOM_INBOX_EVENT} and not json.loads(event['data']).get('test'):
```

过期投递记 `dead_letter / wake_ticket_expired`。有待办的成员由恢复流程生成新事件和新票据。原事件重试时的事件体仍固定，避免同一事件 ID 对应两套票据。

### P2 暂停期间收件与恢复补投（B1、B9）

- 在 `hub/collaboration/weixin.py` 的 `claim_poll`、`commit_updates` 和 `replay_deferred` 增加入站专用校验。原生房间入口从 `room_weixin_native.py::_valid` 拆出绑定校验，允许路由查询返回空成员；现有 `require_member=False` 仍调用 `rooms.member()`，单改该参数覆盖不了无主责。继续校验房间启用、房主、绑定、微信账号、凭据版本、世代、联系人及 poll fence。配对、开工和回传沿用各自的严格校验。
- 两个入口都以 `collaboration_messages` 为准，先保存消息、入站权限上限和路由状态。没有可投成员时保存为 `waiting`，区分暂停、离线待恢复和无主责。当前主责的解析复用 `room_runtime.py::recipient`。成员可用但宿主未就绪时，可沿现有机制先入邮箱，面板仍显示等待连接。
- 在微信轮询事务内保存去重记录、消息、附件任务和待投状态，再提交供应商游标。积压预算同时计入未投的 `waiting` 与邮箱未处理消息，同一消息只计一次。超过预算走现有加密延迟队列；该分支若已推进游标，需一并保存首次观察时的授权证据，缺证据时重放只能作为聊天。
- 在 `rooms.py` 的恢复成员、设主责、首位成员接入处触发补投，并用 `room_consumers.py::recover` 的后台周期补齐重启和超批次。用房间序号升序分页，每批有上限；按可投条件查询，或持久化扫描位置，避免被无法投递的头部记录卡住。现有同一成员跨消费世代的 `catch_up` 继续处理已入邮箱的记录。
- 重放前核对最新消息版本、摘要及原渠道身份。原消息被编辑、撤回或来源被解绑时，使原任务失效；编辑内容只能按现有修订规则显示与审计。解绑后重连不能接管旧绑定的消息。

以下伪代码展示补投事务。把消息状态、稳定邮箱引用和唤醒 outbox 一次写入，外部回调由现有 outbox 发送。

```python
def dispatch_waiting(message_id, principal):
    with store.transaction():
        message = load_latest_waiting_input(message_id)
        if message is None:
            return
        if not inbound_identity_still_valid(message):
            mark_waiting_terminal(message, reason="source_unavailable")
            return
        member = resolve_saved_recipient_or_current_lead(message)
        if member is None or not can_queue_for(member):
            return
        if not compare_and_set_waiting_route(message, member):
            return
        room_consumers.enqueue(message, member, principal)
        rooms.change(message["conversation_id"], "message", message["id"], message["version"])
```

三层幂等分别使用微信供应商消息身份和版本、`enqueue_ref` 的成员／世代／对象／版本引用、`room_work_sources` 与开工回执。换主责只迁移尚未分配且允许走默认主责的等待消息，不复制已入邮箱或已开工的工作。接续已有工作的等待消息仍需保留原工作绑定和权限；工作已终结时显示原因。

### P3 仍有待办时继续唤醒（B5）

`room_consumers.py::recover` 保留 30、120、600 秒的快速提醒，随后降低到每 30 分钟一次，持续 24 小时。保留订阅、暂停和有效消费租约检查。达到上限后保留待办并显示「等待 dot 恢复」，在连接恢复或房主显式恢复时重新检查待办。每轮按实际扫描进度续扫，避免成员数量增加后跳过整页后半段。

```python
FAST_WAKE_DELAYS = (30, 120, 600)
SLOW_WAKE_DELAY = 1800
MAX_WAKE_ATTEMPTS = len(FAST_WAKE_DELAYS) + 48

def wake_delay(attempts):
    if attempts < len(FAST_WAKE_DELAYS):
        return FAST_WAKE_DELAYS[attempts]
    return SLOW_WAKE_DELAY
```

### P4 自动处理传输故障，并隔离待核对的回复（B3）

#### 先复用分段，再处理确定错误

`weixin_delivery.py::queue_reply` 已按 UTF-8 字节数将文本拆成不超过 3000 字节的片段，并为每段生成稳定 `client_id`。继续复用这套分段，在最终请求编码后、转入 `sending` 前检查完整请求大小，覆盖上下文、附件元数据和 JSON 开销。超限的未发送文本可在此阶段重新分段并固定新分项，已尝试发送的分项保留原内容和标识。单个附件或固定协议字段超限时，在原任务显示原因。正文分段应保持完整文字与顺序。

`weixin_protocol.py` 的 `WEIXIN_REQUEST_LIMIT` 是本地请求体过大。相同请求直接进入明确错误处理。对经过协议或测试确认未发送的 `WEIXIN_RATE_LIMITED`，在 `weixin_delivery.py::finish` 沿用原 `client_id`，取有效 Retry-After 与指数退避的较大值，至多六次。重试只由后台完成，耗尽后记录 `rejected` 和原因，并结束本次重试。

```python
def rate_limited_delivery(attempts, now, retry_after_seconds):
    if attempts >= 6:
        return "rejected", None
    backoff = min(900, 15 * 2 ** attempts)
    return "queued", now + max(backoff, retry_after_seconds)
```

调用方继续解析、校验 Retry-After 和核对发送租约。网络读超时、发送后的 5xx、进程中断而无回执时，保留 `unknown` 和原发送证据。后续工作不得据此推断已经送达。

#### 用回复之间的依赖决定阻塞范围

当前 `tick` 和 `claim` 都把同一联系人的最早未结束分项作为屏障。一条 `unknown` 会阻塞此联系人的所有后续回复。建议同时调整两处调度，使用服务端保存的消息来源和工作关系确定依赖。

| 关系 | 调度规则 |
| --- | --- |
| 同一条回复中的文本与附件分项 | 按 ordinal 顺序发送，前段待核对时暂停后段。前段明确失败时把依赖它的余段标为本次回复未完成，避免单独发送残缺结尾 |
| 同一任务的阶段进度、最终结果，或明确引用前一回复的后续消息 | 保持语义顺序，前一条待核对时保留阻塞 |
| 来自另一项任务或另一条独立闲聊的回复 | 无依赖且原身份与回传权限有效时继续发送 |
| 正在准备或发送且租约仍有效 | 同一联系人仍只有一个发送者。租约结束并记录结果后，才选下一条可发送回复 |

增加可索引的 `ordering_key` 和必要的 `depends_on_delivery_id`，由服务端从当前工作 ID、来源话题与 reply 链计算。每次先选出每个顺序组可发送的最前分项，再在各组间按原创建顺序公平调度。该候选判定供 `tick` 与 `claim` 共用，`claim` 在事务内重查状态与活跃租约。结果未知项仍保留原状态，只解除其对无关顺序组的阻塞。客户端提交的参数不能把有关联的回复标为独立。

存量投递先按现有 `source_message_id`、消息和工作关系补齐依赖。不能确定依赖时保守归到原屏障，后台诊断给出原因。保留已发送正文、回执和 fencing token；恢复和晚到的旧回执按原租约处理。手动核对始终挂在原回复详情，其他独立任务继续运行。长文本重排、多线程竞争、附件、迟到回执和历史记录迁移要一起验收。

### P5 撤权后仍能说明任务状态（B2）

在 `room_weixin_native.py` 与 `weixin_delivery.py` 将工作结果与系统状态通知分开。工作结果、附件和阶段进度在入 outbox 和实际发送前都验证原消息、房间、渠道、目标联系人及当前获准工作修订的范围。仅工作许可撤销而原绑定仍有效时，可由服务端按原因码生成固定的纯文本通知，例如「这项任务的授权已撤销，未执行后续操作」。此通知走单独类型和稳定去重键，不接收 dot 自由文本、项目内容或附件。解绑、换联系人、账号凭据失效时终止旧回传。房间中仍展示相应状态。

### P6 两种来源共用 dot 参数（B10）

在 `room_consumers.py::_entry` 为可见的有效消息统一返回含 `source_message_id`、`source_version`、`source_digest` 和 `expected_inbox_revision` 的 `reply_arguments`。经 P8 核验且存在可执行范围的消息提供 `work_start_arguments`。沿用协议 `confirm_task: true` 表示宿主判断这是用户明确交办的任务，服务端在开工时复核同一来源、身份、版本和实际请求能力。宿主说明明确区分任务、闲聊和缺关键信息的请求。已经授权的明确任务不再向用户询问许可。

### P7 按话题判断聊天回复是否过时（B7）

`room_consumers.py` 与 `room_runtime.py::reply` 对纯聊天回复按来源话题检查更新；仍验证租约、fence、消息版本和已读到的来源。有同话题新消息、未处理的撤权／范围变动控制通知、来源修订时，要求重读。任务开工、关联工作回复及汇报继续使用现有严格版本检查。

### P8 统一入站权限上限和实时核验（B6、B11）

1. 在 `room_runtime.py::send` 与 `room_weixin_native.py::ingest` 的事务内写入同一格式的不可变权限快照。键含房间、来源消息 ID、版本和摘要；微信复用已有 `room_channel_owner_inputs` 的来源证明，并校验绑定、账号、联系人、授权记录和凭据世代。面板来源仍需验证登录房主。快照保存按项目、环境和授权目标划分的能力、期限及授权修订锚点。无主责时可记录已核验的房间和渠道权限上限，实际开工必须再与获准接收该消息的成员有效授权求交。
2. 用 `room_permission_revisions` 和相关授权的撤销代际验证自入站以来的连续性。房间规则、渠道、成员和项目授权的收窄、到期及撤销均须被记录或可证明。某项权限中断后，自动处理不再使用该权限。明确批准的旧任务通过独立续办凭证重新准入。无关配置变动不影响原范围内仍连续有效的权利。对缺少完整历史的授权路径，在同一授权写事务记录规则与能力的撤销代际。范围整项撤销时推进来源级代际；逐项收窄时只推进受影响的项目、环境、能力或目标代际。恢复、补投和开工使用同一份入站记录，避免用最新设置补写旧记录。
3. 在 `room_goal_scopes.py::prepare` 逐项目、环境和目标核对请求。只对同一授权目标比较权限，避免把不同项目或授权分支的能力拼成一项。开工校验与写入工作使用同一事务，保留目标、能力、路径等现有约束。对正在运行的工作，`check_work`、`operation_guard` 每次派发前复核原工作规则、来源渠道和当前范围。撤权发生后停止尚未派发的操作；对已交给执行器的步骤记录回执，并按现有取消机制处理。
4. 授权生效时间沿用现有严格边界。授权前消息、无可信时间或无法证明完整快照的历史消息可以聊天和显示状态。来源和原内容仍可核实时，可在授权页加入续办清单；来源无法核实时提示重发。迁移保留旧记录。已开工的旧工作保留原工作快照，续办增加新修订并按当前有效授权检查。

以下纯函数展示单个已匹配项目／环境／授权目标的交集。调用方负责精确对齐规则键并验证权利连续性。缺任一来源的规则时跳过该项；路径、额度等其它约束继续使用现有授权检查，不能从本函数返回值单独推断可执行权限。

```python
def intersect_grants(now, original, *live_grants):
    """Return the continuously authorized capabilities of one matched rule."""
    capabilities = set(original["capabilities"])
    targets = set(original["execution_targets"])
    deadlines = []
    for grant in (original, *live_grants):
        if grant is None:
            return None
        capabilities.intersection_update(grant["capabilities"])
        targets.intersection_update(grant["execution_targets"])
        if grant["expires_at"] is not None:
            deadlines.append(grant["expires_at"])
    expires_at = min(deadlines, default=None)
    if expires_at is not None and now >= expires_at:
        return None
    if not targets:
        capabilities.discard("execute")
    if "read" not in capabilities:
        return None
    return {
        "capabilities": sorted(capabilities),
        "execution_targets": sorted(targets),
        "expires_at": expires_at,
    }
```

常规自动处理时依序纳入入站快照、连续有效权限、房间规则、来源渠道规则和成员实时授权。工作开始后再纳入其当前获准修订的冻结规则。明确续办改用新续办凭证的范围和有效期作为上限，以新批准时间为连续性起点；旧记录保留用于审计和回执去重。微信新授权时间由服务端记录，时钟异常时给出具体状态并保留严格生效边界。

### 重新授权时一次续办

授权页在当前权限摘要下面展示「同时继续未完成的任务」，默认关闭。打开后默认选中本次新权限足以完整续办、来源可核验的候选，支持全选和单选，并显示任务名称与剩余操作。只确认一次「保存并继续」。普通断线或成员暂停恢复继续走自动恢复；明确取消的工作、已撤回或已修改的原任务不进入候选。

`room_runtime.py::control` 已有 `resume`，`room_goal_recovery.py` 已有 `restore_binding` 和 `takeover`，包含回执、成员版本和原意图检查。它们目前保留原权限与原到期时间，不能直接用来重新批准撤销或到期的旧工作。扩展现有恢复模块，增加显式的续办授权修订；将其传入原有工作准入、每步派发和回传检查。原快照保留，新的修订只批准清单中剩余操作及本次显示的范围和期限。

建议的批量请求形状如下。字段属于拟议合约，需要在 `shared/room_runtime_contracts.py` 及对应公开入口实现。

```json
{
  "policy_preview_digest": "preview-of-new-permissions",
  "continuation_preview_id": "reviewed-task-selection",
  "continue_selected": true,
  "selected_task_ids": ["work-a", "waiting-source-b"],
  "idempotency_key": "save-and-continue-once"
}
```

预览由服务端绑定房主、房间、新权限摘要、候选工作或消息版本、原内容摘要和原意图。保存时核对权限预览并记录本次选择，生成有界的续办批次。每个任务在自己的事务中重查来源、当前权限、剩余动作和已有操作回执，以批次 ID 与任务 ID 形成稳定回执。清单外的新任务不会被加入；单项已变化就显示跳过原因，其它符合条件的任务继续。重试取回同一批次和同一任务的结果，避免重复恢复。

- 已有工作保留 `goal_id`，新增续办修订并推进相应意图和协调者版本，旧租约与旧执行参数失效。已完成步骤复用回执，明确未派发的步骤继续，有未确认结束或结果未知的执行操作时只挂起该项。
- 尚未开工的来源建立新的本人续办意图，引用原消息及原摘要。新凭证以本次批准的目标与范围作为上限，开工仍走 `room_work_sources` 和原幂等回执。
- 新权限只能来自房主当前有权授予的范围。授权被再次撤销时立即停止未派发动作。原账号或联系人绑定已失效的微信任务不自动迁到新私聊，界面要求选择可核验的恢复路径。
- 未勾选续办时只更新房间权限。房主无需逐条重发仍可核验的旧消息，完成授权后以一份批次结果展示已继续、待核对和跳过的任务。

这份续办记录是新的明确授权证据。常规后台补投依然只使用旧消息已经具备且连续有效的权限。

### P9 跟随当前主责（B9）

跟随房间模式使用与面板相同的默认收件人解析。配对身份与投递路由分开：绑定仍证明原账号、联系人和房间，主责变更只更新路由。房主启用时需明确同意跟随该房间已授权的主责；旧的成员专属授权不自动扩大。切换时使旧的轮询租约失效，保留已持久化的来源身份和游标；路由变化不得让有效延迟消息因绑定版本变化被误隔离。已经交给旧主责的工作保留原归属，回传同时复核其来源和原绑定。

### P10 验证实际宿主的续期能力（B8）

`events.py` 返回的 `refreshBefore` 是当前订阅到期点。接入时实际验证宿主是否有持久运行的续期逻辑，包括进程重启后恢复定时任务与游标。支持的宿主提前续订，沿用原身份、订阅 ID、回调、签名密钥和约定 TTL，用单个调度者避免并发续订。临近过期时仍保持失败退避，并在到期后展示具体连接状态。

没有后台定时能力的宿主使用房间专用的托管续期契约。房主在首次接入的同一份摘要里批准「在房间授权有效期间保持连接」，由 Hub 的连接维护循环持久化续期安排。该契约单独记录房间、成员和绑定世代、订阅、回调与密钥摘要、批准的连接终点。每次续期都复核这组身份、当前授权和回调验证结果，再按约定 TTL 签发下一段连接租期。房主或宿主取消订阅、房间停用、成员移除或授权到期后，停止续期。凭据或回调变更走相应重验证流程。

托管续期属于拟议功能，需要落在 `events.py` 和 `rooms.py` 的现有生命周期及配置持久化中，并更新公开接入合约。已有短 TTL 订阅只在明确选择此契约后加入托管。后台可维持连接租约，但宿主离线时仍需等待宿主恢复，不能仅凭回调可达就标记 dot 已处理任务。

恢复订阅时使用已保存的签名游标，并处理服务端返回的历史截断提示。现有实现过期后省略游标会从当前事件开始，因此要在连接恢复后主动扫描持久化待办，必要时生成新的唤醒事件。消息归属与开工幂等继续依据收件箱和工作记录。

上线前必须用实际使用的 dot 宿主，分别验证跨过一个真实订阅 TTL、短 TTL 失败恢复、宿主重启和长期无消息后的再次交办。只有自动续期和重新交办均跑通后，才将该宿主标为支持长期自动处理。

### P11 让状态对应真实进度（B8）

`room_runtime.py` 结合 `rooms.py::state` 和消息、工作、投递回执投影状态。在 `web/collaboration-room-store.js` 与 `web/collaboration-room.js` 展示「已保存，等待主责」「已保存，等待 dot 恢复」「待 dot 处理」「处理中」「已完成」；微信回传另显示「待发送」「已送达」「送达待核对」或明确失败原因，待核对状态挂在原回复上。微信供应商仅确认受理时展示「微信已受理」，有送达证据时才显示「已送达」。收到回调和收到工作结果是两个不同事件。

## 6. dot 接入与开通

### 开通流程

房主先在协作房间连接 dot，完成现有读取、回复探测，再在房间配对原微信私聊。在「跟随房间」模式集中显示授权摘要，包含房间、主责路由、项目与能力、有效期、回传对象和撤销入口。房主确认一次。房间没有项目时可正常聊天，界面明确显示当前不具备开工范围。以后在面板授权时可以顺带选择续办仍可核验的待处理任务。首次摘要一并显示连接保持方式和期限，按实际宿主能力选用后台续订或房间托管续期。已配对且有有效许可的房间跳过已完成步骤。

### 首版合并 begin 与首次读收件箱

在 `shared/room_consumer_contracts.py::RoomConsumerBegin` 增加可选布尔字段 `include_inbox`，由 `shared/public_collaboration.py` 的公开协议和工具说明声明。旧宿主继续用 begin → inbox → reply 或 work start → yield。支持该字段的宿主可以省掉首次 inbox 调用：

```python
include_inbox: bool = Field(default=False, strict=True)
```

`room_consumers.py::RoomConsumers` 保持 `consumer_engine.py::FencedConsumerEngine.begin` 的票据兑换、身份、绑定世代、fence、租约和幂等校验。成功后对仍活跃的本次会话复用现有 `inbox` 的权限过滤、分页、体积限制、控制通知与附件引用，附加有界的第一页。读取不确认条目。幂等收据只保存原 begin 回执，不持久化消息正文；同键重放时重新校验活动会话，已结束或过期只按原协议返回回执。新增字段默认值从幂等指纹中省略，保持老请求的指纹。读取失败时保留已成功的租约，宿主改用标准 `room_inbox`。仅在工具协议明确声明字段时传参，授权或版本错误按原错误处理。

### 宿主处理约定

更新 `room_consumers.py::ROOM_HANDLING`、`rooms.py` 的连接探测指引和公开工具说明。两条入口共用一份短指引：

> 先读取当前回合的消息。明确交办且提供开工参数时，在服务端允许的项目和能力内直接发起工作。有歧义时只追问缺失信息。被授权或状态检查拦截时，按房间回复流程说明原因。处理完当前页后继续分页或交还回合。

结果用协作工具回写，宿主对话里的文字没有回传回执。权限来自服务端的授权记录和本次检查。收件箱为空时按现有 fence 和已读版本交还。

### 后续压缩回复与交还

首版保留显式 `room_consumer_yield`。之后可在 `shared/room_runtime_contracts.py` 和 `room_runtime.py::reply` 增加可选 `yield_after`，仅在完整回复已持久化、已读版本仍匹配且没有待处理条目时，用现有 fenced drain 完成交还。有新消息或控制通知则保持活动回合。加入该能力前，先解决会话结束后同键重试无法取回原回复的问题：复用已完成回执的只读路径，精确核对身份、原会话、fence、proof、幂等键和请求指纹，再返回同一结果。新动作仍需要活动租约。

## 7. 验证状态与自动化回归

## 8. 实施顺序

1. 先落地等待入队、续期及状态链路、过期票据、限流重试和受控状态回执。先补能复现丢消息、错误重发和送达状态的测试，再用原有渠道回归验证。
2. 加入权限快照、房间与微信共用开工参数、主责路由和批量续办。常规自动处理与明确续办分别验证，覆盖当前工作、旧数据和重复提交。明确选择续办的权限修订必须进入原有准入和每步派发检查。
3. 接入宿主首页、处理指引和开通摘要，确认实际 dot 的续期方案。完成两端读取、写入、执行和断线续办验收，再将方案设为新房间默认流程。按话题回复和自动交还可独立验收，自动交还依赖上述兼容回执。旧宿主继续可用。

新快照应支持兼容迁移。回滚时保留待投消息、来源版本、已开工记录和投递回执。回滚到旧处理器前暂停新契约的任务准入，保留已有队列待兼容版本处理。

## 9. 真实房间与微信验收

使用隔离的协作房间、测试项目、已绑定的测试微信私聊和实际使用的 dot 宿主。测试项目准备固定输入和专用输出目录，依次授予读取、写入和受限命令执行权限。收集脱敏后的来源消息、工作、操作与投递回执及各阶段时间，记录服务和宿主版本。两端新发的消息各自创建工作；同一来源消息的事件重投或恢复沿用原工作。

| 场景 | 通过条件 |
| --- | --- |
| 开通 | 房间完成 dot 读取与回复探测，微信完成配对和一次任务授权。相同摘要显示范围、连接保持方式和撤销入口 |
| 两端分别读取 | 从房间、微信各发「读取测试项目的 `fixture.txt`，返回第一行」。dot 无需再确认，各创建一条工作，得到相同结果并回原渠道 |
| 两端分别写入 | 指定测试输出目录中不同的文件，写入给定文本。核对实际文件、操作回执与微信回传。未授予写权限时明确阻断，授权后新任务直接执行 |
| 两端分别执行命令 | 在测试项目执行已批准的确定性脚本，将输出保存到指定文件。核对进程实际退出码、结果文件和操作回执。超出目标或能力的请求被阻断 |
| 完成一步后宿主断线 | 任务有两个可独立核验的步骤。第一步完成并有操作回执后中断宿主，恢复后复用第一步结果并继续第二步，核对第一步执行次数 |
| 已派发操作仍在运行或结果未知 | 中断宿主后重连，从原操作 ID 取回实际状态。未确定结束前等待该操作，避免重新派发。同房间独立任务继续 |
| 两边发闲聊 | 两边正常回复，工作数不增加。微信回复只回原私聊 |
| dot 暂停或无主责后恢复 | 两边分别发两条消息，重启 Hub 后待投仍在。恢复 dot 或补设主责后按保存顺序入邮箱，逐来源核对只建一次工作。房主明确暂停的具体工作保持暂停 |
| 重复事件与重连 | 对同一来源重复回调、重试开工并重启。过期票据被丢弃，新票据可恢复。核对同一工作 ID、操作回执与逻辑回复 ID |
| 主责切换 | 切换前已投递或开工的工作保留原成员，切换后新消息到新主责。无主责期间允许默认路由的等待消息在恢复后投递 |
| 只更新权限 | 两端排队中的旧任务均不自动获得新增权限。未勾选续办时，权限更新成功且旧任务保持原状态 |
| 批量保存并续办 | 撤权或到期后，选择多项未完成任务一次授权并续办。两边按新批准范围继续，已完成步骤复用。重复提交返回原批次，未选中和清单外新任务保持原状态 |
| 续办过程中变化 | 预览后取消一项、修改另一来源、再次撤销另一项权限。保存后逐项显示跳过或阻断，其它仍符合本次批准的项继续，不追加批量批准范围 |
| 工作与回传期间撤权 | 停止尚未派发的动作。原微信绑定有效时可回系统状态，解绑后停止旧微信回传。房间里可查原因 |
| 自动续期 | 在实际宿主上跨越一个真实订阅 TTL，期间无需房主操作。另覆盖短 TTL、宿主重启、无消息期间到期恢复。再次从两端发任务均自动处理，记录实际采取的宿主续订或托管续期 |
| 撤销续期 | 房主解除连接或宿主取消订阅后，维护循环停止续期，旧回调和旧凭证不能恢复已解除连接 |
| 文本分段与传输预算 | 发送足够长的中文及混合字符，核对分段后文字完整、顺序正确。完整请求超限在发送前处理，单附件无法发送时给出原因 |
| 限流重试 | 在测试替身注入一次明确 429，再恢复发送，验证固定发送标识和一次最终受理。连续限流耗尽后显示该回复失败，独立回复可继续 |
| 结果未知与依赖组 | 在测试替身模拟发送后超时。一条多段回复停在待核对分项，后续依赖段暂停。另一个独立任务的回复自动继续。进程重启和并发 worker 下同样成立 |

外部发送结果未知时，以平台回执、发送证据和用户实际收到的内容分别登记结果。稳定发送标识不能单独证明微信已经送达，也不能单独证明下游绝无重复。工作去重以来源和操作回执核对，实际副作用另外检查输出文件或执行记录。

每个场景独立记录「已保存」「已开工」「操作结束」「结果回房间」「微信已受理／实际收到」及耗时。普通故障由后台按既定退避和恢复周期处理；只有权限缺失、来源不可核实或操作结果无法判定的具体项等待房主处理。实际宿主续期与两端读写执行全部完成后，才能将“长期直接交办”标为验收通过。
