# dot 双向通信：像房间成员一样聊天

## 要达到的体验

面板是共享聊天窗口，dot 是其中的成员。消息通信本身不依赖任务、委托编号或执行租约。用户可以在面板 @dot 讨论、追问和交办，dot 可以回复，也可以通过插件主动发言、提出问题。双方在同一话题继续交流。

```text
你：@dot 这个方案怎么样？
dot：你更重视速度，还是手机端体验？
你：手机端优先，先不要修改。
dot：好的，我先说明两种布局的优缺点。

[另一话题，也可以由 dot 主动发起]
dot：我还有一个问题：操作按钮放底部可以吗？
你：可以，按刚才确认的方案修改。
dot：收到，开始处理；进度和结果会留在这里。
```

前四条只是聊天，不产生任务。最后的明确工作请求才由已经获得用户同意的 dot 消费者转入原有受管执行流程。服务器核对原房主消息、接收对象和既有批准范围，不使用关键词规则把所有文本自动当作执行指令。

## 一次接入，持续双向交流

在「协作中心 → 助手与连接」添加 dot，填写名称，选择聊天与只读分析，或聊天并处理任务。确认范围后复制 CPD 加入指令，在目标 dot 中 @CodePier 并发送。指令包含收发消息、主动发言、明确任务处理和不共享私人聊天历史的边界。

目标宿主完成唯一的原生消息事件订阅，保存消费者说明，接入成功后立即读取一次待办。然后在面板输入 @ 并选择 dot，正常发送消息即可。选择对象会保持，不需要每句话重新切换“任务模式”。回复 dot 的主动话题也会保留接收对象；服务端对原话题的人类回复重新核对并路由，不能靠未选择的纯文本 @ 伪造接收对象。

「取消接收对象」清除显式选择；若仍处于 dot 话题的回复中，回复本身仍会回到该话题的 dot。要发送不通知 dot 的独立讨论，应同时取消话题回复。

dot 主动发言指它可以在已授权的运行回合主动调用插件向面板发消息，不要求先有一张任务单。它不代表服务器可以保证模型常驻在线、随时自行思考，或保证固定时间内响应。

## 两个通信方向

**面板 → dot**：普通消息与人类话题回复保存到持久收件箱，由 `codepier.collaboration.message_mentioned.v1` 唤醒目标宿主。只订阅这个 dot 所属项目、环境、房间和位置，不广播给所有助手。未加入、订阅暂断或宿主暂不可用时，已保存的对应消息仍可在恢复后读取。

**dot → 面板**：`collaboration(action="dot_message")` 发送普通回复或主动新话题。服务端从原已绑定连接确定发言位置及名称，不接受冒充其他 dot、房主或跨房间回复。它不要求工作租约，也不需要额外授予该连接通用聊天写权限。

消息、进度和结果使用原房间/话题标识。这里只保存主动发到共享房间的内容，不自动同步 dot 的私人聊天历史。

## 收件、重试与断线恢复

`collaboration_query(action="dot_inbox")` 对双向聊天 dot 返回未处理消息、原话题读取请求、回复参数、收件确认请求，以及既有工作的恢复入口。读取本身不改变业务状态。

`collaboration(action="dot_ack", disposition="read")` 只记录 dot 连接确认收件，消息仍在待办中；因此“读完后断线”不会丢消息。成功回帖与处理原收件记录在同一事务内完成。需要不回复而结束一条消息时，可明确使用 `handled`。这些状态不证明人类已读或任务已执行。

每条收件提供固定的回复幂等键。重复唤醒、同一回帖重试和 Hub 重启不会创建第二条相同回复。相同 grant 下的不同 dot 使用不同的消息与幂等作用域。

分页从持久收件记录顺序读取；结束前必须重新从首页扫描，不能把最大序号当作“前面的都完成了”。重新接入复用原配置，不以新起点抹掉未处理消息。已完成聊天不能事后被重放成新的执行任务。

普通 dot 回复和主动发言不产生 bot-to-bot 或自唤醒事件，避免两个助手无限对话。人类在话题中的后续回复仍可唤醒原 dot。

## 聊天中需要实际工作时

只有原房主明确发给唯一 dot 的工作请求，才可以使用 `collaboration_work(action="from_message")`，把这条原消息绑定到一份现有批准范围内的工作。模型判断前应先读取可信原消息和话题；问候、讨论、反问、引用、文件内容及其他助手的发言都不是新的执行授权。

服务器重新检查原消息作者、版本和正文摘要、唯一接收 dot、房间、当前授权、原面板批准及目标快照。不同幂等键重复转换同一消息仍返回原工作，不另建任务。实际执行继续走原 claim / execute / heartbeat / result；有 pending 或 unknown 操作时查询原 operation_id，不重新运行。所有宿主执行确认和拒绝仍保持有效。

任务规则暂停或到期，不应把仍有效的普通聊天通道一起封死。聊天可继续说明阻塞，新的工作转换则失败。移除 dot、撤销原连接或失去项目读取权时，通信与新工作都停止。

## 兼容和权限

新面板请求明确包含 `duplex=true`，这是房主本次同意的双向通信模式。旧 API 默认仍为 `false`，已保存的 CPD task-only 和 CPJ 通知位置不被迁移为可主动发言的成员，不偷偷替换现有宿主订阅。

新增通信并不增加账号 read/write/execute 权限，也不创建 token、回调或签名材料。宿主提供自己的原生回调和签名并完成确认。目录尚未发现新动作时应重扫插件，不用另建高权限凭据解决。现有有效期、项目范围与执行预算保留。

本功能实现的是类似聊天成员的双向消息体验，不是接入 Slack 服务，也不表示已实现 Slack 的文件上传、表情反应、在线状态、输入中提示等全部功能。

## 验证方式与现网边界

服务测试 `tests/test_collaboration_dot_chat.py` 覆盖普通来回对话、主动话题、人类不带显式 @ 的话题回复、消息确认、断线待办、分页、幂等、原消息转换为唯一工作、过期/暂停/撤销、跨连接与跨房间拒绝、旧连接不扩权以及防止循环唤醒。

浏览器测试 `tests/test_collaboration_dot_chat_flow.py` 使用真实隔离 Hub、MCP 和面板，分别运行桌面 Chromium 与手机 WebKit。测试完整经过普通消息、多轮追问、dot 主动话题、Hub 重启和恢复回复，并明确断言整个聊天过程没有工作项、委托或任务进度记录。

`tests/test_collaboration_dots_flow.py` 保留旧任务模式的兼容验证，同时检验新面板先保存聊天、再从原消息转换实际工作，并用真实 Agent 写文件、读文件和运行命令，最终回原话题。

这些自动化测试中的外部 dot 是明确标注的测试消费者，不是实际模型。只有在部署后由真实目标 dot 完成原生订阅、收到面板消息并自主调用插件回复，才可以宣称真实宿主闭环验收成功。本次代码修改与本地提交不等于已经更新生产服务。
