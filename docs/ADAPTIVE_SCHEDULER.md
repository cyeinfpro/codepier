# 并行与队列

> 本页描述当前源码。Agent 自适应执行调度自 1.24.0 引入；Hub 资源感知持久准入自 1.25.0 引入，可下载版本以正式 Releases 为准。发布与源码验收不代表生产节点已升级。

## 在哪里设置

设置中心 → 任务 → 并行与队列。选择你有管理权限的节点，设置自动调节、并发上限，或展开项目配额。留空表示继承节点配置；取消改动重新读取当前值。

保存采用版本检查，其他窗口修改后不会覆盖。界面区分「等待节点确认」「已生效」「节点离线」「升级 Agent 后生效」和「节点未接受」。出现网络错误时先刷新状态核对同一次保存，不反复提交。

## 如何分配资源

- 执行、文件操作和远程命令分开分配容量。项目按运行占用与轮转顺序公平准入，可以利用空闲余量。
- 配额是各个通道内的项目运行上限；子工作区保留原项目身份，不能靠新建 worktree 绕过配额。
- 同一路径写入和显式声明的资源冲突先等待锁，再等待执行名额。不会让等待锁的任务占满执行通道。
- 对远程命令还有每个已验证目标的并发上限。任务必须通过原有 VPS 授权和项目检查。
- Hub 持久准入与 Agent 执行并发是两层限制。旧 Agent、离线、过期或无有效资源报告时仍使用项目 32 / 节点 64 的保守上限，并保留 8 个新项目名额。有效健康资源报告可扩大有限的待完成队列，见下节；这不会提高 Agent 的执行并发配置。拒绝新请求不妨碍查询、取消或按原幂等键找回既有回执。
- 忙时减少后续准入，不强杀正在运行的任务。取消与超时继续使用原进程所有权、进程组和回执机制。

调用流水会分别说明等待本项目额度、远程目标额度、通道容量、资源压力或项目公平轮转。只传递固定原因枚举，不暴露其他项目的命令、目标地址或任务正文；阻塞任务仍逐条核验查看权限。旧 Agent 未提供原因时保留通用等待状态。

## 自动调节与降级

节点使用 CPU、可用内存和支持的平台 I/O 压力指标，连续健康采样后逐步扩大容量。压力升高时降低新任务准入，冷却期避免频繁振荡。严重内存压力暂停新增执行和远程任务，保留有限文件操作能力；指标缺失使用保守容量，不把未知资源当空闲。

Linux、macOS、Windows 采用各自系统计数器，不读取其他任务命令正文。并非所有平台都有 I/O 压力指标；界面不伪造缺失数据。容器资源限额会影响可用预算。已经运行的外部进程仍可能改变负载，所以这些限制不保证任意构建都不会耗尽资源。

## Hub 持久准入预算

仅当前认证 Agent 连接的心跳可提供 admission telemetry v1。Hub 检查 OS 计数器来源、数值类型、采样年龄（Agent 上不超过 15 秒）、调度配置 revision 和通道计数一致性；按 Hub 单调时钟计收包新鲜度，收包后时长加采样年龄不得超过 45 秒。重复采样不刷新时效、不计健康次数；持久 devices.info、客户端参数和旧连接不能用于扩容。升级 Hub 后仍须升级 Agent 才能提供此报告。

- 健康条件：CPU 使用率不高于 65%，可用内存至少 1 GiB 且不少于总量 20%，如有 I/O stall 则低于 10%。至少 3 次不同健康采样、冷却 15 秒后才扩容。
- 节点待完成预算取当前三个 Agent 通道容量之和的 8 倍，限制在 64–512；项目最多 256。8 倍是吸收短突发的排队窗口（约八轮容量），不是八倍执行并发，也不保证长任务的等待时间或吞吐提升。等待仍受原排队期限限制。
- 新项目保留额度为节点预算的 1/8，最少 8、最多 32；项目已有待完成操作后不能再次冒充新项目。额外保留有限读取空间；分类只看已验证的工具类型，不接受用户优先级。已知资源高压时，即便原重任务积压超过收缩后的普通预算，节点仍可保留最多 8 个待完成读取用于探查，每项目最多占 7 个，为其他项目留 1 个；读取仍受项目 256、节点 512、全局数量与字节绝对上限限制。旧 Agent 没有此例外。
- CPU 至少 90%、内存低于 10% 或 I/O stall 至少 25% 时迅速回到保守预算；严重内存压力暂停新重操作。恢复需要新鲜采样与冷却。解除内存暂停使用 Agent 同款、可在小内存机器上达到的恢复储备，连续 3 次安全恢复采样并经过冷却后先回到 32/64；随后重新累计 3 次满足至少 1 GiB 等健康条件的采样和冷却期，才可扩大预算，小于 1 GiB 的容器不会因此永久暂停。缩小预算只限制新准入，既有 queued/running/reconnecting/cancelling 操作继续保留并计数，不强杀、不丢回执。Hub 重启或连接替换后从持久操作重计，并重新等待可信报告。
- Hub 全局最多 4096 个活跃持久操作；每节点绝对最多 512。待完成加密请求另有项目 32 MiB、节点 64 MiB、Hub 256 MiB 上限，并留有限读取/控制余量。这些是数据库待完成负载保护，不代表全进程内存上限或历史记录保留策略。控制工具也最多占用 8 个节点控制名额，不能无限绕过限额。
- 饱和返回 PROJECT_BUSY / DEVICE_BUSY / HUB_BUSY、admitted=false、固定 queue_scope / queue_reason 和 retry_after_seconds。已有回执应查询原 operation_id，不能换新幂等键反复创建。过载退避 5 秒，内存暂停 15 秒，普通饱和 3 秒。
- 同幂等键恢复先于额度检查；查重、额度检查、插入在同一个 SQLite 写事务内完成。取消中和失联协调中的操作也占额度；终态释放额度。权限、撤权取消和发送前最后检查保持独立生效。

节点管理接口 /api/settings/scheduler 的 durable_admission 返回 node_pending_limit、project_pending_limit 和原因，明确指待完成额度；reported.lanes.*.capacity 才是 Agent 通道执行容量。原始资源样本不写入调用日志，也不在项目诊断中暴露其他项目或节点信息。

## 本机配置与面板覆盖

Agent 原配置文件的 scheduler 对象是本机边界：

- adaptive：自动调节；false 使用 initial 固定容量，但严重内存保护保留
- minimum、initial、maximum：执行通道最低、起始和最大容量
- read_limit：文件通道上限
- remote_limit、remote_target_limit：远程通道和单目标上限
- project_limits：按项目 ID 配置的各通道上限

整数范围 1–64；未知字段、布尔冒充数字、无效上下界会拒绝。Hub 保存的是显式覆盖，Agent 计算最终运行值；面板不能提高本机已配置的容量边界或项目约束。无需新增凭据，没有增加目录、项目、命令或网络访问权限。

## 升级与恢复

先升级 Hub，再升级 Agent。旧 Agent 不支持下发时只显示待升级，不将保存称为已生效。偏好保存在 Hub 现有数据中，经既有认证连接发送，重连重新核对版本。无效配置保留最后可用值和原生连接，界面不显示假成功。

回滚到旧 Agent 会恢复旧调度行为，不会应用新偏好。回滚前等待在途任务结束，并按原升级流程保留配置和数据。新版本下若要恢复本机默认，在面板清空覆盖后保存；不要删除整个配置文件。
