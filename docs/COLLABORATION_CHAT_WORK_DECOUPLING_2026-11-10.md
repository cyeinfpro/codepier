## 1. 结论与本轮取舍

v1 找到了正确的根因：聊天回复被整个成员的权限摘要、订阅健康和全局收件箱变化共同拦住。但它还不足以直接落地。主要缺口不是再少查几个字段，而是没有完整区分四件事：**当前身份是否有效、这一条内容是否仍可访问、这一项效果是否仍获授权、原效果是否已经提交**。

v2 保留原来的持久消息、工作、操作、回执、消费租约和 fence，不再新造一套调度器。改动集中在现有入口的判定顺序、原子提交、对象依赖和恢复语义。

v2.1 修正 v2 的产品边界：**用户始终在和同一个 dot 连续对话，讨论、执行、追问、修改和交付可以自然交织。** 不要求把每句话先分成“聊天”或“工作”，不引入两套输入框、人格或上下文。内部按具体效果记录消息、工作和原操作的不同生命周期。撤回尚未实施的 `chat / work_progress / work_publication` 回复三分类；第 9.2 节改为同一回复入口加可选的正式发表效果，第 4.3 节明确连续上下文，第 15.4 节按真实使用过程验收。

| v1 的缺口 | v2 的确定决定 |
| --- | --- |
| `begin` 重放仍先进入严格 `binding()`，订阅过期后拿不回原领取结果 | “恢复原领取”先核对身份、原请求和原票据；只有新领取要求可用唤醒路线 |
| 读取入口改用宽限 `session_binding()`，却不要求证明自己有已领取回合 | 路线失效期间的读取必须提供同一已领取回合的有效凭据；没有回合不能借宽限进入 |
| 权限变化时覆盖保存的 `scope_digest`，抹掉原准入证据 | 原准入摘要不可改写；当前观察摘要单独记录；回合固定服务端策略版本 |
| 工作与汇总仍因无关聊天增加 `dirty_revision` 而失败 | 对已核对的入口使用来源、话题、工作意图、主责世代和具体对象版本；全局版本仅作变更提示与排空 CAS |
| `yield_after` 的历史回执容易被误读为当前回合已交还 | 历史效果与当前回合状态分开返回；重放不交还新回合、不再排投递 |
| 工作在后台进行时仍可能让消费回合不能交还 | 消费通知有“已持久处理／移交”证据；工作完成仍由原工作与操作回执证明 |
| 只说服务器无法收回模型上下文 | 保留事实边界，同时约束跨项目自由文本、结构化引用、投影和面向房主的系统状态 |
| 回退等同改一个开关 | 配置回退、客户端字段回退和旧二进制回退分别设计；安全撤销闸永不因回退恢复 |

### 1.1 用户应得到的体验

用户在房间或微信发一句话，系统保存一次原输入，dot 在当前授权内承接同一段协作。可以先讨论再执行，也可以一边说明一边处理；围绕工作提问不要求进入任务页面，交办也不要求重新复制上下文。长工作有需要时在原时间线显示可展开状态，工作列表只是同一记录的辅助视图。

后端分别保存“这条回复是否完整”“这个输入是否已处理”“相关工作是否完成”“外部操作的真实结果”，因为这些事实可以同时处于不同状态。它们不成为用户必须选择的模式。没有持续执行需求的问答不创建空 Goal；实际操作仍沿已有工作准入和权限入口执行，短耗时不成为绕过准入的理由。

工作可靠移交给独立执行器或可恢复 continuation 后，允许交还消费回合；新消息能否即时得到模型回答还取决于真实宿主的运行与插话能力。缺少这些能力时保留新输入并准确显示等待，不用新增 consumer session 冒充模型并行。断线、真实订阅续期和响应丢失按已有恢复契约自动接续；只有缺少必要信息、需要新增授权或外部结果确实无法核实时，才出现对应事项上的一个明确动作。

本设计不把“零确认”解释为跳过授权。已经有的有效授权不再重复询问；新授权的范围、身份绑定与撤销仍由服务端执行。房间和微信沿用 `COLLABORATION_DOT_WEIXIN_PARITY_2026-11-10.md` 已建立的本人身份、原输入快照和连续授权契约；转发、引用、附件与第三方文本仍是输入数据，不会自己增加授权。

### 1.2 范围

本文负责消费回合、聊天／工作入口的校验分层、回执恢复、分页、让出与入口验收。宿主稳定身份、配对、跨房间复用、撤销代际由文档二负责。对外投递、诊断证据、调度公平性、容量指标、上线与旧协议收口由文档三负责。

不改现有 Goal／work／operation 的主键，不把聊天消息正文作为操作请求自动执行，不将宿主连接或通知票据解释为工作授权。

## 3. 三份文档共用的不变量

| 编号 | 不变量 | 违反时的失败范围 |
| --- | --- | --- |
| I1 | 房间成员身份绑定 owner、space、conversation、member、grant、binding_generation；宿主另绑定 host_connection_id 与 host_revocation_epoch | 当前身份的全部新效果被拒；不影响其他独立身份 |

| I4 | 同一对话中的消息、工作准入、实际执行、正式成果发布和对外投递按具体效果校验 | A 项目的变化不能自动禁止 B 的独立沟通；关联 work 本身不产生工作效果 |
| I5 | 请求键和原回执定义已提交效果；超时、断线、取消和重启不证明未执行 | unknown 沿原操作 ID／原请求键核对，禁止换键重跑 |
| I6 | 一次回复的消息、原输入处理证据、每个预期渠道的投递处置、适用时的逻辑 outbox、回执、回合关联和可选让出同事务提交 | 必需记录整体回滚或整体存在，不能“消息有了但防重没有”；未请求外发不制造 outbox |
| I7 | 自然故障、单纯通知暂停、成员／宿主停用和原交办授权撤销是不同事实；撤销闸优先于任何旧策略 | 运输故障不撤销项目授权；授权撤销仅停止相关新效果 |
| I8 | 新一轮领取不得继承旧 fence；历史回执不得改变当前回合 | 老客户端不能复活旧回合，新回合不会被旧重放交还 |
| I9 | 通知受理、票据领取、输入处理、工作完成、渠道受理分别有原始证据 | 不从时间重叠或单个 2xx 推断 dot 已处理 |
| I10 | 版本／依赖 token 用于发现冲突，不能充当授权 | 同事务读取当前身份、对象能力和意图；外部派发前再复查 |
| I11 | 同一输入可以包含问答和执行要求；同一 work 可以有任意合法讨论 | 一条回复完整不能吞掉尚未处理的执行要求；工作完成、暂停或失败不封闭相关对话 |

本文中的 host 字段以文档二为准。`authority_version` 与 `health_version` 分开；心跳和诊断更新不能使授权预览不断过期。纯项目范围变化不提升 host 身份撤销 epoch。

## 4. 交互流程与反馈

### 4.1 一个输入可以同时产生回复和工作

输入保存之后，dot 判断应答方式，服务端决定其是否有权执行。一次明确交办先持久创建／恢复原工作，再按真实阶段简短回复：仅已准入写“已接收，正在安排”；已有实际派发证据才写“开始处理，完成后回到这里”。进展回复不得把原工作标成完成；原输入只有在持久工作准入成功后才记为已移交，不能因为生成了一句进展就被吞掉。

这里的应答方式可以自然组合，不是对输入做互斥的 chat/work 分类。比如“解释原因，能修就修”可以先给有证据的解释，再继续同一目标的执行；工作已接收不要求每次都先发一条模板式确认。服务端校验结构化动作、来源和证据，不能声称能仅靠自然语言可靠推断所有执行意图。

若已有同一来源对应的原工作，恢复这个工作和已完成步骤，不新建第二份 Goal。“为什么这样做”“到哪一步了”“先给我看看截图”只是与工作有关的沟通，可以只回答当前这条输入，不修订 intent、不要求工作已结束。真正改变目标、约束或执行安排的补充才沿已有 work_id 和 intent_revision 进入原续办／控制语义；同一条补充的重复投递不增加第二次意图修订。

输入处理证据按具体 message/version/成员保存。回答追问不能顺带确认原交办；混合输入中的执行部分尚未准入时，应保留原待办或持久化已有工作流中的未办事项，不能因解释文字 complete 而吞掉它。后续待办引用原输入、已完成的回答和原工作；恢复时不重复发同一段解释，不另建一套待办调度器。

### 4.2 用户可见的结果

| 场景 | 系统自动动作 | 用户看到什么 |
| --- | --- | --- |
| 一页普通聊天 | 领取时带第一页；提交回复并在条件满足时交还 | 原话题出现一条回复；不展示 lease、fence 等内部字段 |
| 已授权任务 | 持久化原工作；确有独立执行／恢复责任者时交还回合 | 原时间线继续沟通，原工作状态更新，不需要再次“确认执行” |
| 工作中问原因、进度或索取预览 | 读取原工作的当前可见事实，回复当前追问，可引用部分成果 | 自然回答，不新建工作、不强制结项，不要求切换模式 |
| 做工作时聊另一个话题 | 新输入不修改无关工作意图；按真实宿主能力处理或排队 | 同一输入框可继续发消息；即时回答与排队状态均符合实际 |
| 撤销 A 项目，回复 B | 按 B 的来源、引用和当前权限完成回复 | B 正常回复；A 的工作卡片显示范围变化 |
| 当前来源已不可读 | 阻止模型继续取源内容；系统投影生成最小阻塞说明 | 房主在原项看到“当前范围已变化”；不要求 dot 先成功调用一个必然被拒的 reply 才能说明原因 |
| 订阅自然到期 | 续期器恢复路线；有效旧回合在有界期限内收尾 | 一般不弹窗；恢复持续超出阈值时在连接状态行提示 |
| 回复提交后响应丢失 | 同键取原回执；重建当前可见投影 | 仍是一条回复，不重复发微信 |
| 原操作结果未知 | 继续查原 operation；保留其他话题处理 | 只在相关工作显示“正在核对原操作结果” |
| 多页或持续新输入 | 完成有界批次后交还；未处理项持久保留并安排后续唤醒 | 不要求用户手动“继续”；后台不空转轮询 |
| 需要新增授权或缺少决定性信息 | 提出一个定位到项目／工作／缺失字段的动作 | 不出现笼统“请确认权限”或重复授权对话 |

“已保存”“处理中”“工作完成”和“微信已受理”的呈现以文档三的证据投影为准。用户界面不把回合结束展示为工作完成，也不把微信受理展示为用户已读。

### 4.3 连续上下文与插话契约

消费回合只是本次领取和提交资格；其交还、过期或更换，不创建新的用户话题，也不要求用户重讲背景。后续运行通过现有授权 context／inbox／message／work 读取，按需得到：当前目标及约束、最近有效补充、已回答内容、尚未处理的要求、原 work／operation 及成果引用、当前意图、下一步与恢复责任者。关键决定带来源和版本；摘要只辅助理解，不替代当前原始记录、权限或操作回执。不复制模型私有思考，不把其他房间和私人聊天的记忆自动并入本房间。

宿主支持原生对话续接或运行中插话时，适配器使用真实能力；没有该能力时，通过可核对的工作上下文恢复连续性，并让新消息等待真实可用的处理机会。能够保存消息、建立多个租约或发出 webhook，都不证明模型正在并行思考。文档二第 10.4 节规定能力证据和降级呈现。

“按刚才第二种做”“这处改一下”“先暂停”优先关联明确引用及当前已有上下文。系统先查原记录；当仍有多个合理目标且会影响实际动作时，只问缺少的目标，不要求用户重填整份任务。房间与微信可在已验证的同一身份、同一房间及有效权限内关联原工作；不能仅凭两个消息时间接近或同一 host ID，擅自合并任务与私聊。

用户的明确更正或停止请求应尽快被持久记录，并在下一次受影响效果提交／派发前检查。宿主是否能立即打断当前推理或取消已经在途的外部操作要分别验证；尚未完成取消时显示“已收到停止请求，正在停止后续步骤”，不能提前显示“已全部停止”。独立提问不修订工作意图，真正更正只影响相关动作。

## 5. 判定管线：先恢复，再决定是否允许新效果

### 5.1 四层检查

| 层 | 输入 | 用途 |
| --- | --- | --- |
| 身份层 | 当前 principal、房间／成员、binding_generation、host 撤销 epoch、连接证明 | 判断是谁、属于哪个席位、是否已被停用；不依赖别的房间 |
| 回执层 | 同一业务请求键、固定业务指纹、调用方有权恢复的原记录 | 已提交则只读恢复；不需要活动租约，不产生第二次效果 |
| 对象层 | 当前来源、附件、成果、项目＋环境、work／intent／epoch、具体能力与目标 | 判断这次读写是否仍允许、依赖是否改变 |
| 提交层 | 活动会话、当前 fence、deadline、CAS 版本、数据库唯一约束 | 同事务提交一次；并发重试拿同一记录或明确冲突 |

新效果的对象检查与会话校验均在写事务内完成。实现可以先做廉价身份／格式检查，但不得在事务外算出“allowed=true”后拿它直接写入。不得跨事务复用投影缓存作为授权依据。

外部操作不能把数据库事务延长到网络往返。事务内保存持久待派发记录，dispatcher 派发前重新验证当前授权、工作意图与目标；撤销和外部请求已在途的竞争，按原 operation 记录并核对，不能保证撤销逆转已经发生的外部效果。

### 5.2 范围摘要的正确位置

`scope_digest` 是变化证据，不是完整授权，也不是可以删掉对象检查的理由。v1 的“变更后新领取能通过，因此移除旧回合摘要一定安全”不能单独构成证明：旧回合可能持有旧来源、旧计划和旧缓存。放宽必须以本文件第 12 节入口清单和第 15 节竞争用例全部成立为条件。

建议保存以下服务端字段，均为拟新增／调整；不是客户端自行声明的能力：

| 字段 | 语义 |
| --- | --- |
| `turn_policy` | 新领取时固定为 strict 或 decoupled；shadow 仍按 strict 决策 |
| `policy_revision` | 对应可审计的服务端判定规则版本 |
| `scope_digest_at_begin` | 原准入范围的不可变证据；不随 scope_updated 刷新 |
| `observed_scope_digest` | 当前已观察范围，用于去重诊断；不能替代原证据 |
| `hard_deadline` | 此回合最长存续时刻；heartbeat 不得延长 |
| `host_connection_id/host_revocation_epoch` | 领取时绑定的独立宿主身份与撤销代际 |
| `route_generation` | 原唤醒路线代际，用于解释恢复；不当作项目授权 |

旧行迁移时按 strict 标记，并从现有 created／lease_until 给出保守截止，不伪造新式身份。旧 scope_digest 可能已经在兼容新增时刷新，因此保留原值并标注证据来源为 legacy_last_observed，不能把它冒称为不可恢复的原始准入快照；只有新领取行的 scope_digest_at_begin 能保证真正不可变。新代码不能再把项目权限收窄实现为“把所有活动会话的原摘要改成现在”。

### 5.3 scope_updated 的效果

项目、能力或环境范围变化时：写入具体受影响集合的权限通知，推进收件箱 dirty_revision；阻止相应 work 后续不再获授权的步骤；保持身份仍有效的聊天回合。若房间暂停、成员移除／暂停、换绑或宿主撤销，执行当前身份闸并封住相应新效果。

通知需要包含可机器判断的影响范围，例如 project_id、environment_id、work_id、change_kind；旧通知缺少定位信息时仍走保守依赖检查，不让模型根据自然语言猜它是否相关。通知正文不得携带已撤销项目的内容。

## 6. 来源与工作依赖：无关变化不阻塞

### 6.1 依赖清单

`dirty_revision` 表示收件箱发生了变化，不能一概等价于本次意图失效。每个写入口应由服务端生成依赖清单；客户端传回的 source/version/token 只用于核对自己基于哪份输入作决定。

| 动作 | 必须核对的冲突依赖 | 不应单独造成冲突的变化 |
| --- | --- | --- |
| 普通回复 | 原来源仍可见且版本／摘要一致、原收件成员、同一话题在读取后新增的有效输入或更正 | 其他话题聊天、其他项目权限通知、其他工作的进度 |
| 关联工作的普通消息 | 当前回复来源及更正、实际引用的工作状态／成果版本与精确可见性；一般讨论不要求主责或执行权 | 仅有关联 work、工作暂停／完成、无关工作进度；不将整个工作生命周期用作回复门槛 |
| 开工 | 原来源与明确任务证据、本人批准、参与成员／项目／环境、当前能力与目标、来源唯一工作映射 | 独立聊天增加的收件箱版本 |
| 续办 | 原 Goal、最新 intent_revision、coordinator_epoch、最新补充来源、旧操作已核对、具体工作项能力 | 无关话题输入 |
| 工作项写操作 | work expected_version、当前意图／epoch、分配成员、原批准与当前授权交集、执行目标 | 其他工作或项目的独立变动 |
| 最终汇总 | 当前意图／epoch、结果集合精确匹配、所有操作已结算、所有引用当前可见 | 无关普通聊天 |
| 上下文修订 | expected_context_version、被替代事实／来源、每个涉及项目＋环境 | 无关的系统进度提示 |
| 确认控制通知 | 具体通知 ID／版本仍有效、当前身份、通知类型允许确认 | 别的独立通知晚到 |
| 回合排空 | 当前 dirty_revision、无尚待当前成员处理的有效条目 | 无；排空本来就是成员收件箱级事实 |

### 6.2 实施方式

首先保留已有 `guard_reply_revision` 的同话题比较，去除无关权限通知的全局拦截，但仍实时校验来源和引用。工作入口只有在清单中的依赖全部可追溯时，才从严格全局版本切到对象依赖检查。

建议新增集中入口 `guard_dependencies(action, raw, context)`，由服务端固定动作映射；未登记的写动作默认 strict。不要让调用方用 `purpose='chat'` 绕过工作校验。`purpose` 是服务端从实际动作、来源关联和引用字段推导的内部枚举。

同话题在模型思考时收到“先别做”“改成另一项”等输入，旧请求必须返回来源／意图冲突。仅当服务器能证明旧请求尚未产生任何效果、来源意图未变、变化与此动作无关时，宿主才可自动刷新依赖再尝试。同键请求若提交结果未知，先查原回执；不得把重新读取理解成可以更换参数或新建操作。

## 7. 回合、路线和撤销的生命周期

### 7.1 领取与原领取恢复分开

原 `begin` 的重试路径必须在“新领取需要有效订阅”的检查前匹配原请求。核对当前仍有效的成员身份、host 撤销闸、原请求指纹、原 wake_ticket 哈希、票据关联的原会话、grant 与 binding_generation。命中后只返回该原会话的真实状态；不生成新 proof、不延长 lease、不增加 fence，不重领票据。

恢复同一条原记录时可以返回原 proof（按现有加密存储解密）；它的写能力仍受当前 fence、租约、hard_deadline 和撤销闸限制。没有匹配原请求时，再执行新领取的全部要求：有效当前路线、真实未消费票据、唯一活动回合、单调 fence 和当前权限上下文。

旧 binding_generation 或 host 撤销 epoch 不通过“原 begin 重试”复活。房主可以走只读历史诊断查看旧回合；新成员按当前身份重新连接，原工作另按已有恢复流程核对。

### 7.2 自然过期的有界收尾

| 路线／身份情况 | 新领取 | 已领取回合读写 | 原回执恢复 |
| --- | --- | --- | --- |
| 路线健康、身份有效 | 正常 | 在租约与 hard_deadline 内正常 | 正常 |
| 原路线自然到期／临时续期失败 | 等续期完成 | 仅持有过期前已领取回合者，按有限收尾期限处理 | 当前身份允许时正常 |
| 会话 lease 已过期或被新 fence 替代 | 按当前票据重新领取 | 原会话不能写，也不能靠续期复活 | 只读恢复原效果 |
| 只暂停通知运输，成员与交办授权保持有效 | 不允许，等待通知恢复 | 原回合在有限期限内收尾；持久原工作按其当前授权继续 | 当前获准身份可恢复 |
| 宿主／成员／房间被明确停用，或原交办授权被撤销 | 停用身份拒绝；局部工作撤权不挡独立聊天领取 | 身份停用阻止该身份新效果；项目撤权只阻止相关工作效果 | 不返新能力；房主诊断保留，成员历史读取受当前身份约束 |
| 换绑／撤销 epoch 改变 | 使用新身份、新路线 | 旧 proof 不再提交效果 | 旧效果只能由当前获准的历史查询路径查看 |

建议初值为每次 lease 上限沿用现有 300 秒、回合最大年龄 3,600 秒、自然过期收尾上限 900 秒。它们是待实测校准的策略值，必须显示在诊断中，不是宿主耗时的已知分布。

有效截止时间始终取当前 lease、领取时固定 hard_deadline，以及原路线已自然到期时的 `expires_at + grace` 中最早者。重试不能把宽限起点重置成 now；心跳不能延长 hard_deadline；新订阅不能把旧回合绑定偷偷换成另一条路线。路线仍健康的长任务也不依赖无限续租，交给持久工作流等待原操作。这里限制的是一次消费者占用，不限制工作总时长；跨小时或跨日工作保留原 Goal、work、operation 和恢复责任者，在新回合继续核对原结果。

### 7.3 读入口不能借宽限绕过领取

现有健康路线的普通只读入口保持成员身份检查和逐对象过滤。路线已自然到期时，如果读取依赖收尾宽限，必须提供同一活动回合的 `consumer_session_id/fence/proof`，并校验该回合在路线到期前已经领取。

拟在相应读取契约加入一组可选、全有或全无的回合凭据；不支持该字段的客户端仍按原严格读法执行。`include_inbox` 的服务端内部读取可直接使用刚领取的原会话。`session_binding()` 不能仅凭 member + expired subscription 给任何调用方开放宽限。

### 7.4 权限撤销不能收回已读上下文

服务端可以阻止后续读取、结构化引用和新效果，不能让模型忘记已经进入宿主上下文的文本。这不成为跨项目转述的许可：宿主处理说明仍要求只使用本次来源及当前可见引用，不把已失权项目的数据写入其他话题。

对需要强上下文隔离的房间，只有宿主实际支持并建立了独立聊天／执行上下文时，才能据此给出隔离保证。新建 host_connection_id 或成员行本身不会清除或隔离模型上下文，也不能用“令旧会话过期”冒充上下文清除。所有新回复继承来源项目＋环境标记，成果／附件增加自己的来源标签；混合引用必须满足全部可见范围。

## 8. 回执恢复：不会重发，也不会泄漏旧正文

### 8.1 固定业务身份

继续使用原 `room_runtime_receipts` 唯一键。相同请求键携带不同业务正文、来源版本、成果集合或意图，返回 `IDEMPOTENCY_CONFLICT`，不覆盖旧结果。

回合 ID、fence、proof、expected_inbox_revision、connection_proof 继续不进入业务指纹。binding_generation 在现有指纹中的行为必须保留，不能迁移时偷偷重算旧指纹。跨回合自动恢复只承诺同一有效绑定；换绑后的历史恢复走只读原回执入口，由当前身份与当前可见性授权。

`yield_after` 默认 false 时须不进入旧请求的规范化序列，保持旧指纹；true 是本次请求的固定选项，重试不得偷偷改为 false。字段支持必须在提交前通过当前工具 schema／能力清单确认。遇到未知提交结果，禁止以“旧服务器不支持”为由删字段后换键重发。

| 字段类别 | 例子 | 指纹规则 |
| --- | --- | --- |
| 固定业务内容 | source ID／version／digest、body、complete、publish_work 的省略／false／true 状态、成果集合、工作 intent／epoch、成员与绑定世代 | 纳入；更改后不能继续占用原请求键 |
| 原子效果选项 | reply 的 yield_after、yield 的 yield_mode | 纳入语义指纹；默认 false／if_drained 与历史省略值按对应版本规范化；true 与 false、两种 mode 互换均冲突 |
| 易轮换调用凭据 | consumer_session_id／fence／proof、connection_proof | reply 业务指纹排除，但每次当前身份核对；独立 lease 动作保持原会话动作身份 |
| 观察版本 | reply 的 expected_inbox_revision | 排除业务指纹；新效果仍用它做依赖检查 |
| 规范版本 | receipt fingerprint_schema_version | 新回执固定记录；旧行按 legacy v1 解码，绝不使用当前默认值重算历史 |

若实现需要新的指纹算法，先加入版本化 decoder 与兼容构建，再生成新版本回执；不能覆盖旧 fingerprint。相同用户输入允许多条合法进展和最终回复，每条有自己的明确业务请求身份；最终 publication 另受 `(goal_id, intent_revision)` 唯一约束。防重验收针对同一请求，不限制整个话题只能有一条回复。

### 8.2 回放顺序与保留期

1. 校验当前 principal 和成员身份、原绑定及当前安全撤销闸。
2. 核对调用方自己的原会话 proof，或已授权的只读原回执查询上下文；proof 只证明可恢复哪条记录。
3. 使用原指纹算法查同键收据；命中后使用统一回执解码器，保留 `history_retention.py::replay_response` 的过期墓碑语义。
4. 已提交且内容当前可见：返回原消息的当前授权投影。已不可见：仅返回已提交事实、原 message_id 和 withheld，不返回正文、引用、路径、诊断摘要或不可见项目名。
5. 原响应已按保留策略压缩：返回 `IDEMPOTENCY_RESPONSE_EXPIRED` 和可用原记录引用；不得当成“没执行过”。防重键与指纹墓碑保留。
6. 未命中才走当前活动租约、来源、依赖和效果授权，执行新事务。

暂停、移除与安全撤销不是回执查询的绕过理由。成员无权查询时，房主保留可审计的历史视图；不能为恢复一条回复把已撤销身份重新激活。

### 8.3 响应区分历史与现在

以下为拟采用的响应结构，字段通过现有 query／act 动作暴露，不新增顶层工具：

```json
{
  "replayed": true,
  "historical_result": {
    "committed": true,
    "message_id": "original-message-id",
    "source_message_id": "original-source-id",
    "original_session_id": "original-consumer-session-id",
    "complete": true,
    "yielded_at_commit": true
  },
  "current_consumer": {
    "consumer_session_id": "current-session-id",
    "state": "active",
    "more": true
  },
  "message": {"id": "original-message-id", "withheld": true},
  "effects_created": false
}
```

没有当前可验证回合时 `current_consumer` 为 null。新回合重放旧回复，不因为历史 `yielded_at_commit=true` 而停止处理当前收件箱。重放不再追加 turn→reply 关联、不确认新的来源、不创建 outbox、不改变新回合租约。

## 9. 回复与让出的原子事务

### 9.1 原子边界

一次新回复在同一写事务内完成：当前身份／对象授权检查 → 固定来源及依赖 → 插入逻辑回复 → 持久化原输入处理证据 → 保存每个预期回传路由的投递处置与可发送路由的 outbox → 记录原会话关联 → 条件让出 → 保存幂等回执。外部发送发生在事务之后，由文档三的 worker 消费原 outbox。

处置枚举以文档三 `EnqueueResult` 为唯一存储契约：`queued / existing / not_requested / blocked / rejected`。未请求该渠道时记 `not_requested`；原回传授权已撤销记 `blocked`，用 `reason_code` 说明撤销。已有有效出站授权及确定原收件对象、仅临时断线／续期／上下文未就绪时，仍保存原逻辑投递与 outbox，处置为 `queued`，投递内部进入 `waiting_context` 等可自动恢复状态，不能变成无 outbox 的人工授权阻塞。确定不可修复的内容或渠道业务拒绝记 `rejected`。原来源版本／摘要失效属于回复准入冲突，不能归入渠道处置后继续保存旧答复。渠道自身不可用不回滚合法房间回复；存储或唯一性错误仍使整个事务回滚。

原会话关联使用文档三唯一 DDL 所定义的 `room_reply_origins`（message_id、consumer_session_id、member_id、binding_generation、request_digest、created）。request_digest 必须与该原 receipt 使用的规范业务指纹完全相同，不是 idempotency_key 的单独哈希。旧消息没有原证据则关联标 unknown，不根据时间猜。该表只保存因果关系，不承担第二套调度职责。

以下为建议伪代码；新增函数名表示职责边界，不表示代码库已有该函数。所有重复执行都先经过唯一回执键，且该流程运行在原 `Store.transaction()` 的写事务内。

```python
def reply(raw, principal):
    args = validate_reply(raw)
    with store.transaction():
        identity = require_current_identity(args, principal)
        prior = lookup_original_receipt(identity, args)
        if prior is not None:
            return project_receipt_with_current_visibility(prior, identity, args)

        session = require_live_fenced_turn(identity, args)
        source = require_current_source(identity, args)
        dependencies = derive_dependencies_from_action(source, args)
        guard_current_authority_and_dependencies(identity, dependencies, args)
        publication = validate_optional_publication(identity, source, args)

        message = persist_reply_once(identity, source, args)
        if publication is not None:
            persist_publication_once(message, publication)
        handling = record_source_handling(message, source, args)
        delivery_dispositions = record_route_dispositions_and_eligible_outbox(message, handling)
        insert_reply_origin(session, message, receipt_business_fingerprint(args))

        turn_result = maybe_yield_after_reply(session, args, handling)
        receipt = save_original_receipt(message, delivery_dispositions, turn_result, args)
    return project_receipt_with_current_visibility(receipt, identity, args)
```

内部存储／一致性错误使以上数据库效果一起回滚；渠道不可用是可持久化的业务处置，不是这样的存储错误。已经提交后响应发送失败，下一次只读恢复原收据。投递 provider 超时不回滚逻辑回复、不重新执行工作；只修改该原投递的待核对状态。`project_receipt_with_current_visibility` 必须在新的读取快照里重新解析当前身份与精确可见性，不能使用提交前缓存来回放内容；可见性的线性化时点是该读取快照，不承诺撤销能收回已经发出的响应字节。

### 9.2 同一回复入口，可选正式发表效果

现有 `reply()` 在来源关联工作且 complete=true 时进入 publication 校验，因此不能直接改写旧 complete 的含义。v2.1 不实施回复三分类，改为可选 `publish_work`：只在工具 schema／能力清单声明 `explicit_publication` 后使用。适配器为普通回复自动填 false；只有请求正式发表工作结果时才填 true，用户不需要选择消息类型。

| publish_work | 服务端校验与效果 | complete=true 的含义 |
| --- | --- | --- |
| 省略 | 沿用现有 related＋complete 判定 | 关联工作时仍必须通过最终 publication 校验 |
| false | 同一普通回复，可有关联 work；核对来源、当前可见性及具体依赖，允许引用有效成果子集；不接受 outcome／工作终态修改，不写 publication | 这条消息文字完整；输入处理证据按第 4.1 节单独确定 |
| true | 必须关联经验证的原 Goal、complete=true，并通过原 terminal／完整结果集合／成果可见性／当前意图／主责检查 | 消息完整，且当前工作意图的最终汇总已持久发表 |

false 不跳过来源、授权、引用版本和当前依赖检查；它只不附加工作状态变化。普通回复的可见性检查不能复用要求主责、全部操作已结算的 `native.guard(action='publish')`。回答“为什么这样设计”不需要执行权；声称当前进度时核对实际依据的状态；讨论旧方案时明确其历史版本，不冒称当前计划。消息包含部分可见成果与正式发表完整结果集是两种不同效果。

省略、false、true 是三个不同的协议输入；验证模型必须保留字段是否提供，不能用默认 false 或序列化过滤 false 抹掉区别。显式字段进入业务指纹并持久保存；旧行按旧规范读取，不重算旧指纹。同键从省略改为 false、false 改 true 或更换成果集合均为异参冲突。未知提交结果先查原回执，不为兼容删字段重试；旧服务没有该能力时继续旧协议，不能宣称已经支持统一消息语义。

沟通位置与执行授权依据分别核对。`source_message_id`／现有 `reply_to_id` 继续指向本次实际回复的输入；正式发表所需的本人原交办、当前 intent source、原批准与主责，从同一 Goal 的持久记录解析。当前追问必须与该 Goal 有可验证关联且在同一有效房间／可见范围，不能用随意指定的 work ID 替代授权。新路径允许在当前追问下附带正式发表，原授权输入的版本／摘要仍单独核对；旧路径保持“回复当前意图原输入”的规则。

消息、可选正式发表、当前输入处理证据、适用渠道处置和回执仍同事务保存。`(goal_id, intent_revision)` 仍只允许一次正式发表；工作已发表后，后续普通问答可引用原成果，不新增第二份发表。消息回传当前输入的原渠道；原工作应回传的渠道继续按原路由契约处理，同一消息／目标只排一次，不能因追问在另一端就给所有渠道广播。具体路由与原入站证据必须可审计。

### 9.3 `yield_after` 的精确定义

`yield_after=true` 仅用于 complete=true 的本次回复。服务端在回复已经持久化、原来源已按真实处理结果确认后，尝试原子排空并让出。

排空成功须同时满足：当前 fence 仍属于这条会话；当前租约和 hard_deadline 有效；客户端读取版本与当前 dirty_revision 一致；当前身份下没有未处理的有效收件项；会话状态 CAS 成功。建议更新明确带上 `(session_id, member_id, generation, fence, state='active')` 条件，并检查 rowcount。

排空失败不是回复失败。回复和回执照常提交，返回 `yielded_at_commit=false`、当前 inbox_revision、more 及原因；宿主继续处理或按 9.4 有界让出。

在显式 publish_work=false 的新路径中，complete 表示该条消息已结束，不表示工作完成。服务端按当前输入的回答、准入、变更或移交证据判断处理结果，不允许仅凭 complete 吞掉未准入要求。省略 publish_work 时仍按原 publication 语义处理。

### 9.4 有待办时也能主动让出

维持原 `room_consumer_yield` 的默认 `if_drained`。拟增加能力声明后的 `yield_mode='continue_later'`：在同一事务内关闭当前回合，保留全部未确认项，并记录一次后续唤醒需求。返回 `pending_preserved=true`、`continuation_queued=true`；不把 drained_revision 冒进到当前 dirty_revision。

后续通知由已有投递调度器合并和重试，遵守文档二／三的 host 并发与退避。仅对当前可处理且未持久移交的待办创建一条合并需求，并记录最早 eligible_at；只剩等待后台结果的条目时，等待原 operation／result 事件，不立即自唤醒。离线和限流按有界指数退避处理。不能对有 active fence 的同一成员并发开第二个回合，也不能在每一条剩余消息上制造一张新票据。新输入、旧未处理项和 continuation demand 的原子提交保证进程在让出后崩溃仍可恢复；到期需求签发新票据重新领取，不复活旧 turn。

采用有界批次，初始建议单回合完成最多 12 个普通输入或 4 页后评估让出；这是公平性调度参数，不限制用户任务大小。临近 hard_deadline 时优先保存当前进展与原操作引用，再让出，不等待租约硬超时。

### 9.5 工作通知已处理不等于工作完成

不能直接把 work_ready 加入普通 ack 白名单。拟由原工作流程在以下真实事务点记录通知处理证据：工作项已领取并存在可恢复租约及独立持久 continuation；或操作已持久派发且其 operation_id 可恢复；或已明确移交给另一个有效工作消费者。证据至少包含 work_id、work_version、intent_revision、assignee_member_id、原 receipt／operation 引用及 recovery_owner。只有内存状态或一个即将随会话结束的租约不够；移交记录与原引用必须同事务保存。

仅有 queued 工作或模型说“稍后处理”不算已移交。对执行进程尚无独立持久 continuation 的步骤，保留待办并安排后续回合，不伪造“后台会自动做”。工作完成仍由原 operation 终态、结果归档、验收和 publication 证明。

完成或失败产生新的 result_ready／settled 事件，主责在新消费回合读取并回复。消费回合的让出不取消工作租约；工作取消也不假装撤回已在途的外部请求。

## 10. 分页、可见性变化与持续输入

### 10.1 游标只定位，不授权

新游标的签名域包含 schema_version、owner／space／conversation、member、binding_generation、队列代际、after_sequence 和本次扫描上界；不以 scope_digest 作为有效性的硬条件。每一页仍按当前项目＋环境、来源状态与对象权限过滤，拒绝跨成员、跨房间和旧绑定游标。

首次读取固定扫描上界，确保持续新输入不会使一轮分页永远没有末页。上界后的输入在下一批读取；`pagination_complete=true` 只表示该扫描窗口结束，不表示成员已排空。排空只由当前 dirty_revision + 当前有效待办检查证明。

### 10.2 新增可见性不能漏旧条目

权限变化可能使游标之前的记录重新可见。游标可携带非授权用途的 visibility_digest；当前可见集合变化时返回 `visibility_changed=true` 和服务端签发的 `restart_cursor`，允许当前页处理后从头重扫当前窗口。重扫不会再执行已处理项，已确认／已移交记录与业务幂等键去重。

发生可见性变化时不让回合过期，也不要求用户确认。范围减少时过滤失权条目；范围增加时重扫补齐。不要把“页面返回空数组”当成排空，仍需看 next_cursor／扫描状态。

### 10.3 有界查询与缓存

`_ready` 目前可能逐页扫完大量不可见历史；在写事务内无界扫描会拖住其他房间。拟将扫描预算、continue_after 与 drain_check_pending 作为内部状态；预算耗尽只表示尚未证明排空，不能返回 drained=true。后台预计算可作为提示，最终排空仍在短写事务以 revision CAS 核对。

持久扫描检查点须绑定 member、generation、dirty_revision 与可见性版本，变化后作废，不能据旧缓存确认新消息。保留适合待处理条目查询的复合索引，使用 EXPLAIN 和大规模不可见前缀数据验证查询计划；具体延迟目标归文档三。

## 11. 成果与所有投影的精确边界

### 11.1 最终汇总独立修正

`publication()` 在 `teams.artifacts()` 取得原成果引用后，逐个从工作项与原 scope 解析精确 `(project_id, environment_id)`，核对当前成员可读集合；附件、产物 URI、工作路由和嵌入结果同样检查。不能只用项目 ID 代替环境边界。

当前意图要求的全部成果集合规则保留。少一项可见成果时，不能偷偷删掉引用然后宣称“全部完成”。原工作与结果保留，房主看到具体范围变化；已有原汇总若已提交，重复请求走回执并按当前可见性缩减投影。

`partial` 是真实业务结果，不能作为授权失败的快捷绕过。上述完整集合规则仅用于正式 publication。普通消息可以展示当前可见、版本有效的成果子集，例如一张预览图或某一步结果，明确已完成和未完成的范围，不改变工作终态，也不宣称全部完成。对这种消息逐项检查引用，不能为了展示一个合法预览而要求先取得所有项目成果。

### 11.2 同一个可见性服务

拟集中实现 `visible_scope_keys(member, principal, goal)`，返回精确项目／环境集合。`message_view`、`public_scope`、`work_routes`、成果列表、历史回执投影、附件读和诊断展开都使用这份语义，避免主体被隐藏但路径、项目名、能力或摘要继续泄漏。

投影过滤不能修改数据库中的原证据、原摘要或回执指纹。withheld 是当前读取的结果，不是删除原历史。

| --- | --- | --- | --- | --- |

| 普通 reply（publish_work=false，可关联 work） | 活动 fence 与 deadline | 当前 source、收件人、具体话题／快照依赖、引用可见；不要求工作主责或终态 | 自然到期可有界收尾 | 同键先恢复，过滤原正文 |
| work start | 活动 fence | 本人输入证明、参与者、原准入规则与当前授权交集 | 参与者须具备可用处理路线；失效则保存等待原输入 | 原 source→Goal 映射优先，不能重建 Goal |

| 省略 publish_work 的兼容 reply | 原活动回合规则 | 保持 related＋complete 触发 publication 的旧语义及原来源约束 | 按原兼容规则 | 按旧指纹恢复，不补默认 false |
| handoff | 活动 fence | 双方成员、当前意图、原工作、引用可见、交接限制 | 接收方有有效可处理路线 | 同一交接原回执 |
| context update | 活动 fence | 主责、context version、事实／来源及全部精确可见范围 | 可合格收尾 | 原修订回执 |
| ack notice | 活动 fence | 具体 notice ID／version、允许确认类型 | 可合格收尾 | 确认不是工作完成 |
| heartbeat | 当前身份、活动 fence | 原会话 deadline | 自然过期内有界，不复活过期会话 | 原心跳请求结果 |
| yield | 当前身份、活动 fence | 排空 CAS 或真实 continuation demand | 不要求未来唤醒健康来关闭旧回合；新唤醒仍待路线恢复 | 重放不操作新回合 |
| 历史 reply receipt | 当前获准历史读取身份 | 原请求键／指纹、当前投影可见性 | 不要求唤醒路线 | tombstone 不等于未执行 |

## 13. 可恢复错误与宿主自动动作

| 错误／状态 | 自动动作 | 何时需要用户 |
| --- | --- | --- |
| 原请求超时，提交未知 | 查原 operation／receipt，保持原键与原参数；有证据后继续 | 原系统长期无法核对且需要用户选择后续动作 |
| `ROOM_INBOX_CHANGED`，独立依赖未变且旧请求明确未提交 | 读取变化，按服务端 next_request 更新无关版本后继续 | 不需要 |
| `ROOM_SOURCE_CHANGED/ROOM_INTENT_CHANGED` | 读取最新本人输入，丢弃尚未提交的旧计划；保留原操作记录 | 只有最新输入本身有决定性歧义 |
| `DOT_CONSUMER_BUSY` | 沿原会话或等待服务端给定恢复时间；不抢占新 fence | 不需要 |
| `DOT_CONSUMER_LEASE_EXPIRED` | 先取原回执；有待办时由当前路线重新唤醒，不用旧 proof 写入 | 自动路线无法恢复时，仅连接项提示 |
| 自然订阅到期 | 续期器修复，原回合有界收尾 | 平台要求交互重新连接时才出现一次具体连接动作 |
| 当前来源／成果已不可见 | 返回最小 blocked/withheld；系统在原工作投影说明范围变化 | 需要新增授权或变更负责人时 |
| `WORK_OPERATION_PENDING` | 查询原操作直到可判定，不创建新工作副本 | 原操作确实无法自动核实时 |
| `IDEMPOTENCY_CONFLICT` | 停止变更该原键；展示原请求冲突，保留记录 | 真实业务内容要另发时，按新的明确意图处理 |
| `IDEMPOTENCY_RESPONSE_EXPIRED` | 查询保留的原对象／审计引用；不重执行 | 原证据确实不可获取时 |
| 成员暂停／房间暂停／host revoked | 不提交新效果，持久保存输入和原待办 | 房主有意恢复或更换绑定；不能自动撤销房主的停用决定 |

错误详情返回可执行的下一步与原对象标识，不返回含敏感路径的堆栈。宿主说明中只包含当前入口需要的简短处理规则；完整故障解释留在 help／诊断，减少每次输入重复的提示词。

## 14. 能力声明、实施顺序与回退

### 14.1 不做复杂协商，但必须识别新字段

服务端改变内部判定不要求模型声明自己理解新授权语义；但 `publish_work`、`yield_after`、带回合的过期读、`yield_mode` 和响应结构确实是协议能力，不能再写成“没有协议变化”。

工具 schema／help 能力清单声明 `explicit_publication`、`reply_yield_after`、`consumer_continue_later`、`expired_route_session_read` 等精确能力；宿主只发送已声明字段。`explicit_publication` 同时包含普通消息可关联工作／引用成果子集、显式正式发表和其授权来源分离契约，不能只加一个布尔字段就宣称支持。服务端以 `turn_policy + policy_revision` 固定已领取回合的处理规则；当前撤销闸和实时对象授权始终优先，不固定过期权限。

默认字段不改变旧请求指纹；旧客户端继续使用显式 reply、inbox、yield 三步，不要求立即升级。旧会话、旧 request digest、旧游标均有明确兼容分支，不能捕获所有 DevError 后盲试另一种游标或指纹。

### 14.2 实施切片

| 切片 | 内容 | 可独立验收的结果 |
| --- | --- | --- |

| C1 | 拆分原领取恢复／新领取；原回复回执先查；统一 tombstone decoder | 响应丢失、lease 到期后不重复效果 |

| C3 | 普通聊天话题依赖、可见性游标、权限通知定位 | 撤 A 不打断 B；同话题更正仍冲突 |
| C4 | 工作入口逐项依赖、后台移交证据、pending yield | 做任务时可继续聊天；未知操作不被重跑 |
| C5 | reply＋ack/handling＋outbox＋receipt＋yield 原子路径 | 普通单页聊天达到两次业务调用，故障重放无第二条回复 |
| C6 | 真实宿主／微信验收、容量与故障注入、兼容窗口收口 | 只有原始证据支持的能力标为完成 |

切片是合并和验证顺序，不把“后做”写成最终可以省略的功能。界面可渐进接入，但最终交付必须覆盖 C0–C6。

### 14.3 开关与策略

继续使用 `CODEPIER_ROOM_CHAT_SCOPE_MODE=strict|shadow|decoupled` 和受实例管理员保护的按房间覆盖。不要要求日常运维手工执行 UPDATE；拟增加经过原 owner/admin 权限校验、expected_version 和 idempotency_key 保护的配置入口，记录操作者、旧值、新值与原因。

shadow 的新旧判定必须来自同一身份／对象快照，且新判定只能产生诊断，不写入任何业务表、不消费票据、不刷新摘要。记录被旧 guard 提前挡住的候选请求，不能仅在成功通过旧路径后统计，造成“零差异”的假象。

v1 的 `mark('room_scope_drift', purpose=..., enforced=...)` 不可照抄：现有 `hub/mcp_request_audit.py::Trace.record` 只有固定阶段与参数白名单，任意新字段可能报 TypeError，未知阶段也可能被丢弃。拟采用类型化协作 telemetry hook，或同时扩展并验证原 stage／field schema；用稳定枚举表达 action_class、decision_class、reason_code、policy_revision。消息正文、request key、member／work／operation ID 不能作为 metrics labels；必要的原始关联放有界诊断记录。诊断失败不改变业务判定、不吞业务异常；有 trace 和无 trace 两条路径都应测试。

开关只决定新回合采用的策略；已经领取的回合按其固定策略有限结束。安全撤销、对象撤权仍立即生效。紧急回退可停止新 decoupled 准入并主动 fence 已领取回合，但须明确记录为中断；原效果按回执恢复，不能假称无感。

### 14.4 旧二进制回退

直接回旧二进制可能不认识新字段、新回执结构、host 撤销闸或 pending yield。因此“改回 strict”不等于可以任意降级二进制。首先停止新能力准入、让现有回合结束／核对、保留全部 outbox 和原收据，再用声明支持新数据与撤销闸的兼容构建回退。

不能改写原 scope 摘要来制造兼容，不能清空队列，不能把 unknown 改为 failed 以便重跑，不能恢复已经撤销的 host。兼容窗口、发布记录和样本由文档三统一管理。

## 15. 验收设计

以下测试文件名均为拟新增或现有文件的扩展建议，不表示已经存在或执行。应复用现有 `tests/test_room_consumer_sessions.py`、`tests/test_room_permissions.py`、`tests/test_room_goal_scope_boundaries.py` 等夹具；实际 fixture 的签名以实现时源码为准。

### 15.1 行为与权限矩阵

| 变化 | B 独立聊天 | A 当前来源回复 | A 新效果 | A 历史回执 | 关键验证 |
| --- | --- | --- | --- | --- | --- |
| 撤销 A 项目 | 成功 | 当前不可见则拒绝 | 拒绝 | 最小 committed/withheld | 通过真实撤权入口，不只改 revision |
| A 从写执行变只读 | 成功 | 仍可读则成功 | 写／execute 拒绝 | 按当前可读投影 | grant、项目 mode、allow_tasks 各自覆盖 |
| A 授权时间到期 | 成功 | 按实时读范围判断 | 拒绝 | 不恢复权限 | 固定测试时钟，覆盖未生成通知的情况 |
| 移除 A 某执行目标 | 成功 | 成功 | 该目标拒绝 | 原 receipt 保留 | 原操作派发前再校验 target |
| 原 grant 失效／host 被撤销 | 对应身份拒绝 | 拒绝 | 拒绝 | 成员拒绝，owner 历史仍可查 | 不能通过 strict 回退恢复身份 |
| 另一房间暂停或换 dot | 成功 | 本房间不受影响 | 按本房间授权 | 正常 | 与文档二跨房间隔离共同验收 |
| 相同项目不同环境被撤销 | 无关环境成功 | 仅失权环境拒绝 | 精确环境拒绝 | 精确环境 withheld | 附件、work_routes、成果引用也覆盖 |

### 15.2 必须有的竞争与故障用例

1. 回复提交前撤权与回复事务竞争：按数据库提交顺序只有一种结果；未获授权效果不能入库。
2. 同键并发 100 次回复：一条逻辑回复、一条原 receipt、一个逻辑 outbox；不能只断言 body 相同。
3. 同键异正文／异来源／异成果：冲突，不覆盖原记录；新请求键不能用来掩盖结果未知。
4. 事务提交后、响应发送前崩溃：重试取得同一 message_id；原回合已让出仍能恢复。
5. 原回合已结束，新回合已领取后重放旧 reply：不增加消息，不增加 turn→reply 关联，不让出新回合。
6. `begin` 已提交而响应丢失，随后原订阅自然到期：恢复原 session／fence，不产生新 fence；未曾领取者仍拒绝。
7. heartbeat、expiry、new begin 和 yield 竞争：同一成员至多一个可写 fence；hard_deadline 不滑动。
8. 路线自然过期与人工停用分别测试：前者有界收尾，后者对应新效果立即停止。
9. 第一页之后新增可见权限：游标前旧未处理输入可重扫；失权条目、失权附件和元数据不再返回。
10. 持续新消息、巨大不可见前缀、多页空结果：分页有界结束，不能误标排空，也不能长事务阻塞其他房间。
11. 一项异步 operation 长时间运行，另一话题到达：原工作有真实执行／恢复责任者，普通回复能有证据地让出；工作未被提前标完成；省略 publish_work 的旧请求保持原 publication 要求，显式 false 不能绕过来源或修改工作状态。
12. `continue_later` 提交后立即重启：未确认项仍在，只产生一次有效后续唤醒需求。
13. 同话题“停止”或新补充在模型计算中到达：旧意图不再派发新效果；已经在途的操作保持真实待核对状态。
14. 成果引用涉及被撤销环境：publication 和 public_scope/work_routes 均拒绝或过滤，不能只测试正文。
15. response tombstone：返回过期原响应语义，防重键不丢失，不调用 perform。
16. 新旧客户端＋兼容二进制组合：默认字段不改变旧 fingerprint；不支持字段的实例不收到新参数；安全撤销闸贯穿回退。

### 15.3 量化目标与证据

| 目标 | 计量方法 | 通过条件 |
| --- | --- | --- |
| 普通聊天两次业务调用 | 真实宿主记录同一输入的 begin(include_inbox) 和 reply(yield_after)，结合原会话关联 | 在单页、无并发更正、路线健康、无需额外上下文的限定场景恰为两次；不能由 reply_count 推断没有读调用 |
| 不重复效果 | 数据库唯一记录＋原 operation／outbox 引用＋故障注入 | 100 次同键重放没有第二条逻辑效果；外部发送另按文档三的供应商证据判定 |
| 无关变化不阻塞 | 按项目／环境／话题矩阵注入真实变更 | B 的成功不以 A 恢复授权为条件；A 的失权效果均被拒 |
| 对话与工作连续 | 工作运行期间发送独立消息并主动让出 | 在真实执行／恢复责任者及宿主能力成立时，工作保留原 ID 继续、新消息可处理；串行宿主如实显示等待，不能以 lease 终止当作工作完成 |
| 回合有限且可恢复 | 固定时钟、服务重启、并发 fence 检查 | deadline 不延长，原 receipt 可恢复，剩余待办可被后续消费 |
| 真实验收 | 隔离房间＋测试项目＋真实 dot 和测试微信，保留脱敏原回执 | 房间与微信同一输入语义、相同授权决策、回复回原位置；未实测标待验证 |

样本量应覆盖故障类别与真实宿主差异。时间窗口用于发现周期问题，不能把“等待 7 天”当成安全证明；低流量部署补确定性竞争测试和主动验收，不为了凑天数延后已经有证据的修复。实际灰度门槛统一见文档三。

### 15.4 统一对话体验验收

以下测试与真实 dot 直接使用的同类过程对照。记录宿主类型、版本、运行和原始回执；不能只用页面原型或 HTTP 成功证明体验一致。

| 场景 | 必须成立的体验与事实 |
| --- | --- |
| “先讨论，不开工”→“按刚才第二种做” | 前半不启动工作；后半沿当前方案准入一次，不要求用户重述、切换模式或重复授权 |
| “解释原因，能修就修” | 同一对话回答并执行；未处理的执行部分持久保留，回答 complete 不吞掉它 |
| 工作中问原因／进度／索取截图 | 回复当前问题，可展示当前可见成果子集；不新建 Goal、不自动改 intent、不要求结项或主责资格 |
| “改成 PNG，其他保持”或“先停下” | 关联原工作并记录真正变更；受影响新效果检查最新决定；不把未知在途操作显示为已取消 |
| 已完成、暂停、失败后继续问原因 | 对话仍可继续，当前可见内容可解释；普通消息不重新打开工作、不重做原操作 |
| 房间交办，微信追问，再回房间继续 | 在已验证同一身份／房间的前提下接上原上下文；当前问答回当前入口，原工作回传策略单独保留 |
| 旧进展外发 unknown 后继续问同一工作 | 按文档三发送新的独立回答；不重发旧未知内容，不解除真正分段／成功依赖 |
| 后台工作跨宿主运行和断线 | 后续运行取到最新要求及原结果；独立执行器继续；未独立派发时显示等待，不能用“后台处理中”掩盖停滞 |
| publish_work 省略／false／true 与重放 | 三态和旧指纹保持；false 只结束消息，true 才正式发表；同键变更三态冲突，原发表唯一 |

用户无需看见 lease、fence、reply 类型或意图版本才能完成以上过程。可观察的等待来自真实宿主／渠道状态；实现者不能用“内部已解耦”替代对这些体验的验证。

## 16. 实现完成清单

勾选项以本地实现和定向回归为准。涉及尚未验证的入口、竞争矩阵和真实环境的条目单独保留。

- [x] 当前身份、当前对象授权、回执恢复和新效果提交各有明确入口；未知动作保持严格。
- [x] 原 begin／reply 在 lease、自然订阅到期和响应丢失后可恢复；同键异参及墓碑语义不退化。
- [x] `decoupled` 回合的项目撤权不作废无关聊天，相关来源／附件／成果／环境投影仍实时过滤。
- [ ] 工作与聊天不被全局 dirty_revision 无差别互相阻塞；同话题与同一 work 意图仍正确冲突。
- [x] 回合有固定期限，异步工作移交保存原持久证据，普通 ack 保留未处理输入。
- [x] reply、handling、outbox、receipt、turn 关联和条件 yield 原子提交，同键重放复用原效果。
- [ ] 分页、排空和 pending yield 在持续输入、权限变化和重启下不漏待办。
- [x] 会话策略固定，当前撤销闸优先。
- [ ] 用实际 reader/writer 组合验证二进制回退。
- [ ] 自动恢复只在证据允许的范围内进行，用户界面只在具体事项需要决定时出现一个明确动作。
