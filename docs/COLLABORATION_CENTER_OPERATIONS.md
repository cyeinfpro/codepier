# 协作中心维护与恢复

本指南描述房间中心的维护边界与检查顺序。发布、CI、部署、真实宿主验收分别记录，不能把本地测试通过写成真实 dot 或微信已接通。

## 数据身份

产品房间沿用 `conversation_rooms.id`，旧项目环境分区仍使用 `collaboration_rooms.id`。新房间工具使用 `conversation_id`；旧公共 action 的 `room_id` 不改变原语义。

成员使用稳定 `member_id`，邀请、宿主绑定世代、订阅、消费者和工作授权分别保存。邀请过期只刷新邀请；订阅问题只恢复该路线。不要删除成员来清除错误，也不要把同名成员合并。

新入口使用 `/api/collaboration/rooms`，规范前端状态由 `collaboration-room-store.js` 管理，界面由 `collaboration-room.js` 呈现。旧协作界面的 12 个 JavaScript/CSS 文件已移出生产静态目录，原 `/static/` 地址不再提供这些文件。字节不变的快照只在 `tests/fixtures/legacy_collaboration_ui` 供明确的兼容测试读取；测试页的资源替换不安装到生产路由。兼容工具与历史回执保留原身份和权限；已切换到新房间的旧写入入口不能另行创建同一房间的新业务输入。

生产旧界面退出与旧 wire 退役分别核对。旧 API 仍用于原连接的兼容与历史回执，不能因为生产页面不再加载旧资源就删掉共享的 Goal、work、operation、lease 或 fence。旧 wire 的版本窗口、调用统计、真实替代旅程及正式退役公告另行记录；本指南不代替这些实际证据。历史设计中的旧 `web/` 路径描述当时版本，不能据此重新把测试快照暴露为生产资源。

## 出现“接入了但没有工作”

按当前成员顺序核对：

1. 房间状态、成员状态与当前绑定世代是否一致。
2. 宿主是否真实登记；当前凭据是否仍有效。
3. 房间通知事件是否有当前身份的有效原生订阅，而非复制其他成员的回调。
4. 当前世代的连接检查是否有真实读取与规范回复证明。
5. 具体工作所需项目、能力、位置与有效期是否仍满足交集。
6. 原消息是否已有工作或原操作，是否仅在等待资源、宿主或回传。

Webhook 接受、模型处理和最终执行成功是不同事实。诊断只展示已记录证据，不手工设置 ready，不制造 probe 回复，也不通过额外授权消除错误提示。

房间设置中的「运行诊断」关联当前成员世代、订阅接受时间、消费者 fence、待办水位、原 message、Goal、工作项、operation 与微信投递分项。它只读取原日志，不领取回调、不消费消息、不解密凭据。队列数量和最老年龄属于返回的当前授权窗口；`truncated` 与 `limits` 明确说明是否列全，不能把窗口数量当全站总量。模型在线、真人已读与外部模型调用数没有独立证据时保持未验证。

诊断中的工作额度来自原 Goal 的计数与上限；通知令牌来自原持久派发预算。两者不授予权限。技术详情保留原对象关联，不包含消息正文、命令、完整回调地址、加入码、连接证明或微信令牌。

原生订阅接口按当前 grant 鉴权，公开过滤器中的成员编号不能充当秘密。共用同一个 grant 的调用方若知道尚未绑定宿主的成员编号，可能抢先完成该成员的回调路线登记，造成接入受阻；回调 challenge 本身不证明它持有独立的成员连接证明。没有受控加入交换返回的 `connection_proof`、该绑定实际回调中的短期票据，以及同一绑定 nonce 的读取和回复，不能把成员标记为可用，也不能消费或启动工作。不要把“回调已接受”解释为宿主之间已实现凭据隔离。核对失败时由房主准备独立候选绑定；候选验证失败不改变原有效路线，成功后才原子切换并使旧消费者失效。

## 页面恢复

切房间和页面卸载会取消无用读取，不取消已经提交的持久操作。房间视图的 epoch、版本和授权投影保护页面不被迟到响应覆盖；相同数据域只允许一次刷新。

页面通过房间 SSE 接收不含正文的变更提示，随后单飞补读持久状态，并保留有界的断线补读。权限变更提示先清除旧投影再重新核对授权；隐藏、切房间与卸载时关闭旧事件流。消息节点按身份更新，输入法组合期间不会替换编辑器。回看旧消息时新消息只显示跳转按钮，不抢滚动位置。草稿保留在当前账号的内存中，不把消息正文或邀请材料写入浏览器持久存储。

网络未知的消息按原 `client_message_id` 查询。准确命中后使用原消息；只有权威 `not_saved` 且当前房间允许写入时，才用同一请求键补交。只读或暂停期间保留草稿与原请求，不重新发送。已经提交的控制请求仍可用原序列化内容和原键核对成功回执。权限投影修订变化时丢弃旧消息缓存，再读取当前可见投影。

## 原工作恢复与主责接替

原生 Goal 的绑定恢复与主责接替沿用原 Goal、批准范围、工作项和 operation 身份，不创建相同目标的第二份工作。详情从持久授权投影读取验收条件、原参与成员、步骤和当前可见的操作回执；控制请求的瞬时响应不是唯一事实来源。

`work.recovery.restore_candidates` 列出原已批准但需要明确恢复当前连接的成员，可以是主责或执行成员；`takeover_candidates` 列出当前具备原主责所需有效范围的已就绪房间成员，也可以包含经房主明确选择的新替代成员。接替只替换原角色身份，不扩大原项目、能力、执行位置或期限。面板只使用服务端返回的候选，不从同名成员或共用凭据推算候选。恢复和接替分别提交原工作 `expected_version`、`expected_intent_revision`、`expected_coordinator_epoch` 与房主明确选择的 `target_member_id`。服务端切换推进版本及相应 fence，旧主责的迟到结果只保留为历史证据。

操作结果未知或仍待停止时，保留原回执并显示等待核对。没有确切未开始证据时不能自动重跑。候选绑定世代、范围、意图或主责版本变化后，面板清空选择并要求重新核对；冲突补读不能代替房主选择。响应未知的控制请求保留原序列化内容和幂等键，使用「核对原操作」重取原结果。

房间 `lead_member_id` 负责后续输入的路由；原工作主责由该工作的 coordinator 和 epoch 决定。不要通过修改房间主责绕过原工作接替约束。

工作历史使用创建时间和原 ID 的稳定分页，当前授权和房间项目版本绑定到签名游标。较早工作更新不会从未读页消失；权限变化后旧游标失效，重新读取首屏。精确工作读取与精确原消息读取仍逐次检查当前房间和项目权限。

## 房间上下文证据

`room_context` 是有来源的读取投影，`room_context_update` 是当前房间主责的 fenced mutation，均复用现有三项 MCP 工具。事实绑定原消息 ID、版本和正文摘要；完成产物额外绑定原工作结果版本与摘要。当前事实的唯一指针和替代记录保存在原消息之外，不改写原消息、工作批准或执行回执。

主责更新核对当前成员、绑定世代、消费者会话、收件箱修订及上下文 CAS 版本。本人明确纠正通过同一消息提交事务撤下旧事实，纠正消息继承原事实的项目来源范围。失去源项目读取权限后，不能借摘要或精确来源入口继续读取；旧消费者也不能恢复已撤下事实。上下文更新不产生工作、执行或新的主动模型唤醒。

页面、成员读取和新加入成员的上下文包都按当前权限裁剪，并返回分页、字节预算和待复核状态。来源变化后不能把旧事实继续标成已核对；需要通过新的原消息证据更新。它不读取宿主私人历史，也不把其他房间全部聊天自动导入。

## 复用连接与附件

已有 dot 列表仅向本人面板返回已验证原连接的安全元数据。复用记录保存 `connection_source_member_id` 与选定的来源绑定世代；每次加入、消费与订阅都重新核对来源有效、同一账号/空间/连接凭据。只有显式跨房间来源关系允许共用原宿主通知路线，同一凭据下无关联的两位 dot 仍不能冒用彼此的通知身份。

目标成员始终独立保存授权、证明、订阅过滤器、消费者与水位。原连接暂停或成功更换世代会使旧复用关系停止准入，不能静默迁到新宿主。成员候选重绑只在验证完成的原子切换中改变当前关系；验证失败保留原连接。

面板上传复用加密附件缓存，上传请求使用原文件的稳定 `X-Upload-Key`。单文件限制 8 MiB，每条消息最多 16 个附件，保留期为 7 天。上传成功不创建消息或工作；发送时在同一事务中核对原房间与附件状态并关联规范消息。未知上传用原字节与原键核对；未知消息仍按原消息键恢复，不能把一个房间的待发附件移到另一个房间。

下载与 `room_attachment_read` 都重新核对当前成员/消息/项目可见性和保留期限。到期显示准确状态，不重生成文件。附件文本与图像均为不可信上下文，不提供新的执行授权。

## 微信连接与投递

账号登录、配对、本人任务许可和房间路由分别检查。确认账号与联系人必须使用真实平台返回。恢复只复用相同账号、联系人、房间和范围的原同意。

投递失败与工作失败分开。工作完成后，恢复的是原渠道 outbox 分项，不重新执行工作。未知发送结果保留未知状态，不能全量重发来获得一个成功提示。

迁移私聊路由前先核对原绑定与版本。原历史与正在运行工作的回复不迁到新房间；撤销旧绑定后未发出的内容留在原处，显示准确原因。

`revoke_tasks` 只撤销该微信的本人任务许可，保留账号、配对与聊天路由。即使许可范围已经变化，仍可沿原 flow 及 `expected_version` 撤销；不需要先扩大范围。撤销 fence 原微信来源工作的后续准入，原 operation 回执继续保存。重新批准时使用当前 `approve_tasks` 投影和新的明确范围确认，不能把聊天恢复当作工作许可恢复。

## 暂停、撤销与停止

暂停房间、成员或工作优先停止新步骤准入。已准入的操作保留原身份并追踪停止回执。恢复不得恢复已撤销权限、延长旧限时授权或自动复活已移除成员。

项目移出只撤去此房间后续使用资格，不能删除底层项目文件。范围变更只影响相关成员和项目，其他工作继续。角色、连接上限、成员批准、工作范围和宿主审批继续分别核对。

成员范围编辑的 `MemberApproval.lifetime` 省略或为空时保留各既有项目的原期限，新增项目采用 `until_revoked`。明确提交期限才重设所选范围。未改变的 capability、执行目标、期限与授权快照不增加 scope version，也不更新原批准时间；新增其他项目不会使依赖原 scope version/fingerprint 的工作失效。新建成员仍保留原来的显式期限默认值。原 timed 记录超过截止时间后按原规则到期，恢复或无改动保存不能把它改为长期授权。

## 迁移与回滚

先核对仓库提交、发布版本、运行镜像与数据库迁移状态。旧 ID、批准、游标、ledger、微信账号密文与发送分项必须保持。

旧房间的 `room_protocol=0` 表示尚未完成房间写入切换。新接口返回 `read_only` 与 `migration`，前端据此显示迁移条件；服务端也独立阻止未迁移房间的新业务写入。只读不妨碍历史、诊断、明确的连接迁移、撤销和安全停止。不能通过直接修改数据库标志或只隐藏按钮来绕过这一边界。

房主通过 `POST /api/collaboration/rooms/{id}/migration` 提交 `action=activate`、当前 `expected_version` 和原 `idempotency_key`。公共 MCP 工具使用 `collaboration`，对应字段为 `action=room_migrate`、`flow_action=activate`、`conversation_id`、`expected_version` 和 `idempotency_key`。同一事务重新检查成员当前验证、准备中绑定、仍可写的旧 dot、订阅及微信、Telegram 路线；有阻断条件时不切换。只有所有条件满足，才记录房间激活并开放新入口。成员 probe 成功只切换该成员，不自动激活整个旧房间；已经返回的就绪投影也不替代提交时的复核。

迁移请求响应未知时，先用原内容和原键核对。只有本次尚未保存、且提交前的版本或迁移条件检查明确拒绝时，接口才返回 `not_saved: true`。页面随后重新显示当前条件并清除旧勾选；不能把一次新的确认自动换成更高版本重试。旧连接的精简身份记录仅保留来源关系，不当作新连接的完整身份或独立证明使用。

迁移期间不要复活原已撤销或到期的授权。仍在使用的旧微信或 Telegram 绑定应由房主明确暂停、解除或按原流程转接，账号密文与发送分项保留；新流程恢复时仍按当前账号、联系人及范围核对。迁移条件中的安全暂停入口核对当前房主、精确绑定和原版本，即使原项目已从房间移除，也只允许暂停原路线及其来源工作，不恢复项目资格。未完成的旧扫码可以沿原流程关闭，不新建账号或登录。

房间切换后，原手工 Goal、旧 dot 和旧渠道入口不能再新建、分配、领取或执行旧工作图中的新步骤。原已准入 operation 的进度、结果、查询和取消仍沿原 ID 核对；历史工作可查看或安全停止，不把旧批准静默转成新房间工作授权。新房间的私有执行适配只接受当前成员、世代与明确批准范围，公共旧 API 不能借此重新开启旧写入面。

切换成员通知前准备并验证新路线。只有原子切换才能改变当前绑定世代与唯一写入消费者；验证失败保留原有效路线。已启动操作仍按原身份核对，迟到旧消费者不得产生新工作。

新版本未接受写入时，可按既有更新器恢复。接受新数据后优先前向修复；回退旧二进制必须使用已验收的兼容准备程序。`prepare_multidot_rollback.py` 发现独立房间、成员或房间原生订阅时会明确拒绝旧版冻结回退；这类数据需要支持房间协议的恢复版本。不得直接还原旧数据库快照丢掉新消息与回执。

清理沿用最多两份已完成快照的策略；活动迁移与唯一恢复证据不能在替代验证前删除。源码包不得携带数据库、账号令牌、加入码或浏览器认证状态。

## 通知容量与测量

房间通知使用原事件派发器的独立限额：全局每秒 8 次、突发 16 次，每位所有者每秒 4 次、突发 8 次，最多同时发送 4 条回调。长命令不会占用这组回调名额；回调等待也不持有数据库事务。一个房间最多 32 个成员，原生订阅可暂存当前路线和每位成员的一个待验证候选，最多 64 条；候选不获得业务消费权。

这些限额意味着，大量成员同时有新输入时，通知领取的 p95 不保证在 1 秒内。dirty 提示会合并，原消息仍逐条保存；必须同时观察消息持久化延迟、最老待办年龄、完整排空时间及实际回复回执。压力报告应计入负载结束后的慢尾，不能只截取发送窗口。合成回调的吞吐不代表真实宿主模型或微信平台的响应能力。

事件发现的分页和实际服务顺位分开保存。只有成功扣减预算并取得原投递租约才推进服务顺位；无令牌的扫描不能跳过尚未获服务的成员。独立有界检查页绕过不可调度订阅，避免禁用旧事件、端点冷却或耗尽的单一所有者阻塞下一页有效成员。多派发器共享 SQLite 顺位与原预算，不提高速率、字节或并发上限。

消息的 conversation 序号、房主消息幂等查找、最近发送计数，以及仍处于 leased 状态的投递使用附加非唯一索引。原查询范围、唯一约束、限频和迁移保留规则不变。历史增长回归比较实际查询的 SQLite 工作量，同时核对结果与迁移完整性；微观查询改善不能代替完整持续负载和排空数据。

## 回归证据

关键自动回归包括：

- `tests/test_room_store_unit.py`：迟到响应、单飞刷新、写后旧读、消息与上传未知状态原键、账号切换清理、权限投影更新、工作补充和附件快照；上下文纠正的原事实与版本快照、普通消息不携纠正字段、独立工作分页可见域和游标失效恢复。
- `tests/test_room_connections.py`：合成原生回调的显式复用、独立 proof/scope/水位、不同 dot 隔离、来源暂停与实际候选换代。
